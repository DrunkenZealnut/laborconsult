## 3. 독립 경로 리뷰 — 설계가 못 본 것

설계 준수와 무관하게 변경 경로를 훑은 결과. **에이전트 보고를 그대로 채택하지 않고 아래 4건은 직접 재현했다.**

### 🔴 H-1 — M1이 자신이 막으려던 회귀에서 값이 **거꾸로 내려간다** (직접 재현)

`PROTECTED_TERMS`를 비워 이번 변경 이전 상태를 재현하고 20,000문서로 측정:

| | M1 | 판정 | 후보 행 | 연차휴가 | 연차휴 | 연장근로 | 연장근 |
|---|---:|:---:|---:|---:|---:|---:|---:|
| 보호 ON (현재) | 3.75% | PASS | 14 | 936 | 2 | 981 | 8 |
| **보호 OFF (회귀 재현)** | **0.00%** | **PASS** | **0** | **0** | 938 | **0** | 989 |

원인은 탐지식 `w[-1] in JOSA_SINGLE and w[:-1] in vocab`이다. 이 식은 **원형과 절단형이 둘 다 어휘에 있을 때만** 후보로 삼는다. 그런데 새 `_strip_josa`는 문맥 독립적으로 **일관되게** 자르므로, 보호가 없으면 원형이 어휘에서 **통째로 사라져** 후보 집합에서 탈락한다.

**M1은 "분열"을 재는데, 새 구현의 실패 모드는 "분열"이 아니라 "전면 절단"이다.** 구 구현에서는 절단이 문맥 의존적(`(?=\s|$)`)이라 분열이 지문으로 남았지만, 그 지문을 없앤 것이 바로 이번 변경이다.

- 이 회귀를 실제로 잡는 지표는 **M2 하나뿐**이고, M2는 평가셋에 문자열이 있는 **4종**만 본다.
- 임계 7%의 안전 마진 근거(*"보호 실패 시 43%·68%보다 한참 아래"*)도 **구 구현의 수치**다. 새 구현에서 같은 실패는 43%가 아니라 0%다.
- `eval_tokenizer.py` 안에서 두 주석이 서로 모순된다 — `:162-164`는 *"보호어에 없는 새 분열도 드러낸다"*, `:46-49`는 *"보호어는 절단되지 않으므로…"*. 후자가 맞다.

**조치**: M1을 비율이 아니라 **존재 단언**으로 교체 — 코퍼스 원문에 N회 있는 보호어가 어휘에 0회면 전면 절단이다. 현재 비율 지표는 보조로만.

### 🔴 H-2 — 평가 자산 전부가 보호어 27종에서 파생돼, 미보호 도메인어는 어디서도 측정되지 않는다

`TOPIC_TERMS`(M2) 10종·`M4_QUERIES` 키 10종·T-h 과교정 12종이 **전부 `PROTECTED_TERMS`의 부분집합이거나 2음절**이다. 그 사각에서 실제로 절단되는 것들(원형 어휘 카운트 전부 0):

| 원형 | 절단형(빈도) | 문제 |
|------|---|---|
| 근로시간제도 | `근로시간제` 569 | **실재하는 다른 용어와 병합** |
| 전문가 | `전문` 398 | 판례 `전문(全文)`과 **병합** |
| 생리휴가(근기법 §73) | `생리휴` 65 | |
| 배우자출산휴가 / 가족돌봄휴가 | `배우자출산휴` / `가족돌봄휴` | 남녀고평법 §18-2·§22-2 |
| 파견근로 / 단시간근로 / 기간제근로 | `파견근` 67 / `단시간근` 18 / `기간제근` 11 | `연장근로`는 보호됨 |
| 서면동의 | `서면동` | `서면합의`는 보호됨 |

질의·코퍼스가 같은 함수를 쓰므로 **대부분은 대칭이라 검색이 깨지지 않는다.** 실질 피해는 (a) 위 2건의 의미 병합, (b) 보호/미보호 경계가 자의적, (c) **아무 지표도 이 집합을 보지 않아** 코퍼스가 커져도 드러나지 않는다는 것.

### 🟡 M-1 — `MIN_STEM`이 `근로`와 `있는`을 똑같이 살린다 (직접 재현)

```
"받을 수 있는 권리가 있는 경우"
  구: ['권리', '경우']
  신: ['받을', '있는', '권리', '있는', '경우']
```

`있는`이 전 코퍼스 **53,000회로 3번째 최빈 토큰**(`경우` 74k, `근로자` 59k 다음)이고 `많은` 16k가 뒤따른다. STOPWORDS 도입 명분이 *"상용구가 doc_len을 부풀려 BM25 길이 정규화를 왜곡한다"*였는데 이 부작용은 **정확히 같은 해를 반대 방향으로** 만든다 — 그것도 조문체 문장에 편중돼서. 어느 지표도 보지 않는다.

### 🟡 M-2 — M3(불용어 잔존율)는 항등적으로 0이고, 진짜 상용구는 남아 있다

`_reduce_eojeol`이 STOPWORDS를 정확히 제거하므로 어휘에 들어갈 수 없다. M3은 "어휘가 깨끗한가"가 아니라 **"필터가 실행됐는가"**만 잰다. 그 사이:

| 문자열 | 포함 문서 | STOPWORDS? |
|---|---:|---|
| `관심` | 16,069 (20.9%) | ✗ |
| `노동환경개선` | 16,018 (20.8%) | ✗ |
| `권익향상` | 16,020 | ✓ |

`관심`·`노동환경개선`은 `권익향상`·`성원`이 들어간 **바로 그 서명 블록의 나머지 절반**인데 누락됐다(실제로 최빈 토큰 20위 안에 둘 다 있다). 덧붙여 STOPWORDS의 `성원` 근거로 적은 `"성원과 관심"`은 코퍼스에 **0건 일치**한다 — 실제 표기가 다르다.

### 🟡 M-3 — CI가 이 변경의 검색 품질을 전혀 보지 않는다

`--check`는 M4(유일한 검색 품질 지표)를 제외한다. 남는 M1(H-1로 무력)·M2(4종)·M3(항등 0)·M7(순서 전용)·M5(성능)는 전부 구조/성능 검사다. `test_bm25_memory.py`의 "8/8 동일"은 **같은 토크나이저로 신·구 코퍼스 포맷**을 비교하므로 토크나이저의 랭킹 영향을 원리적으로 못 잡는다.

### 🟡 M-4 — 메모리·시간 실측이 드리프트했는데 문서가 그대로

| | 문서 기재 | 실측(변경 후) |
|---|---|---|
| 피크 RSS (macOS) | 410MB — `bm25_search.py:80`, `CLAUDE.md:295` | **453MB** |
| 로드 시간 (macOS) | 2.6초 | **3.4~4.2초** |
| 550MB 대비 여유 | 140MB | **97MB** |
| CI(Linux) 값 | 370MB / 7.0초 | **미측정** |

`CLAUDE.md:295`가 *"판단은 Linux 값으로"*라고 지시하는데 그 Linux 값이 변경 전 것이다. "1만 건당 +90MB" 기준으로 남은 여유는 약 1만 건.

### 🟡 M-5 — 성능 수치가 같은 PR 안에서 세 가지로 갈렸다

design R-1 *"캐시로 1.20x"* / `bm25_search.py:369` docstring *"1.20x"* / `eval_tokenizer.py:63` *"3.11 → 1.91x"* / 실측 1.87~1.94x. 1.20x는 **`Counter.update()`를 양쪽에 포함해 잰 값**이라 토크나이저 순수 배수가 아니다. 임계를 2.00x로 올린 것이 *"통과시키려고 올린 것"*으로 읽힐 수 있어 근거를 명확히 해야 한다(실제 근거는 콜드 스타트 1.28x).

### 🟡 M-6 — 부서명 보호의 근거로 적은 설명이 **사실이 아니다** (직접 재현)

`bm25_search.py:162-163` 주석: *"행정 부서명 6종은 citation_validator.py가 `[부서명]과-NNNN`으로 검증하는 문자열과 같다"*.

확인 결과 `citation_validator.py`에는 `_tokenize_ko`·`bm25` 참조가 **전혀 없고**, `_ADMIN_PATTERN`은 `hit["title"]`·`chunk_text`(원문 그대로)에 대해 돈다. **토크나이저 토큰을 보는 경로가 없다.** 보호의 실제 효용은 BM25 recall이지 인용 검증이 아니다.

부서명은 코퍼스에 **50종 6,266회**이고 보호 6종이 90.5%를 덮는다. 나머지 44종은 이중 절단된다 — `근로조건지도과`(147회) → `근로조건지`.

### 🟢 Low (11건, 요약)

L-3 `_ENDING_RE`의 "긴 것 먼저"는 `$` 앵커 때문에 **무의미**(직접 확인) · L-4 `ENDINGS` `re.escape` 부재(현재 안전) · L-10 `_reduce_eojeol` docstring 수치(101,223/33,237)가 실측(72,048/4,045)과 불일치(직접 확인) · L-2 토크나이저 자체에 NFC 정규화 부재(웹 경로는 `abuse_guard`가 방어, CLI·eval 경로는 무방비) · L-8 `m2_topic_preserved`가 평가셋 파일 없으면 **조용히 통과** · L-9 M4 키 `근로`·`합의`는 사실상 전 문서 포함이라 20/20 무상 · L-11 `eval_tokenizer.py` untracked인데 CI가 이미 참조 · 그 외 L-1/L-5/L-6/L-7.

### 문제 없음으로 확인된 것

정규식 문자 클래스 손실(한자 0.030%·원문자는 1글자라 구 구현도 폐기, **`ㆍ` 분리는 오히려 개선**) · `_strip_josa` 무한 루프 없음·경계 조건 정확 · `_CACHE_MISS` 센티널 정확(300문장 캐시/무캐시 불일치 0) · `del tok_cache` 실효(토큰화 피크 283.8MB < 전체 피크 456.5MB) · 엣지 입력 · 하위 호환(`content`·`CORPUS_FIELDS` 불변).

## 5. 이 사이클의 메타 교훈

**"측정 수단 부재가 결함을 살렸다"는 진단으로 시작해, 측정 수단을 만들었는데, 그 측정 수단이 같은 종류의 사각을 가졌다.**

원인은 구체적이다 — 지표 M1을 **구 구현의 실패 지문**(문맥 의존 절단이 남기는 분열)으로 설계했는데, 이번 변경이 그 지문 자체를 없앴다. 새 구현의 실패는 다른 모양(전면 절단)이라 같은 자로 잴 수 없다.

> **일반화**: 회귀 지표를 "고치기 전 상태의 증상"으로 정의하면, 고친 뒤의 실패 모드를 못 잡는다. 지표는 **증상**이 아니라 **불변식**(보호어는 어휘에 존재한다)으로 세워야 한다.
