## 2. Gap 목록

### G-1 (Low) — 설계 문구가 구현과 어긋남. **설계가 틀렸다**

설계 §4.5는 *"판정은 `build_chunks()` 단계 — `chunk_section()`에 두면 섹션별로 흩어져 집계·출력이 불가능하다"* 라고 썼으나, 구현은 판정을 `chunk_section`에, 집계·게이트를 `build_chunks`에 둔다.

**구현이 옳다.** 설계 §4.5의 다른 요구(`chunk_index` 재부여)는 인덱스를 부여하는 `chunk_section` 안에서만 만족될 수 있어 두 문장이 서로 충돌했다. 구현은 `chunk_section`이 `(chunks, dropped)`를 반환해 설계가 밝힌 *목적*(집계·출력 가능)을 그대로 달성한다.

→ **조치**: 설계 §4.5 문구를 "판정은 `chunk_section`, 집계·게이트는 `build_chunks`"로 수정. 완료.

## 3. Match Rate 밖 검토 (설계 공백)

### 3.1 [수정 완료] 한글 없는 정상 청크가 무조건 제외됐다

**발견**: 의미비율의 분자 `_MEANING_RE`는 한글·한자·로마숫자만 센다(헤딩용으로 만들어진 상수). 분모는 숫자·영문을 포함한다. 따라서 한글이 없는 청크는 의미비 0.000으로 **예외 없이 제외**된다.

실측:

| 입력 | 의미비 | 수정 전 | 수정 후 |
|------|:---:|:---:|:---:|
| `\| 2024 \| 9,860 \| 2,060,740 \|` | 0/31 = 0.000 | **제외** | 유지 |
| `\| 2020 \| 8,590 \|…` | 0/38 = 0.000 | **제외** | 유지 |

최저임금·통상임금 수치표는 `근로기준법 주해 Ⅲ — 임금`의 핵심 자료형이다. 현재 3권에서 오탐이 0이었던 것은 700자 청크에 보통 한글 표제가 섞이기 때문이며, `split_by_size`가 표 중간을 자르면 바로 재현된다. **다음 서적 추가 시 조용히 데이터가 사라질 경로였다.**

**수정**: 표(`_looks_like_table`)에 한해 숫자를 의미문자로 인정(`_MEANING_IN_TABLE_RE`). 숫자를 *항상* 인정하면 숫자 OCR 잔해가 살아나므로 표에서만 인정한다. 표 형태의 OCR 잡음(`| The state of the state…`)은 숫자가 없어 여전히 걸린다.

**부수 발견**: 이 수정 직후 검증에서 `1-1-1-0 0 Ex -- … | 5 -- 1-1-1-0 | 5`(산문형 숫자 잔해)가 표로 오판돼 살아났다. 기존 `_looks_like_table`이 "`|`를 포함한 줄이 과반"이었기 때문이다. 판정을 **"줄 첫 글자가 `|`인 줄이 하나라도 있으면 표"** 로 좁혀 해소했다.

**산출물 영향 없음** — 수정 후 3권 합계가 3,565로 재업로드 결과와 동일해 재업로드가 불필요했다.

### 3.2 [수정 완료] `chunk_section` 반환 타입 주석 오류

`-> list[dict]`로 선언돼 있으나 `(chunks, dropped)` 튜플을 반환. 동작에는 영향 없으나 타입체커·독자를 오도한다. → `-> tuple[list[dict], int]`로 수정.

### 3.3 [수정 완료] 제외율 상한이 헤딩 폐기율 상한을 참조하지 않았다

설계 §4.5는 *"헤딩 게이트와 같은 값이라 규약이 하나로 유지된다"* 를 근거로 삼았으나, 구현은 `MAX_CHUNK_DROP_RATE = 0.10`으로 값만 복사해 상수가 둘이었다. 한쪽만 조정하면 규약이 조용히 갈라진다. → `MAX_CHUNK_DROP_RATE = MAX_HEADING_DROP_RATE` 참조로 수정. 회귀 T22-h2가 동일성(`is`)으로 고정한다.

### 3.4 [수정 완료] 설계 문서 내부 수치 불일치

§4.5의 "gaebyeol 3.0%(53/1,747)"는 규칙 수정 전 값(확정치는 49, 2.8%), §5의 "win(1,404)"는 초안값(확정 1,407), §9의 "57건 전량 육안 확인"은 최종 50건과 어긋남. 전부 정정.

### 3.5 [미조치·기록] 설계에 없는 튜닝 상수

`_looks_like_table`의 판정식과 `_TOKEN_RE`의 토큰화 방식이 설계 문서에 정의돼 있지 않았다. §4.2에 판정식을 명시해 해소했다. `_TOKEN_RE`(`[0-9A-Za-z가-힣]+`)는 코드 주석으로만 남긴다 — 고유토큰비의 보조 정의이고 회귀가 동작을 고정한다.

gap-detector 이후 별도 코드리뷰에서 15건이 나왔고 전부 실측 검증했다. **Match Rate 97.8%가 잡지 못한 결함이 다수였다** — 설계 대조는 "설계대로 만들었는가"만 보기 때문이다.

### 6.1 명백한 결함 (6건, 수정 완료)

| # | 내용 |
|---|------|
| 1 | **`--book X --all --allow-large-prune`이 가드를 우회했다.** 조건이 `not args.book`인데 `targets`를 정하는 것은 `--all`이다 → `args.all` 기준으로 수정 |
| 2 | **T22-j가 아무것도 검증하지 않았다.** `"--book" in r.stderr`가 argparse **usage 배너**에 걸려, 플래그 오타 같은 무관한 거부에도 통과 → 가드 자체 문구로 어서션 + `--book X --all` 조합 추가 |
| 3 | **`CLAUDE.md`의 실측 근거가 거짓이었다.** "`90누9421`은 인접 청크에 없다"고 적었으나 `textbook_win_0612_0`의 뒷부분에 실재한다(앞 230자만 보고 판단한 오독). 축약 선행의 정당성은 유지되나 이유가 다르다 — 반복을 걷어내면 유효 본문이 남기 때문 |

### 6.3 기록만 (사용자 판단으로 이번 범위 밖)

- **G4-T가 외부 전송을 막지 못한다** — `format_pinecone_hits`가 Cohere rerank·Self-RAG 판정 **뒤**에 있어, Cohere는 최대 20~80건, Self-RAG의 Haiku는 rerank 후 전량을 개별로 받는다. 상한 6은 *답변 컨텍스트*의 천장이지 *제3자 전송*의 천장이 아니다. `CLAUDE.md`에 명시함.
- `uses_textbook`(source_type만) vs `_book_id_of`(3단계 폴백) 술어 분기 — 한쪽만 참이면 G1~G3·G6이 샌다. 현재 잠재적.
- `_book_id_of`가 `book_id`를 `source_type`보다 먼저 봄 — 비해설서가 그 키를 가지면 총량 예산을 소비. 현재 잠재적.
- 빈 `content` hit이 상한 슬롯을 소비 — 해설서는 잠재적, 타 소스는 실재.

## 7. 결론

Match Rate 97.8%, 유일한 Gap은 설계 문구 오류(구현이 옳음). 설계 이탈은 없다.

**그러나 Match Rate는 이 사이클의 실제 결함을 거의 잡지 못했다.** 설계 대조 이후 두 차례의 독립 검토에서 나온 것들:

| 출처 | 발견 | 성격 |
|------|------|------|
| gap-detector 부수 관찰 | 한글 없는 정상 청크(수치표) 무조건 제외 | 설계 공백 |
| `/code-review` | 가드 우회, 회귀 무효, 거짓 근거, 산술 오류, 순서 주석 오류 | 설계 대조로는 원리적으로 불가 |
| 〃 | 섹션 소실, 판정↔저장 불일치, 제외율 희석 | 코퍼스 실측 필요 |

세 부류 모두 "설계대로 만들었는가"라는 질문의 사각이다. `CLAUDE.md` 첫 항목이 *"Match Rate가 90%를 넘어도 그대로 배포하지 말 것"* 이라 적은 이유가 그대로 재현됐다 — **이번에는 Match Rate 97.8% 뒤에 9건의 실제 결함이 있었다.**

특히 세 가지는 자기점검의 한계를 보여준다: ① 가드를 지워도 CI가 녹색이었고(회귀가 초크포인트를 안 봄), ② 테스트 어서션이 argparse 배너에 걸려 아무것도 검증하지 않았으며, ③ 문서에 적은 실측 근거가 **원문을 잘못 읽은 것**이었다. 셋 다 "통과했다"는 신호를 내면서 실제로는 비어 있었다.

최종 산출물은 3,568청크, 회귀는 T22 33개로 늘었다.
