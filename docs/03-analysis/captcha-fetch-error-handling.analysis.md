## 4. 정밀 검증

### 4.1 `finally`의 `!captchaToken`이 정상 토큰을 잠그는가 — **기각**

`captchaToken`이 비워지는 지점은 `board.html:922`(`loadCaptcha` 진입) 하나뿐이다.

| 종료 경로 | `finally` 시점 토큰 | 버튼 | 판정 |
|-----------|---------------------|:----:|:----:|
| 400 (입력 검증) | 유효(loadCaptcha 미호출) | 활성 | 정상 — 입력 고쳐 재제출 |
| 429 | 유효 | 활성 | §4.2 |
| 네트워크 예외 | 유효 | 활성 | 정상 |
| 403 + 재로딩 성공 | 신규 | 활성 | 정상 |
| 403 + 재로딩 실패 | `''` | **잠금** | 의도대로 |

400 후 재제출 가능성은 **서버 계약으로 확인**했다. `_verify_captcha`(`api/index.py:748-763`)는 상태 없는 HMAC + 만료 검증이며 nonce 소비가 없다 → 만료 전 재사용 가능. 또 400은 CAPTCHA 검증(`:808`) **이후**에 나오므로 토큰이 반드시 유효하다.

### 4.2 429 분기와 `finally`의 충돌 — **양방향 확인**

서버는 CAPTCHA 검증(`:808`) **다음에** rate limit(`:817`)을 본다. 따라서 429 시점의 토큰은 항상 유효하다.

**(A) `finally`가 429 잠금을 즉시 무효화 (선행 결함)**

`return`이 `finally`를 트리거하므로 `:975`의 잠금이 같은 틱에 덮인다. **30초 잠금은 죽은 코드다.** 다만 변경 전 `finally`도 무조건 `false`였으므로 **본 변경이 만든 회귀가 아니다.** 서버가 3건/60초를 강제하므로 보안 영향 없음.

**(B) 잔여 타이머가 게이팅을 덮음 — FR-3 위반 (시뮬레이션 재현)**

```text
t=0   429 수신 → 타이머 예약 → finally가 버튼 재활성 (열림)
t=1s  모달 재오픈 → loadCaptcha 실패 → 토큰='' , 버튼 잠김 ✅
t=30s 잔여 타이머 발화 → disabled = false      ← 토큰 없이 열림 ❌
```

이 상태에서 제출하면 `captcha_token: ''` → 403 → `await loadCaptcha()` 재실패 → **설계 §1.2가 막으려던 바로 그 403 루프**로 복귀한다.

### 4.3 `await loadCaptcha()` + `finally` 최종 상태 — **의도대로**

| 재로딩 | `loadCaptcha` 종료 시 | `finally` 결과 | 일치 |
|--------|----------------------|----------------|:----:|
| 성공 | 신규 토큰, `disabled=false` | `false`(활성) | ✅ |
| 실패 | `''`, `disabled=true` | `true`(잠금) | ✅ |

변경 전에는 `await`가 없어 미해결 Promise가 `finally` **이후**에 resolve됐고 무조건 `false`가 경합에서 이겼다(git 원본 확인). 설계가 지목한 경합은 실재했고 정확히 닫혔다.

### 4.4 `index.html` 모달 재오픈 시 상태 잔존 — **없음**

`openEmailModal`이 fetch **이전에** 전 상태를 초기화한다: `:1535` 토큰, `:1543-1544` 입력, `:1545` 오류 문구, `:1546` 문제 표시, `:1547` 버튼 잠금. 버튼을 여는 지점은 성공 경로뿐이므로 재오픈 시 `:1547`이 무조건 다시 잠근다.

**D2("추가 처리 없음")는 회피가 아니라 구조적으로 옳은 판단이었다.** `board.html`이 별도 처리를 필요로 한 이유(`captchaToken`이 모듈 전역, `openWriteModal`에 토큰 초기화 없음)와 정확히 대비된다.

### 4.5 전수 검사가 실제로 위반을 잡는가 — **미탐 경로 있음**

조건: `/\.ok\b/.test(window) || /catch\s*[({]/.test(window)` (초안 600자 → Act-1에서 800자)

**미탐 1 — `catch(` 허용이 원 결함을 통과시킨다.** 변경 전 `loadCaptcha`는 `try { fetch → resp.json() } catch(e) {}` 형태였다. `catch (e)`가 윈도우 안에 있으므로 **이 코드는 전수 검사를 통과한다.** 즉 2026-08-07 실장애를 일으킨 코드 형태가 검사망을 빠져나간다.

CAPTCHA 2곳은 테스트 1(`/\.ok\b/` 명시 요구)이 별도로 막으므로 현시점 실害는 없다. 그러나 **"같은 실수의 재발 방지"는 실질적으로 CAPTCHA 2곳에만 걸려 있다.** 설계 D9/§4.2가 명시 결정한 트레이드오프라 설계 위반은 아니지만, 이 한계가 어느 문서에도 기록돼 있지 않다.

**미탐 2 — 윈도우 침범.** `index.html:1688`과 `:1701`은 `:1703`의 `if (!resp.ok)` 하나를 공유한다(정상 설계). 여기 근처에 가드 없는 fetch를 추가하면 통과한다.

**오탐 여유 얇음**: 최장 거리 `:1688 → :1703`이 약 520자로 한도 600의 87%였다 → Act-1에서 800자로 완화(여유 65%).

**변이 정적 검증** (설계 §4.3의 3종 + 2종)

| 변이 | 잡히는가 | 비고 |
|------|:--------:|------|
| `index:1557` `if (!r.ok) throw` 제거 | 잡힘 | 다음 `.ok`가 700자 밖 |
| `board:925` `disabled = true` 제거 | 잡힘 | 단 `:939`에도 같은 문자열이 있어 **둘 다 지워야** 실패 — 민감도가 설계 의도보다 낮음 |
| `board:922` `captchaToken = ''` 제거 | 잡힘 | 유일 출현 |
| `board:991` `!captchaToken` → `false` | 잡힘 | 테스트 3 |
| `board:973` `await` 제거 | 잡힘 | 테스트 3 |

### 4.6 `slice()` 중복 — **2곳(설계 결정 유효), 단 개념은 3곳**

| 파일 | 헬퍼 | 성격 |
|------|------|------|
| `test_answer_glance.js:27-39` | `slice` | 들여쓰기 앵커링 |
| `test_public_fetch.js:27-38` | `slice` | **동일 복제** |
| `test_answer_renderer.js:17-29` | `extractDeclaration` | 이름·시그니처 다름, **앵커링 없음**(더 약함) |

### 🟡 GAP-2 — 429 잔여 타이머가 게이팅을 덮는다 (**P2**, FR-3 위반)

`board.html:976`의 콜백이 무조건적이라 예약 후 30초 내 CAPTCHA 실패 시 토큰 없이 버튼이 열린다(§4.2-B, 시뮬레이션 재현). 설계가 `finally` 경합은 다뤘으나 같은 함수의 두 번째 비동기 상태 변경원은 다루지 않았다.

```js

setTimeout(function() { submitBtn.disabled = !captchaToken; }, 30000);
```

회귀 고정: 테스트 3에 `disabled = false` 타이머 부재 단언 추가

### 🔵 GAP-3 — 429 잠금 30초가 `finally`에 즉시 무효화 (**P3, 선행 결함**)

`return`이 `finally`를 트리거해 잠금이 같은 틱에 덮인다(§4.2-A). **본 변경이 만든 회귀가 아니다** — 변경 전에도 동일하게 무효였다. 서버가 3건/60초를 강제하므로 보안 영향 없음, UI 약속만 거짓. GAP-2 수정으로는 해소되지 않는다. **본 사이클 범위 밖 — 후속 이슈 권고.**

### 🔵 GAP-4 — 전수 검사가 원 결함 형태를 통과시킨다 (**P3, 설계 결정 내**)

`catch(` 허용 때문에 "try/catch는 있으나 `resp.ok` 검사 없는 fetch"가 통과한다. 변경 전 `loadCaptcha`가 정확히 그 형태였으므로 **전수 검사망은 실장애 코드를 잡지 못했을 것이다**(§4.5).

**수정** — 코드보다 **문서화**가 적절:
> "이 전수 검사는 '오류 처리 의도'만 확인한다. try/catch만 있고 상태 검사가 없는 fetch는 통과하므로, 중요한 엔드포인트는 개별 테스트로 별도 고정할 것."

### 🔵 GAP-5 — 전수 검사 600자 여유가 얇다 (**P3**)

최장 `:1688 → :1703`이 약 520자(한도의 87%). 윈도우 800자 완화 또는 실패 메시지에 안내 추가 권고.

### 결론

**Match Rate 95% — 설계와 구현이 잘 일치한다.** D1~D9 전부, NFR 4개 전부 준수했고 설계에 있으나 미구현된 항목은 0건이다. 특히 설계 §1.2의 핵심 발견("두 페이지의 버튼 게이팅 구조가 다르다")이 구현에 정확히 반영됐다 — `index.html`은 D2대로 손대지 않았고(§4.4에서 안전성 확인), `board.html`은 D3/D4대로 게이팅·초기화를 추가했다. 설계 §3.2가 예측한 `finally` 경합은 실재했으며(git 원본 확인) `await` + 조건부 해제로 정확히 닫혔다.

**Plan §5의 최대 리스크는 전 계층에서 방어되고 있다.** `api/index.py`는 한 줄도 바뀌지 않았고 503은 여전히 503이다.

그리고 **PR 전 반드시 처리해야 할 것은 GAP-1이다** — CI에 등록된 테스트 파일이 커밋되지 않아 현 상태로 push하면 잡이 실패한다.
