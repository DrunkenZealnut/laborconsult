> Design: `docs/02-design/features/bm25-memory-scaling.design.md`

## 1. 결론

**Match Rate 88%**(gap-detector, 51항목). 목표 지표는 전부 달성했으나, **이 사이클의 핵심 산출물인 메모리 회귀 테스트가 CI에서 구조적으로 통과만 하는 상태**였다.

두 리뷰가 **독립적으로 같은 High 결함**을 찾았다 — `ru_maxrss`의 플랫폼별 단위 차이. 그만큼 명백했고, 그만큼 혼자서는 놓쳤다.

| 지표 | 전 | 목표 | 실측(리뷰 재측정 포함) |
|---|---:|---:|---:|
| 로드 피크 RSS | 692MB | ≤450MB | **408~417MB** ✅ |
| Vercel 한도 대비 | 68% | ≤45% | **40%** ✅ |
| 여유 문서 수 | 3.7만 | ≥6만 | **≈6.8만** ✅ |
| 검색 결과 | — | 불변 | **신·구 경로 8/8 완전 일치** ✅ |
| 로드 시간 | 2.7초 | ≤4초 | 2.6초 ✅ |

두 리뷰가 각각 별도 프로세스로 재측정해 같은 결론에 도달했다(408.1 / 413.6 / 415.7MB). 구 배열 경로는 698~712MB로 일관되게 약 300MB 높다.

## 2. 핵심 결함 — 회귀 테스트가 CI에서 무력했다

### H1. `ru_maxrss` 단위가 플랫폼마다 다른데 고정 나눗셈을 썼다

`ru_maxrss`는 **macOS/BSD는 바이트, Linux는 킬로바이트**다. `test_bm25_memory.py`가 무조건 `/(1024**2)`로 나눠, CI(`ubuntu-latest`)에서:

| 실제 | CI 보고값 | 상한 550MB 검사 |
|---:|---:|---|
| 415MB (정상) | 0.40MB | 통과 |
| 703MB (구 경로) | 0.69MB | 통과 |
| **1,218MB (인터닝 소실, 한도의 119%)** | **1.2MB** | **통과** |

즉 이 테스트가 막겠다고 선언한 상황 — *"RSS가 한도의 119%가 될 때까지 아무도 몰랐다"* — 이 **그대로 재현되는** 상태였다. 로컬(macOS)에서만 유효했고, CI에서 실제로 검증되던 것은 `ok=True`·`docs>0`·`elapsed≤8` 세 가지뿐이었다.

**수정**: `sys.platform` 분기 + **단위 위생 검사**(`50MB < rss < 3000MB`). 위생 검사가 핵심이다 — 분기를 또 잘못 써도 값이 말이 안 되면 잡힌다. 두 플랫폼 경로가 각각 400MB로 환산됨을 강제 검증했다.

### 왜 Do 단계에서 못 잡았나

Design §3이 *"Do 단계에서 CI 실측 후 상한을 확정한다"* 고 적어두었는데 **이행하지 않았다**. CI를 한 번만 돌렸으면 `로드 피크 RSS 0MB (한도의 0%)` 출력으로 즉시 드러났다. 설계가 요구한 검증 단계를 건너뛴 것이 유일한 원인이다.

## 3. 경로 리뷰가 추가로 찾은 것

gap-detector가 원리적으로 못 잡는 영역이다.

| # | 결함 | 실패 시나리오 |
|---|---|---|
| **H2** | **어느 파일을 읽었는지 로그에 없다** | 신·구 로그가 `"BM25 loaded: 76983 docs, 2600ms"`로 **완전히 동일**. `jsonl.gz` 커밋을 빠뜨리면 프로덕션이 703MB 경로로 돌아가는데 **아무 신호가 없다** — "고쳤다고 믿는데 프로덕션은 그대로"가 성립 |
| **H4** | **구 `json.gz`가 영구히 갱신되지 않는 폴백이 된다** | 빌더는 이제 `jsonl.gz`만 쓴다. 어떤 이유로든 신 파일이 배포본에 없으면 로더가 **몇 달 전 코퍼스**로 검색을 계속하고, 신규 적재분이 BM25에서 안 잡히는데 Dense가 받쳐줘 "그럴듯한" 결과가 나온다. `law-version-drift`(MST 고정으로 낡은 조문 반환)와 **같은 실패 클래스**. 더 나쁜 것은 구 파일 존재가 "코퍼스 없음" 경고마저 가린다는 점 |
| **H3** | baseline이 미커밋 + **로드 실패해도 기준값을 쓴다** | `ok=False, docs=0`인 상태에서 `{q: []}` 8개를 파일로 굳힌다. `.venv` 밖에서 실행하면(docstring이 그렇게 안내했다) 빈 기준값이 생성되고, 커밋되면 이후 모든 실행이 영문 모를 실패가 된다 |
| **M1** | **baseline이 코퍼스 순서에 결합** | `search_bm25`는 안정 정렬이라 **동점의 순서가 코퍼스 인덱스에 의존**하고, 코퍼스 순서는 Pinecone 페이지네이션 때문에 재빌드마다 달라진다. 한 쿼리 top-50에서 정확한 동점 3건이 관측됐다. 즉 **내용이 같아도 재빌드만으로 깨지고**, 실무 대응이 "기준값 삭제"가 되어 가드가 소멸한다 |
| **M2** | `BM25_MAX_DOCS` 도달이 무로그 + 절단이 편향 | 코퍼스는 NS 순차 수집이라 뒷부분이 qa다. 상한에 걸리면 무작위가 아니라 **최대 코퍼스인 Q&A의 꼬리가 통째로** 잘리고, Dense가 받쳐줘 "특정 주제만 BM25 미도달"로만 나타난다 |
| **M4** | `_KEEP_FIELDS`와 빌더 필드가 이중 선언 | `_slim()`은 모르는 키를 **말없이 버린다**. 빌더가 필드를 추가하고 로더를 잊으면 Dense 히트에는 있고 BM25 히트에만 빈 값 |
| **M5** | 손상 줄의 진단 정보 부족 | 정책(전량 중단)은 **옳다** — 줄 skip은 "부분 데이터가 정상으로 보이는" 실패를 만든다. 다만 몇 번째 줄에서 깨졌는지 알 수 없었다 |
| **M7** | 인덱스 구축 실패 시 코퍼스 400MB 영구 점유 | `_bm25_corpus`가 인덱스 구축 **전**에 채워지므로, `BM25Okapi`가 MemoryError로 죽으면 쓸모없는 코퍼스가 프로세스 수명 내내 남는다 — 메모리가 모자라 실패한 상황에서 메모리를 붙든다 |
| **L4** | 포맷 감지가 공백/BOM에서 오판 | `read(1).lstrip()`이 빈 문자열이 되면 JSONL로 오판하고, 한 줄짜리 배열을 1건으로 세어 **급감 가드를 조용히 무효화**한다(0.8×1보다 작은 값은 없다) |
| **L8** | 프로덕션 관측 수단 없음 | `/api/health`가 `{"status":"ok"}`뿐이라 BM25가 살아 있는지, 어느 파일을 읽었는지 외부에서 확인할 방법이 없었다 |

### 4.1 M1 재설계가 가장 큰 개선이다

초안의 프로즌 기준값은 두 가지가 어긋났다: ① 전환 **후** 스냅샷이라 값 보존을 자체로 증명하지 못하고, ② 코퍼스 재빌드마다 깨진다. 지금은 **같은 실행에서 두 포맷 경로를 서로 대조**한다:

```
✅ 신·구 포맷 검색 결과 동일 8/8 쿼리
✅ 스트리밍이 배열보다 메모리 절감 (409MB < 704MB)
```

코퍼스를 갱신해도 깨지지 않고, "이번 변경이 값을 보존한다"는 **직접 증거**가 된다. 구 포맷이 삭제되면 이 대조는 자동으로 생략된다(전환 완료 상태).

## 7. 이 사이클의 교훈

**"검증 장치를 만들었다"와 "검증이 동작한다"는 다르다.** 이 사이클은 메모리 회귀 테스트를 가장 오래 남을 산출물이라고 선언했는데, 그 테스트가 CI에서 어떤 값이 와도 통과하는 상태였다. Design이 요구한 "CI 1회 실측"을 건너뛴 것이 원인이고, 그 한 번이면 즉시 드러났다.

그래서 이번에 넣은 것이 **단위 위생 검사**다 — 상한 검사와 별개로 "값이 말이 되는 범위인가"를 본다. 임계값 검사만 두면 단위 오류·측정 실패가 항상 통과로 흡수되지만, 위생 검사는 그것을 잡는다. 같은 이유로 로드 실패 시 이후 검증을 중단하도록 했다(0건을 "동일"로 통과시키지 않는다).

**두 리뷰가 독립적으로 같은 결함을 찾은 것**도 기록해 둔다. gap-detector는 설계 대조 중에, 경로 리뷰는 테스트 신뢰성 점검 중에 각각 H1에 도달했다. 한 축만 돌렸다면 놓쳤을 확률이 절반이었다.
