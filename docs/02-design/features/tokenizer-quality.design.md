## 2. Plan 이후 추가 발견

### 2.1 D1-b — 2음절 핵심어가 색인에서 **소멸**한다 (신규 · Critical)

Plan 작성 시점에는 D1을 "분열"로만 파악했다. 프로토타입 대조 중 `'별도의 합의'` → C0가 `['별도']` 를 반환하는 것을 발견했다. **`합의`가 사라졌다.**

원인: 현행 구현에 **어간 최소 길이 가드가 없다.**

```python
text = re.sub(r"[은는이가을를의로도만와과](?=\s|$)", "", text)   # 합의 → 합
tokens = re.sub(r"[^\w\s]", " ", text).split()
return [t for t in tokens if len(t) >= 2]                        # 합 → 폐기
```

2음절 단어의 끝글자가 조사 후보이면 1음절이 되고, 마지막 줄의 `len >= 2` 필터가 그것을 **통째로 버린다.** 실측 — 16종 중 13종 소멸:

| 소멸 | 생존 |
|------|------|
| 합의 · 근로 · 휴가 · 동의 · 협의 · 이의 · 임의 · 대가 · 차이 · 고의 · 사이 · 별도 · 연도 | 해고 · 임금 · 퇴직 |

`근로`와 `휴가`는 노동법 코퍼스의 가장 기본적인 어휘다. 이들이 **단독으로 등장할 때는 색인에 존재하지 않는다.** (긴 어절에서 절단돼 온 경우 — `근로를`→`근로` — 만 살아남아, 그래서 어휘 목록에는 보이고 아무도 이상을 눈치채지 못했다.)

질의 쪽에서도 동일하게 작동한다:

```
"근로 제공 의무가 없는 날"  →  C0=['제공', '의무']       ← '근로' 증발
                            →  C1=['근로','제공','의무','없는']
```

**처방**: `MIN_STEM = 2` — 절단 결과가 2음절 미만이 되면 절단하지 않는다. 한 줄이지만 이 사이클에서 가장 영향이 큰 변경이다.

### 2.2 Plan §4.2의 처리 순서는 틀렸다 — 어미가 조사보다 **먼저**

Plan은 `④조사 절단 → ⑤어미 정규화` 순서를 제시했다. 프로토타입에서 반증됐다.

`지급하는`을 조사부터 처리하면 `하는`의 `는`이 **조사로 오인**돼 먼저 떨어지고, 남은 `지급하`는 어떤 어미 패턴에도 매치되지 않아 그대로 색인된다:

| 입력 | ④조사→⑤어미 | ⑤어미→④조사 |
|------|---|---|
| `지급하는` | `지급하` ❌ | `지급` ✅ |
| `신청하는` | `신청하` ❌ | `신청` ✅ |
| `해고되는` | `해고되` ❌ | `해고` ✅ |
| `지급해야` | `지급` | `지급` |
| `연차휴가를` | `연차휴가` | `연차휴가` |
| `경우에는` | `경우` | `경우` |

전량 실측 — `…하`/`…되`로 끝나는 잔재 토큰 출현:

| 순서 | 잔재 토큰 | 고유토큰 |
|------|---:|---:|
| ④조사 → ⑤어미 | 101,223 | 272,646 |
| **⑤어미 → ④조사** | **33,237 (−67%)** | **271,752** |

시간은 동일(2.48s vs 2.47s)하다. **순서만 바꾸는 무비용 개선**이다.

> **정의 주의 (Do)** — 위 101,223/33,237은 프로토타입이 `endswith(("하","되","시","드"))`로 센 값이다. 구현과 `eval_tokenizer.py` M7은 `("하","되")` 기준이라 **72,048 / 4,045**가 된다. 정의가 다를 뿐 방향과 배율(−94%)은 같다. 인용할 때 어느 정의인지 밝힐 것.

> 근본 이유: 한국어 어미(`-는`, `-은`, `-을`)와 조사(`는`, `은`, `을`)는 **표기가 겹친다.** 형태소 분석기 없이 구분하려면 더 긴 패턴(어미)을 먼저 소진하는 최장일치 순서에 의존할 수밖에 없다.

## 3. 배제된 설계안 — C2 양형 색인 (실측 기각)

커레이션 사전 없이 D1을 해결하는 방법으로 **원형과 절단형을 둘 다 색인**하는 안을 검토했다. `연차휴가 ` → `[연차휴가, 연차휴]`. 어느 쪽이 옳은지 몰라도 되고 사전 드리프트(Plan R-3)가 원리적으로 사라진다는 장점이 있다.

전량 실측으로 기각했다:

| 지표 | C0 | C2 | 판정 |
|------|---:|---:|:---:|
| 총토큰 | 5,490,490 | 7,395,421 (**+34.7%**) | NFR-2 위험 |
| 고유토큰 | 326,235 | 485,465 (**+48.8%**) | 메모리 |
| 문서당 토큰 | 71.3 | 96.1 | BM25 길이 정규화 왜곡 |
| 분열쌍 | 225 | **1,190** | **악화** |

분열쌍이 5배로 늘어난 것이 결정적이다. `근로자` 와 `근로자가` 를 둘 다 색인하므로, 해결하려던 "한 단어가 두 토큰" 상태를 **모든 명사로 확대**한다. 문서당 토큰 +34.7%는 `test_bm25_memory.py`의 550MB 상한에도 직접 위협이다.

> 기록용 — C2는 "사전이 필요 없다"는 매력 때문에 유력해 보였다. 실측 없이 채택했으면 메모리 회귀와 검색 품질 저하를 동시에 만들었을 것이다.

## 4. 채택 설계 — 처리 순서

### 4.1 7단계

```
① 어절 분할     _SPLIT = re.compile(r"[^0-9A-Za-z가-힣]+")
                 구두점을 조사 절단 '전'에 경계로 소진한다 (D2 해소)
② 캐시 조회     어절 → 토큰(또는 None). 적중 시 ③~⑦ 생략
③ 불용어 1차    원형 기준 (안녕하세요·바랍니다 등)
④ 어미 정규화   명사+하다/되다 활용 어미, 최장일치 (D4)      ← 조사보다 먼저
⑤ 조사 절단     반복 1단위씩, 매 회차 보호어 검사 (D1·D3)
⑥ 불용어 2차    절단 결과 기준 (경우에는 → 경우 → 제외)
⑦ 길이 필터     len >= 2
```

**①이 ⑤보다 먼저**여야 D2가 풀린다. 현행은 구두점 치환이 조사 절단 뒤에 있어 룩어헤드 `(?=\s|$)`가 구두점을 보지 못했다. 분할을 먼저 하면 모든 조사가 어절 끝에 오므로 **룩어헤드 자체가 불필요**해진다.

**③과 ⑥ 둘 다 필요하다.** 불용어에는 원형(`안녕하세요`)과 절단 후 형태(`경우`) 둘 다 있고, 한쪽만 검사하면 나머지가 샌다.

### 4.2 조사 절단은 반복 + **매 회차** 보호어 검사

```python
def _strip_josa(w: str) -> str:
    while len(w) > MIN_STEM and w not in PROTECTED_TERMS:
        for j in JOSA_MULTI:                       # 긴 것 먼저 = 최장일치
            if w.endswith(j) and len(w) - len(j) >= MIN_STEM:
                w = w[:-len(j)]
                break
        else:
            if w[-1] in JOSA_SINGLE and len(w) - 1 >= MIN_STEM:
                w = w[:-1]
                continue
            break
    return w
```

지켜야 할 것 셋 — **전부 프로토타입에서 실제로 깨뜨려 본 것**이다:

1. **반복이어야 한다.** 조사는 중첩된다(`에는`·`으로는`·`에서의`·`만으로`). 현행의 "2글자 1회 + 1글자 1회"로는 `경우에는` → `경우에`에서 멈춘다(실측: `경우에`가 어휘에 16,180회).

2. **보호어 검사가 루프 안에 있어야 한다.** 최적화 시도로 `(?:...|[은는이가...])+$` 단일 탐욕 정규식을 썼더니 `연차휴가를`이 `가를`을 한꺼번에 매치해 **`연차휴`** 가 됐다. 보호어를 원형에서만 검사하면 중간 결과(`연차휴가`)가 보호받지 못한다. 같은 정규식은 `근로를`에서 `로를`을 매치해 어간 가드에 걸려 **아무것도 절단하지 않는** 반대 방향 오류도 냈다.

3. **다글자 조사는 긴 것부터.** `으로써`가 `으로`보다 뒤에 오면 `으로`가 먼저 매치해 `써`가 남는다. `CLAUDE.md`의 사건부호 화이트리스트(`다카`가 `다`보다 앞) 규칙과 같은 실패 클래스다.

### 4.3 MIN_STEM = 2

절단 결과가 2음절 미만이면 절단하지 않는다. §2.1의 소멸 13종이 이 한 줄로 복구된다.

> **`len(t) >= 2` 최종 필터를 지우는 것으로 대체하지 말 것.** 그러면 소멸은 막지만 `합`·`근` 같은 1음절 파편이 색인에 들어가 고유토큰이 폭증한다. 막아야 할 것은 **파편 생성**이지 파편 폐기가 아니다.

### 4.4 어미 정규화 (D4)

대상은 **명사+하다/되다 활용형**으로 한정한다. 이 부류는 어간이 이미 코퍼스에 명사로 존재하므로 절단 결과가 실재하는 단어임이 보장된다 — Plan R-4("오변환이 미변환보다 비싸다")를 만족하는 유일한 안전 구간이다.

```python
ENDINGS = ("하여야한다","하여야하는","하였습니다","되었습니다","하겠습니다","드립니다",
           "하여야","해야하는","했습니다","합니다","습니다","됩니다",
           "하여","해야","한다","된다","하는","되는","했다","됐다",
           "하고","되고","하며","되며","하면","되면","하기","되기")
# 최장일치 + 어간 2음절 이상일 때만
```

과교정 점검 — 아래 12종은 **변형되면 안 된다**(실측 전부 불변):

```
근로시간 퇴직금 연차휴가 최저임금 산업재해 취업규칙
부당해고 노동조합 단체협약 통상임금 평균임금 고용보험
```

수렴 확인: `지급해야`·`지급하여야`·`지급한다`·`지급합니다`·`지급하는` → 전부 **`지급`**.

## 5. 두 사전

### 5.1 `PROTECTED_TERMS` (설계 27종 → **Act 후 40종**)

말끝 조사 절단을 금지할 도메인 실단어. **코퍼스 실측 분열쌍에서 도출**했고 추측으로 채우지 않았다.

| 분류 | 항목 |
|------|------|
| 휴가 (7) | 연차휴가 · 연차유급휴가 · 유급휴가 · 무급휴가 · 출산휴가 · 출산전후휴가 · 보상휴가 |
| 근로 (6) | 연장근로 · 휴일근로 · 소정근로 · 야간근로 · 계속근로 · 초과근로 |
| 제도 (3) | 퇴직연금제도 · 퇴직급여제도 · 퇴직금제도 |
| 기타 (5) | 서면합의 · 노사합의 · 영업양도 · 회계연도 · 회계년도 |
| 행정 부서 (6) | 근로기준정책과 · 퇴직연금복지과 · 근로기준과 · 근로개선정책과 · 임금근로시간과 · 근로복지과 |

> **정정 1 (Do)** — `자유로`를 뺐다(27종). 분열쌍 목록에서 기계적으로 옮겼으나 `자유`+조사 `로`일 개연성이 높다.

> **정정 2 (Act)** — 이 목록은 **커레이션이고 자동 발견되지 않는다.** 27종은 "구 구현이 남긴 분열쌍"에서 뽑았는데 그것은 **편향된 표본**이었다 — 구 구현에서 문맥에 따라 원형이 살아남은 것만 보였기 때문이다. 독립 리뷰가 사각에서 13종을 더 찾아 **40종**이 됐다: 생리휴가 · 배우자출산휴가 · 가족돌봄휴가 · 파견근로 · 단시간근로 · 기간제근로 · 서면동의 · 근로시간제도 · 전문가 · 근로조건지도과 · 임금복지과 · 여성고용정책과 · 고용평등정책과. 이 중 `근로시간제도`→`근로시간제`(569회)와 `전문가`→`전문`(398회, 판례 `전문(全文)`)은 **다른 실단어와 병합** 중이었고 나머지는 원형 카운트가 **0**이었다.

> **정정 3 (Act)** — 위 문단에는 원래 *"행정 부서명은 citation_validator.py가 검증하는 문자열과 동일하다"* 고 적혀 있었으나 **사실이 아니다.** `citation_validator.py`에 `_tokenize_ko`·`bm25` 참조가 없고 `_ADMIN_PATTERN`은 원문 필드(`title`·`chunk_text`)에 대해 돈다 — 토크나이저 토큰을 보는 경로가 없다. 실제 근거는 **BM25 recall**이다(코퍼스 50종 6,266회, 절단 시 `근로조건지도과`→`근로조건지`로 이중 절단).

### 5.2 `STOPWORDS` — 보수적 선택

Plan R-2("불용어 과다 지정으로 실단어 소멸")가 High 리스크이므로 **경계선 어휘를 일부러 뺐다.**

| 채택 | 근거 |
|------|------|
| 크롤러 상용구 8종 (`안녕하세요`·`한국노총`·`부천상담소입니다`·`하루되시기`·`권익향상`·`성원`·`노력하고`·`노동OK`) | 각 16k~32k회, 내용 신호 0 |

|------|------|
| `경우`(74,000) · `해당`(24,000) | 고빈도이나 **법률 문언의 내용어**다. IDF가 이미 이들을 억제하고 있고, 제거의 실익은 `doc_len` 축소뿐인데 오제거의 대가는 회수 불능이다. 실측상 채택/보류 차이는 총토큰 3.1%에 그친다(5,568,264 vs 5,394,634, 고유토큰은 동일 286,8xx) — **비용 대비 위험이 맞지 않는다.** |

> 보류 항목은 `eval_tokenizer.py`가 매 실행 시 출력하는 "최빈 토큰 25"에 계속 노출된다. 향후 근거가 쌓이면 그때 옮긴다.

### 5.3 두 사전을 분리하는 이유 (FR-7)

Plan §1.8이 밝힌 대로, 분열쌍 탐지가 찾아낸 45종은 **정반대의 처방이 필요한 두 부류**다.

| 부류 | 예 | 처방 |
|------|---|------|
| 도메인 실단어 | `연차휴가`(7,942) | **보호** — 끝글자를 지킨다 |
| 연결어 | `하더라도`(508) · `것으로`(321) | **제거** — 통째로 버린다 |

45종을 일괄 "보호"하면 색인에 연결어 노이즈를 주입한다. 하나의 사전으로 합치면 이 구분이 코드에서 사라지고, 다음 사람이 새 항목을 어느 쪽 의미로 넣는지 알 수 없게 된다. **교집합은 공집합이어야 하며 회귀 T-d가 그것을 고정한다.**

## 6. 성능 설계 — 어절 캐시

### 6.1 문제

정확한 구현(§4.2의 반복 루프)은 어절마다 파이썬 레벨 반복이 필요하다. 현행 C0는 텍스트 전체에 정규식 `sub`를 2회 거는 C 레벨 연산이라 훨씬 싸다. 프로토타입 실측 **2.06s → 3.88s (1.88x)** 로 NFR-1(+50%)을 위반했다.

### 6.2 해법 — 어절 단위 메모이제이션

코퍼스 토큰의 **94.1%가 중복**이라는 사실은 이미 이 모듈에 기록돼 있다(인터닝 근거, 549만 → 고유 32.6만). 같은 사실이 어절 수준에서도 성립하므로, `어절 → 토큰|None` dict 하나로 대부분의 호출이 조회 1회가 된다.

| | 시간 | 배수 |
|---|---:|---:|
| C0 현행 | 2.06s | 1.00x |
| 캐시 없음 | 3.88s | 1.88x ❌ |
| **캐시 적용** | **2.47s** | **1.20x** ✅ |

캐시 항목 417,903개.

### 6.3 캐시는 **로드 스코프**다 — 모듈 전역 금지

```python
def _tokenize_ko(text: str, cache: dict | None = None) -> list[str]: ...

# _load_streaming() 내부
_cache: dict[str, str | None] = {}
...
tokenized.append([sys.intern(w) for w in _tokenize_ko(doc.get("text",""), _cache)])
...
del _cache          # BM25Okapi 구축 **전**에 해제
gc.collect()
```

전역 캐시로 두면 **질의마다 항목이 누적**돼 장기 실행 인스턴스에서 무한히 자란다. 질의는 어절 10개 남짓이라 캐시 이득도 없다.

### 6.4 메모리 — 캐시는 피크와 겹치지 않는다 (NFR-2)

BM25 로드의 RSS 피크는 `BM25Okapi(tokenized)` 구축 시점이다(모듈 주석 기록: 스트리밍+인터닝 후 약 410MB). 캐시는 그 **직전**에 해제되므로 피크에 더해지지 않는다.

토큰 총량도 유리한 방향이다 — 5,490,490 → 5,568,230 (+1.4%). 불용어 제거분보다 §2.1 소멸어 복구분이 커서 소폭 늘지만, 고유토큰은 326,235 → 271,752(**−16.7%**)로 줄어 인터닝 이후 실제 문자열 보유량은 감소한다.

> 그럼에도 **`test_bm25_memory.py`(상한 550MB)로 반드시 실측한다.** 이 모듈의 이력이 "메모리는 사람이 기억해서 재는 값이었고, 그래서 119%가 될 때까지 아무도 몰랐다"이다.

## 7. 지표 재정의 — M1의 "0종"은 달성 불가능하고, 목표로도 틀렸다

Plan §6.1은 M1을 "분열쌍 22종 → **0종**"으로 잡았다. 프로토타입 결과 **18종이 남는다.** 원인을 확인한 결과 목표 정의가 틀렸다:

| 잔여 | 원형 빈도 | 절단형 빈도 | 분열률 |
|------|---:|---:|---:|
| 연차휴가 | 14,645 | 5 | **0.03%** |
| 연장근로 | 6,001 | 11 | 0.18% |
| 연차유급휴가 | 3,266 | 4 | 0.12% |
| 휴일근로 | 2,374 | 3 | 0.13% |
| 근로기준과 | 888 | 50 | 5.3% |

절단형 빈도가 1~50으로 떨어졌다 — 이들은 **토크나이저가 만든 인공물이 아니라 원문에 실제로 존재하는 문자열**이다(OCR 잔해, 줄바꿈으로 끊긴 표기 등). 토크나이저가 없앨 수 있는 대상이 아니다.

**M1을 개수가 아니라 분열률로 재정의한다:**

> ⛔ **이 재정의는 Act에서 폐기됐다. 아래 표를 그대로 쓰지 말 것 — §7.1 참조.**

| | 정의 | C0 | 목표 |
|---|---|---:|---|
| M1 | `PROTECTED_TERMS` 각 항목의 `절단형 / (원형+절단형)` **최댓값** | 68% | **< 6%** |

(C0 최댓값은 `회계년도` 68%. 채택안 최댓값은 `근로기준과` 5.3%.)

> 개수 기반 목표를 그대로 뒀다면 "18종 잔존 = 실패"로 읽혀, 없앨 수 없는 것을 없애려는 작업이 이어졌을 것이다.

### 7.1 그런데 분열률도 틀렸다 (Act 정정)

독립 리뷰가 **분열률 지표가 자신이 막으려던 회귀에서 값이 거꾸로 내려간다**는 것을 찾아냈고, 20,000문서로 직접 재현했다:

| | 분열률 | 판정 |
|---|---:|:---:|
| 보호 ON (정상) | 3.75% | PASS |
| **보호 OFF (회귀 재현)** | **0.00%** | **PASS** ← 회귀인데 더 좋은 점수 |

탐지식이 원형과 절단형이 **둘 다 어휘에 있을 때만** 후보로 삼기 때문이다. 새 `_strip_josa`는 문맥 독립적으로 일관되게 자르므로 보호가 없으면 원형이 어휘에서 **통째로 사라져** 후보 집합에서 탈락한다. 분열률은 *분열*을 재는데 이 구현의 실패 모드는 *전면 절단*이다. 임계 7%의 근거로 적었던 "보호 실패 시 43%·68%"도 **구 구현 수치**였다.

**최종 M1 = 존재 단언**: `PROTECTED_TERMS`의 각 항목이 색인 어휘에 존재한다(0종 사라짐). 검증 — 보호 전체 제거 시 40종 FAIL, 부분 제거(3종) 시 3종 FAIL로 **둘 다 잡는다.** 분열률은 `m1b_split_rate`로 남기되 게이팅하지 않는다.

> **일반 교훈**: 회귀 지표를 "고치기 전 상태의 증상"으로 정의하면, 그 증상을 없애는 것이 바로 이번 변경이므로 고친 뒤의 실패 모드를 못 잡는다. 지표는 증상이 아니라 **불변식**으로 세운다.

| M7 `…하/되` 잔재 | 어미 절단 실패 지문 | 72,048 | **< 15,000** |

**M1의 분열쌍 탐지는 하드코딩 목록 대조가 아니라 알고리즘으로 만든다** (Plan R-3):

```python
splits = [w for w, c in vocab.items()
          if len(w) >= 3 and c >= 200 and w[-1] in JOSA_SINGLE and w[:-1] in vocab]
```

목록 대조는 이번에 고친 28종만 지키고 코퍼스가 커지며 새로 생기는 분열을 놓친다. 탐지식은 `PROTECTED_TERMS`에 없는 새 분열도 드러낸다.

> M4는 BM25 전량 색인이 필요해 약 90초·700MB다. **Act에서 CI를 `--check --full`로 바꿔 M4를 포함시켰다** — M4가 유일한 *검색 품질* 지표이고 나머지는 전부 구조·성능 검사라, 제외하면 토큰화가 랭킹을 어떻게 바꿨는지 아무도 보지 않는다(이 사이클이 고치려던 것과 같은 실패 모드).

> `--discover`(Act 신설) — 원문에 어절로 자주 나오는데 색인 어휘에 없는 3음절 이상 문자열을 나열한다. **결정하지 않고 후보만 낸다** — `근로자가`의 `가`(조사)와 `연차휴가`의 `가`(단어 일부)는 문자열만으로 구분할 수 없기 때문이다.
