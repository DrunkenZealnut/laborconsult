| Feature | 누락 판례 601건 수집 → 중복제거 → 마크다운 정규화 → Pinecone 임베딩 |

| 관점 | 내용 |

| Problem | 노무사 수험서가 실제로 인용하는 판례 867건 중 601건(69%)이 우리 판례 코퍼스에 없어, 시험·실무에서 표준으로 다뤄지는 판례를 RAG가 검색하지 못한다 |

### 1.2 수집 경로 검증 결과 (실측 완료)

기존 크롤러(`crawl_boards.py`)는 nodong.kr 게시판 **순회** 방식이라 사건번호로 특정
판례를 지목할 수 없다. 대신 **법제처 Open API**를 검증했다.

| 검증 항목 | 결과 |
|-----------|------|
| `LAW_API_KEY` 유효성 | ✅ 정상 (`OC=kcsvictory`, HTTP 200) — 아카이브 문서의 "미등록" 기록은 현재 무효 |
| 대법원 판례 조회 (`target=prec`) | ✅ 무작위 40건 샘플 중 **38건 정확일치 (95%)** |
| 헌재 결정 조회 (`target=detc`) | ✅ 샘플 6건 전건 일치 (XML 태그는 `Detc`, 대문자 주의) |
| 하급심 (`target=prec`) | ⚠️ 4건 중 1건만 조회 가능 — 법제처는 대법원 중심 |
| 상세 API 반환 필드 | ✅ 사건명·사건번호·선고일자·법원명·판결유형·판시사항·판결요지·**참조조문·참조판례·판례내용(전문)** |
| 추가 API 키 | 불필요 — `LAW_API_KEY` 하나가 `prec`/`detc` 모두 커버 |

**예상 확보량: 약 568건 / 601건 (94%)**

> **실측 정정 (Do 단계 완료 후):** 실제 확보량은 **500건 / 601건 (83%)** 이다.
> 40건 표본의 95%는 낙관적이었다(전량 기준 83.6% 대비 +2σ 수준의 표본 운).
> 미달분 98건은 표본 진단 결과 **복구 불가** — 25건 표본에서 17건이 법제처
> DB 미수록(`totalCnt=0`), 8건은 검색은 되나 해당 사건번호로 색인되지 않음,
> 복구 가능 0건. 페이지네이션·라우팅·병합사건번호 결함은 Do 단계에서
> 수정해 29건을 추가 회수한 뒤의 수치다(설계 §3.3).

### 1.3 핵심 문제

- `app/core/legal_api.py::fetch_precedent()`는 **판시사항·판결요지만** 파싱한다
  (L727). 참조조문·판례내용은 버려지므로 코퍼스 구축에는 필드 확장이 필요하다.
- **사건번호로 조회하는 전용 함수가 없다.** `search_precedent()` 반환 dict에
  `사건번호` 키가 없어(원본 XML에는 있음) 검색 결과가 요청한 사건인지 검증할 수 없다.
  실제로 `90누9421` 검색 시 전혀 무관한 6건이 반환됐다 — **정확일치 검증 없이
  쓰면 엉뚱한 판례가 코퍼스에 섞인다.**
- `upload_new_precedents.py::collect_existing_case_numbers()`의 중복 판정 정규식이
  `(\d{4}[다두도가누][A-Za-z가-힣]*\d+)` 라서 **`다카`(27건)·`헌바`(16건)·`헌마`(9건)를
  놓친다.** 이대로 쓰면 이미 있는 판례를 다시 넣는다.
- OCR 오인식 4건(`2000대8127`, `2006대381`, `2021대69`, `2020도다296321`) —
  "다"를 "대"로 읽은 것. 보정하지 않으면 조회 실패로 버려진다.

## 2. 구현 계획

### Phase 1 — 수집 (`fetch_court_precedents.py` 신규)

- 입력: `output_노동법교재/누락_판례목록.csv` (601행)
- 사건번호 → 법제처 조회 2단계: `lawSearch.do` (검색) → `lawService.do` (상세)
- **정확일치 게이트**: 검색 결과 XML의 `<사건번호>`가 요청 사건번호와 공백 제거 후
  일치할 때만 채택. 불일치는 미발견으로 기록하고 넘어간다.
- 법원 분기: 헌법재판소 → `target=detc` (태그 `Detc`, ID 필드 `헌재결정례일련번호`),
  그 외 → `target=prec`
- OCR 보정: 명시적 치환 dict 4건 (`2000대8127`→`2000다8127` 등)
- 레이트 리밋: 요청당 0.3초 간격 (601건 × 2요청 ≈ 6분), 실패 시 재시도 3회
- **재개 가능**: 이미 저장된 파일은 건너뜀 (`crawl_boards.py::_progress.json` 관례)
- 미발견 목록을 `output_판례_보강/_미발견.csv`로 별도 기록

### Phase 2 — 정규화 (마크다운 생성)

`upload_new_precedents.py::convert_to_markdown()`이 쓰는 기존 포맷을 따르되
`원문` 필드를 추가한다 (기존 nodong.kr 포맷과 합류):

```
# {사건명}

| 항목 | 내용 |
| --- | --- |
| 분류 | {사건종류명} |
| 작성일 | {선고일자} |
| 사건번호 | {사건번호} |
| 법원 | {법원명} |
| 판결유형 | {판결유형} |
| 원문 | https://www.law.go.kr/DRF/lawService.do?...ID={일련번호} |

---

## 판시사항
...
## 판결요지
...
## 참조조문
...
## 참조판례
...
```

- 파일명: `{사건번호}_{사건명 80자}.md` — 기존 B포맷과 동일(사건번호가 앞에 와야
  중복 검사가 파일명만으로도 동작)
- 저장 위치: `output_판례_보강/` (`.gitignore`의 `output_*/` 패턴에 자동 포함)
- `<br/>` 태그 → 개행 변환, HTML 엔티티 언이스케이프

### Phase 3 — 중복 제거 (3단계)

| 단계 | 대상 | 방법 |
|------|------|------|
| L1 | 601 목록 내부 | 이미 유니크(추출 단계에서 set 처리) |
| L2 | 기존 파일 코퍼스 | `output_법원 노동판례/` + `output_판례_보강/` 전 파일에서 사건번호 추출 후 대조. **정규식을 `(\d{2,4}[가-힣]{1,4}\d+)`로 확장** — `다카`/`헌바`/`헌마` 포함 |
| L3 | Pinecone 벡터 | `chunk_id = f"precedent_{사건번호}_chunk_{i}"` — 사건번호 기반 **결정적 ID**라 재실행해도 upsert가 덮어쓴다(중복 벡터 불가) |

### Phase 4 — 임베딩 업로드 (`pinecone_upload_legal.py` 확장)

- `LEGAL_SOURCES`에 `{"directory": "output_판례_보강", "namespace": "laborlaw-v2",
  "source_type": "precedent", "label": "법제처 판례 보강"}` 추가
- **네임스페이스는 `laborlaw-v2`** — `app/core/rag.py::NS_GROUP_LAW`가 실제로
  검색하는 유일한 법령 NS. 스크립트에 정의된 `precedent` NS는 프로덕션 검색 대상이
  아니라 넣어봐야 안 잡힌다.
- **`source_type="precedent"` 재사용** → `rag.py:317` 라벨 매핑과
  `public/index.html:1365` 표시 라벨이 이미 "판례"로 대응. UI 수정 불필요.
- 청킹은 기존 700자/80자 유지

### Phase 5 — BM25 코퍼스 재빌드

- `python3 build_bm25_corpus.py` → `data/bm25_corpus.json.gz` **커밋 필수**
- 누락 시 프로덕션 하이브리드 검색이 Dense-only로 조용히 폴백된다(CLAUDE.md 규약)

## 3. 의사결정 필요 사항

| # | 질문 | 선택지 | 권장 |
|---|------|--------|------|
| 1 | 청킹 본문 범위 | A: 판시사항+판결요지+참조조문 / B: A + 판례내용 전문 | **A** — 전문은 최대 52,867자(전원합의체 실측)로 한 건이 75청크가 되고, 【원고, 상고인】 같은 절차 보일러플레이트가 검색 노이즈가 된다. 전문은 파일에 보존하되 청킹 대상에서 제외 |

| 3 | 저장 디렉토리 | 기존 `output_법원 노동판례/`에 병합 / 신규 `output_판례_보강/` | **신규 분리** — 출처(nodong.kr vs 법제처)와 포맷이 달라 섞으면 재수집·검증이 어려워진다 |
| 4 | 미발견 ~33건 처리 | 무시 / 목록 보존 | **목록 보존** — `_미발견.csv`로 남겨 추후 다른 경로(종합법률정보 등)로 보완 |
| 5 | 예상 비용 | 임베딩 API | **$0.05 미만** — 601건 × 평균 3,000자 ≈ 1M 토큰 × $0.02/1M |
