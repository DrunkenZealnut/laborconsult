## 1. 배경 및 목적

### 1.1 목적

노동상담 답변은 결론·법적 근거·판례·실무 절차·주의사항이 섞여 길어지기 쉽다. 사용자가 **핵심을 먼저 파악하고, 원하는 부분만 골라 읽을 수 있도록** 답변에 조망·탐색 레이어를 추가한다.

### 1.2 배경 (현재 상태)

`answer-visual-upgrade`(2026-03)가 이미 구현 완료되어 다음은 **작동 중**이다:

- 프롬프트(`app/templates/prompts.py`): `## ⚖️ 핵심 답변`(1~2문장 요약) 우선 배치, `> 📘 법적 근거` / `> ⚠️ 주의사항` / `> 🚨 중요` / `> 💡 참고` 콜아웃, `## 절차` 스텝, 면책 고지 구조 지시
- 렌더러(`public/index.html::md()`): 위 패턴을 `callout`, `summary-badge`, `step-list`, 향상된 테이블(`total-row`/`num-cell`), `disclaimer-notice`로 변환

**즉 "요약·시각화·구조 지침"은 이미 존재한다.** 남은 갭은 *정보 스타일링*이 아니라 *정보 조망/탐색*이다:

1. 헤딩(`##`)이 여러 개인 긴 답변에서 **전체 구조를 한눈에** 볼 방법이 없다(목차 부재)
2. 법조문 원문·판례 요지·상세 절차처럼 길지만 부차적인 내용이 **핵심과 같은 비중**으로 펼쳐져 스크롤을 늘린다(접기 부재 — answer-visual-upgrade에서 YAGNI로 보류했던 항목)
3. 스크롤을 내리면 상단 핵심 요약이 시야에서 사라진다

### 1.3 관련 문서

- 선행: `docs/01-plan/features/answer-visual-upgrade.plan.md` (시각 스타일링 — 구현 완료)
- 연관: `docs/01-plan/features/conversation-export.plan.md` (답변 내보내기)
- 코드: `public/index.html`(`md()`, `renderAnswerActions`), `app/templates/prompts.py`

## 2. 범위 (Scope)

### 2.1 In Scope (챗봇 답변 + 게시판 상세, §8 확정)

- [ ] **FR-1 섹션 목차/앵커(Outline)**: 답변에 `##` 헤딩이 3개 이상이면 답변 상단에 목차 칩을 생성, 클릭 시 해당 섹션으로 스크롤
- [ ] **FR-2 긴 섹션 접기/펼치기(Collapsible)**: 법적 근거 원문·판례 요지·상세 절차 등 지정 섹션을 `<details>`로 감싸 접기 가능(핵심 답변·요약은 항상 펼침)
- [ ] **FR-3 핵심 요약 상시 접근**: 상단 `## ⚖️ 핵심 답변`(summary-badge)을 스크롤 후에도 접근 가능하게(스티키 또는 "핵심으로" 앵커)
- [ ] **FR-4 스트리밍 안전 finalize**: 목차·접기는 스트리밍 완료 시점(답변 확정 후)에만 적용해 부분 렌더 깨짐 방지
- [ ] **FR-5 프롬프트 정합**: 접기 대상 섹션 heading 명명을 프롬프트에서 일관화(예: `## 법적 근거(상세)`)
- [ ] **FR-6 게시판 상세 적용**(§8 확정으로 신설): `public/board.html::renderDetail()`의 AI 답변에도 동일한 목차·접기·요약고정 적용

### 2.2 Out of Scope

- LLM 답변 **생성 로직**의 대규모 변경(백엔드 재작성) — 프롬프트 미세조정만
- 새 SSE 이벤트 타입 추가(프론트 후처리로 해결)
- `answer-visual-upgrade`가 이미 완료한 콜아웃/카드/스텝 재작업. **단, `board.html`은 그 작업 대상이 아니었다** — §8-2 참고
- 관리자(admin) 대화 상세 적용 — 게시판까지만, 성공 시 후속 확장
- 다크모드, 과도한 애니메이션/트랜지션
- 목차 자동 생성을 위한 LLM 추가 호출(비용·지연 — 규칙 기반 heading 수집으로 충분)

## 4. 구현 접근

### 4.1 전략: 프론트엔드 후처리 레이어

```text
LLM 답변(markdown, 구조 지침 이미 존재)
  → 렌더 (콜아웃/요약배지/스텝 — index.html은 md(), board.html은 marked.parse())
  → finalize() 후처리 (신규, 양쪽 페이지 공유): heading 수집→목차, 지정 섹션→<details>, 요약 앵커
  → 조망·탐색 가능한 답변 카드
```

- **왜 finalize 분리**: 스트리밍 중에는 heading이 미완성일 수 있어, 답변 확정 시점(`readSSE`의 done 처리, `renderAnswerActions` 부근)에만 목차/접기를 적용한다.
- **왜 규칙 기반**: 목차는 렌더된 `h2` 수집으로 충분하며 LLM 추가 호출이 불필요(비용·지연 회피).

**게시판 적용의 전제 조건 (FR-6, §8-2 확정 후 실측 확인)**: `board.html::renderDetail()`은 `index.html`의 `md()`를 재사용하지 않는다 — `DOMPurify.sanitize(marked.parse(data.answer))`로 콜아웃·요약배지 없이 순수 마크다운만 렌더링한다. 다만 `data.answer`는 챗봇과 동일한 LLM이 동일한 구조 지침(`app/templates/prompts.py`)으로 생성한 마크다운이므로, `##` 헤딩 자체는 양쪽에 동일하게 존재한다. 따라서 `finalize()`를 **렌더된 DOM의 `h2`만 보고 동작하도록** 작성하면(콜아웃 클래스에 의존하지 않으면) `md()` 유무와 무관하게 두 페이지에 그대로 재사용할 수 있다 — `md()`를 `board.html`에 이식하는 것은 이 계획의 범위가 아니다(그건 `answer-visual-upgrade` 성격의 별도 작업).

### 4.2 변경 대상 파일

| 파일 | 변경 내용 | 영향도 |
|------|-----------|--------|
| `public/index.html` (JS) | finalize 후처리: h2 수집→목차 생성, 지정 섹션 `<details>` 래핑, 요약 앵커/스티키 | **High** |
| `public/index.html` (CSS) | 목차 칩, `<details>` 접기, 스티키 요약 스타일(< 4KB) | **Medium** |
| `public/board.html` (JS) | `renderDetail()`의 `marked.parse()` 결과에도 동일 finalize 적용(FR-6) — 공유 함수로 분리 또는 인라인 이식 | **High** |
| `public/board.html` (CSS) | index.html과 동일 토큰 공유 또는 복제(< 4KB 예산 board 몫 별도 산정) | **Medium** |
| `app/templates/prompts.py` | 접기 대상 섹션 heading 명명 규칙 명시(FR-5) | **Low** |
