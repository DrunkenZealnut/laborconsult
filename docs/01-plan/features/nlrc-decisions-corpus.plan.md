## 0. 왜 이 문서가 있는가

`korean-law-mcp`(https://github.com/chrisryugj/korean-law-mcp)를 실시간 법률 API로
쓸 수 있는지 조사하다가, **그 저장소가 아니라 법제처 API 자체에서** 우리가 쓰지 않던
데이터 층을 발견했다. 조사 결과와 실측을 잃지 않으려고 남긴다.

**MCP 도입 자체는 권장하지 않는다**(§4). 그 결론도 함께 기록해 같은 조사를 반복하지
않게 한다.

## 1. 발견 — 법제처 `nlrc` target

`korean-law-mcp` README의 18개 도메인 목록을 보고, 우리가 쓰지 않는 target을
**우리 `LAW_API_KEY`로 직접** 호출해 확인했다(MCP 경유 없음).

| target | 설명 | `부당해고` 검색 | 현재 사용 |
|---|---|---:|---|
| `prec` | 판례 | 408 | ✅ `fetch_court_precedents.py` |
| `detc` | 헌재 결정 | 6 | ✅ 동일 |
| **`nlrc`** | **노동위원회 결정문** | **40,090** | ❌ |
| `decc` | 행정심판 재결례 | 4 | ❌ |
| `expc` | 법령해석례 | 3 | ❌ |
| `admrul`·`ordin`·`ppc`·`ftc` | 행정규칙·자치법규·개인정보위·공정위 | 0 | ❌ (노동 무관) |

### 1.2 현재 보유분과의 격차

`data/nlrc_cases.json`은 odcloud API 산출물로 **360건**이고, 결정적으로
**본문이 없다**:

```json
{"구분":1, "순번":360, "위원회명":"중앙", "자료구분":"기타징계",
 "작성일자":"2025-05-14", "제목":"징계처분이 최초 징계처분과 동일한 경우…",
 "조회수":470}
```

`app/core/nlrc_cases.py`는 이 제목만으로 검색해 **제목을 답변에 넣는다**(모듈
docstring: *"판정사례 제목 + 법제처 판례 본문을 결합하여 반환"*). 판정 내용 자체는
코퍼스에 없다.

법제처 `nlrc`는 상세 조회가 되고 구조가 RAG에 바로 맞는다:

```
기관명      노동위원회
담당부서    전남지방노동위원회        ← 지방노동위까지 포함
사건번호    2016부해OOO
자료구분    부당해고
판정사항    사업기간의 종료에 따라 계약기간이 종료되어 부당해고에 해당하지 아니한다고 판정한 사례
판정요지    가. 당사자 적격 여부  사용자가 공사에 대해 도급체계에서…  (491자)
판정결과    기각
```

`판정사항`/`판정요지`/`판정결과` 분리 구조가 letec 판례의 `판시사항`/`판결요지`와
같아, `pinecone_upload_court_precedents.py`의 `EMBED_SECTIONS` 방식을 거의 그대로
적용할 수 있다.

## 2. 왜 가치가 있는가

이번 세션에서 확인된 코퍼스 공백의 성격이 **"하급심이라 법제처에 없다"** 였다
(미수집 1,186건 중 하급심 부호 비중 62%, 수집률 7%). 노동 분야에서 그 층위를
실질적으로 메우는 것이 노동위원회 판정례다 — 지방노동위 수준의 구체적 사실관계를
담고, 사용자 상담 질문(계약기간 종료·당사자 적격·징계 양정)과 밀도가 맞는다.

또한 **현재 `nlrc_cases.py`가 제목만으로 답변을 만드는 구조**를 실질 본문으로
바꾼다 — 제목 360건 대비 본문 44,430건이다.

## 3. 착수 전 결정해야 할 것 (이것이 이 작업의 핵심)

| # | 미결 | 비고 |
|---|---|---|
| **D1** | **적재 범위** — 44,430건 전량인가, 자료구분·연도로 좁히는가 | 가장 큰 설계 문제. 전량은 임베딩 비용·BM25 메모리(현재 RSS 455MB/상한 550MB)를 직접 위협한다 |
| **D2** | 저작권 | 노동위원회 결정문의 법적 지위 확인 필요. 판결문(저작권법 제7조 제3호)과 같은 취급인지 별도 판단 |
| **D3** | 기존 `nlrc_cases.py`와의 관계 | 번들 360건을 대체할지, 병행할지. 병행이면 같은 사건이 두 경로로 답변에 실린다 |
| **D4** | `source_type` | 기존 `precedent`를 쓸지 신규 값을 둘지. 신규면 `rag.py` 라벨 맵·`renderSources`·법률근거 승격 3곳을 함께 갱신해야 한다 |
| **D5** | 사건번호 마스킹 | 실측 사건번호가 `2016부해OOO`로 **일부 마스킹**돼 있다. 인용 화이트리스트·중복 판정에 영향 |

**D5는 착수 전에 반드시 확인할 것** — 사건번호가 마스킹돼 있으면 `case_no` 기반
원장 그룹 키·중복 판정·인용이 전부 성립하지 않는다. 이 하나로 설계가 크게 달라진다.

## 4. `korean-law-mcp` 도입은 권장하지 않음 (조사 결론)

| 항목 | 확인 내용 |
|---|---|
| 1차 출처 | **`law.go.kr` Open API — 우리가 이미 쓰는 것과 동일** (README 원문 인용) |
| 인증 | 동일한 법제처 OC 키 |
| 라이선스 | MIT |
| 미수집 1,186건 회수 | **불가** — 같은 DB라 없는 것은 여전히 없다 |

아키텍처상으로도 맞지 않는다. MCP는 에이전트용 도구 프로토콜이고 프로덕션 경로는
Vercel 서버리스 FastAPI다. `legal_api.py`가 이미 같은 API를 `requests`로 호출하며
서킷브레이커·L1/L2/L3 캐시를 갖고 있어, MCP를 넣으면 프로세스·전송 의존만 는다.

**MCP의 실제 기여는 "어떤 target이 존재하는지 알려준 것"이다.** 그 정보는 이 문서에
옮겨 적었으므로 의존을 추가할 이유가 없다.
