## 0. 왜 이 문서가 있는가

`korean-law-mcp`(https://github.com/chrisryugj/korean-law-mcp)를 실시간 법률 API로
쓸 수 있는지 조사하다가, **그 저장소가 아니라 법제처 API 자체에서** 우리가 쓰지 않던
데이터 층을 발견했다. 조사 결과와 실측을 잃지 않으려고 남긴다.

**MCP 도입 자체는 권장하지 않는다**(§4). 그 결론도 함께 기록해 같은 조사를 반복하지
않게 한다.

|---|---|---:|---|
| `prec` | 판례 | 408 | ✅ `fetch_court_precedents.py` + `legal_api.py` 라이브 폴백 |
| `detc` | 헌재 결정 | 6 | ✅ 동일 |

### 1.1 규모 (2026-09-14 실측)

```
nlrc 전체(query=*)      44,430건
  부당해고               40,090
  부당노동행위             1,346
  차별시정                  605
```

### 1.2 현재 보유분과의 격차

`data/nlrc_cases.json`은 odcloud API 산출물로 **360건**이고, 결정적으로
**본문이 없다**:

```json
{"구분":1, "순번":360, "위원회명":"중앙", "자료구분":"기타징계",
 "작성일자":"2025-05-14", "제목":"징계처분이 최초 징계처분과 동일한 경우…",
 "조회수":470}
```

`app/core/nlrc_cases.py::search_nlrc_with_details()`는 이 제목만으로 검색해
**제목**을 답변에 넣고, 본문 보강은 **그 제목을 법제처 `prec`(법원판례) API에
검색해 대신 찾은 관련 법원판례**로 한다(`_search_related_precedent()`). 즉
**노동위 판정문 자체의 판단 내용은 지금 파이프라인 어디서도 쓰이지 않는다** —
제목을 미끼로 엉뚱한(그러나 주제는 비슷한) 법원 판례를 빌려오는 우회다.

법제처 `nlrc`는 상세 조회가 되고 구조가 letec 판례의 `판시사항`/`판결요지`와
닮았다:

```
기관명      노동위원회
담당부서    전남지방노동위원회        ← 지방노동위까지 포함
사건번호    2016부해OOO
자료구분    부당해고
판정사항    사업기간의 종료에 따라 계약기간이 종료되어 부당해고에 해당하지 아니한다고 판정한 사례
판정요지    가. 당사자 적격 여부  사용자가 공사에 대해 도급체계에서…  (491자)
판정결과    기각
```

**이 구조 유사성이 처음엔 "court_precedents처럼 통째로 적재하자"는 결론으로
이어질 뻔했다.** 그런데 §3의 실측이 그 결론을 뒤집었다 — 아래 참조.

## 2. 왜 가치가 있는가

이번 세션에서 확인된 코퍼스 공백의 성격이 **"하급심이라 법제처에 없다"** 였다
(미수집 1,186건 중 하급심 부호 비중 62%, 수집률 7%). 노동 분야에서 그 층위를
실질적으로 메우는 것이 노동위원회 판정례다 — 지방노동위 수준의 구체적 사실관계를
담고, 사용자 상담 질문(계약기간 종료·당사자 적격·징계 양정)과 밀도가 맞는다.

§3의 API 라이브 연동 방향에서는 이 가치가 **더 커진다** — 사전에 얼마나 가져올지
고민할 필요 없이 **44,430건 전체**가 매 질문마다 검색 대상이다(부분 적재로
좁힐 필요가 있는 RAG 방식과 달리).

또한 **현재 `search_nlrc_with_details()`가 노동위 판정 대신 법원판례를 대리
표시하는 우회 구조**를 실질 본문으로 바꾼다.

## 3. 접근 방식 — API 라이브 연동 (2026-09-15 확정, RAG 적재 기각)

### 3.1 왜 RAG 적재(전량/부분)를 기각했는가

Design 착수 전 실측 3건(부당해고·부당노동행위·차별시정 각 1건, `target=nlrc`
직접 조회)으로 두 전제가 무너졌다:

| 실측 | 값 | 함의 |
|---|---|---|
| 사건번호 | `2016부해OOO` / `2023부노OOO` / `2023차별OOO` — **일부 마스킹 확인** | `case_no_to_ascii(case_no)` 기반 원장 키·중복판정·인용 화이트리스트(court/crawl 판례가 쓰는 그 설계)가 **성립하지 않는다**. 같은 해·자료구분이면 다수 결정문이 이 형태를 공유할 수 있다 |
| 본문 합계(판정사항+판정요지+판정결과) | 470자 / 486자 / 728자 — **전부 700자 미만** | 크롤 판례(중앙값 3,770자)와의 유비가 틀렸다. 전량 적재해도 대부분 **1건당 1청크**, 예상 청크 수 ≈ 44,430건 × ~1 ≈ **4.5만 개 안팎** |
| 위 청크 수 대비 현재 코퍼스 | 82,166문서(RSS 471MB, 상한 550MB, 여유 79MB) | 55~60% 증가 — **BM25 메모리 상한을 직접 위협**(막연한 우려가 아니라 이 규모로) |
| `<내용>` 필드 | 3건 모두 공백 | 판정사항/판정요지/판정결과가 실질 전문(全文)이다 — 별도 "전문" 필드를 못 쓰는 게 아니라 애초에 없다 |

RAG 적재를 택하면 마스킹 문제 때문에 원장·인용 설계를 처음부터 새로 짜야 하고,
그래도 BM25 메모리 상한 리스크가 남는다. **API 라이브 연동은 이 둘을 모두
피해간다** — 색인이 없으니 메모리 상한과 무관하고, 원장·벡터ID 체계 자체가
필요 없어 마스킹이 설계를 깨지 않는다.

### 3.2 이미 검증된 패턴을 그대로 미러링한다

`app/core/legal_api.py`가 법원판례(`target=prec`)에 대해 **이미 이 정확한
패턴으로 프로덕션에 떠 있다**(`pipeline.py:1794` "Pinecone 결과 부족 시 법제처
API 폴백"):

```
search_precedent(query)           검색만(사건명·법원·날짜) — 캐시 없음, 매번 라이브
                                   LAW_SEARCH_TIMEOUT=3s
fetch_precedent(prec_id)          본문 조회 — L1(메모리)→L2(Supabase)→L3(API) 3단 캐시
                                   LAW_SERVICE_TIMEOUT=8s, 캐시 히트 시 즉시
fetch_relevant_precedents(query)  위 둘을 묶어 최대 3~5건 병렬 조회 → 포맷된 텍스트
```

새로 만들 것은 이 셋을 `target="nlrc"`로 그대로 복제하는 것뿐이다:

```python
search_nlrc(query, api_key, max_results=3)
    # target=nlrc, query=키워드
    # → [{id: 결정문일련번호, case_no(마스킹됨, 표시 안 함), title, category:자료구분,
    #     dept:담당부서, date:등록일}]

fetch_nlrc_detail(decision_id, api_key)
    # target=nlrc, ID=결정문일련번호 (마스킹 안 된 고유 숫자 — 캐시·중복판정 키로 사용)
    # → 판정사항 + 판정요지 + 판정결과 추출, 3단 캐시(prec와 동일 인프라 재사용)

fetch_relevant_nlrc(query, api_key, max_results=3)
    # 위 둘을 묶어 병렬 조회 → 포맷된 텍스트 + meta_list
```

**인용 표시**: 마스킹된 `사건번호`를 그대로 노출하지 않는다. `담당부서·자료구분·
등록일·판정결과`로 표시한다(court precedent가 `[법원 사건명]`을 헤더로 쓰는
자리에 대응) — 마스킹된 가짜 정확성보다 정직하고, 인용 화이트리스트·환각 판정
로직도 필요 없다(애초에 RAG 컨텍스트가 아니라 이 호출 결과가 직접 LLM에 들어간다).

### 3.3 파이프라인 교체 지점

`pipeline.py:1814`("2-1c. 중앙노동위원회 주요판정사례 검색")가 이미 있다.
트리거 조건(`analysis.precedent_keywords` + `consultation_topic`)은 그대로
재사용하고, **내부 구현만 교체**한다:

```
현재: nlrc_cases.search_nlrc_with_details(keywords, odcloud_key, law_key)
        └─ 로컬 360건 제목 번들 키워드 매칭
        └─ 매칭된 제목으로 법원판례(prec)를 대신 검색해 붙임 ← 노동위 본문 미사용

변경: legal_api.fetch_relevant_nlrc(query, law_key)  (신설, §3.2)
        └─ target=nlrc 라이브 검색 → 노동위 자체 판정사항·판정요지 직접 사용
```

`odcloud_api_key` 의존과 `data/nlrc_cases.json` 360건 번들, `refresh_nlrc_cases.py`는
**불필요해진다** — 44,430건 전체가 항상 최신 상태로 라이브 조회되므로 번들
갱신이라는 운영 부담 자체가 사라진다.

### 3.4 지연시간·비용

court precedent 폴백과 같은 예산이다 — 검색 3초 + 상세조회 8초(병렬, 최대
3~5건 동시), 캐시 히트 시 즉시. 이미 프로덕션에서 court precedent로 검증된
예산이라 새로운 리스크가 아니다. 임베딩 비용·BM25 재빌드(~3.5시간)·Pinecone
upsert는 전부 해당 없음.

### 3.5 fuzzy 매칭 한계는 새 리스크가 아니다

`nlrc` 검색(`lawSearch.do`)도 `prec`와 같은 **사건명 키워드 fuzzy 매칭**이다
(실측: `section=evtNm`). court precedent 라이브 폴백이 이미 이 한계를 감수하고
있다 — 목적이 "정확 인용 대상 지목"이 아니라 "관련성 있어 보이는 사례 제시"라
기존 코드의 정확일치 게이트(`fetch_court_precedents.py::search_case`, 아카이브
구축용)가 여기엔 필요 없다.

## 4. `korean-law-mcp` 도입은 권장하지 않음 (조사 결론)

| 항목 | 확인 내용 |
|---|---|
| 1차 출처 | **`law.go.kr` Open API — 우리가 이미 쓰는 것과 동일** (README 원문 인용) |
| 인증 | 동일한 법제처 OC 키 |
| 라이선스 | MIT |
| 미수집 1,186건 회수 | **불가** — 같은 DB라 없는 것은 여전히 없다 |

아키텍처상으로도 맞지 않는다. MCP는 에이전트용 도구 프로토콜이고 프로덕션 경로는
Vercel 서버리스 FastAPI다. `legal_api.py`가 이미 같은 API를 `requests`로 호출하며
서킷브레이커·L1/L2/L3 캐시를 갖고 있어, MCP를 넣으면 프로세스·전송 의존만 는다.

**MCP의 실제 기여는 "어떤 target이 존재하는지 알려준 것"이다.** 그 정보는 이 문서에
옮겨 적었으므로 의존을 추가할 이유가 없다.

### 5.1 D2 판단 — 저작권법 제7조 제3호 해당 (내부 결정, 2026-09-15)

**결정**: 노동위원회 판정(구제명령·기각·각하)을 저작권법 제7조 제3호
*"법원의 판결·결정·명령 및 심판이나 **행정심판절차 그 밖에 이와 유사한 절차에
의한 의결·결정 등**"* 후단에 해당하는 것으로 본다 — 이 프로젝트가 법원 판결문·
헌재결정(detc)·훈령예규를 같은 조항으로 취급해온 것과 **같은 판단 기준**(공적
절차에 의한 분쟁해결 결정)을 노동위원회에도 일관 적용한다.

**근거**:
- 노동위원회는 노동위원회법·근로기준법 제28조에 근거해 부당해고 등 구제신청을
  심리하는 **준사법적 합의제 행정기관**이다. 당사자 대립구조·심문을 거쳐 판정을
  내리는 절차로, 통상적 단독 행정처분과 다르다
- 제7조 제3호 후단("행정심판절차 그 밖에 이와 유사한 절차에 의한 의결·결정")은
  문언 구조상 전단(법원)과 별도로 **법원이 아닌 준사법 절차**를 포섭하도록 둔
  조항으로 읽힌다
- 법제처가 `nlrc`를 `prec`(법원판례)·`detc`(헌재결정)와 **같은 API 카테고리
  체계**로 제공한다는 정책적 정황(§1)

**한계 — 정직하게 기록한다**: 노동위원회를 **특정해** 제7조 제3호 해당을
확인해주는 판례·법제처 유권해석을 찾지 못했다(2026-09-15, WebSearch 5회 +
WebFetch 2회 — casenote.kr 제7조 판례목록, 법제처 Open API 이용안내 페이지
포함). 법원 판결문(이 프로젝트가 6개 이상 사이클에서 전단 직접 적용으로 다뤄온
대상)과 달리, **이 적용은 구조적 유비이지 확정된 선례가 아니다.** 검색 중 한
AI 요약이 "노동위원회 판정서는 행정심판절차에 해당"이라고 단정했으나 인용된
출처 어디에도 그 문장의 근거가 없어 **채택하지 않았다** — 이 결정은 그 요약이
아니라 위 근거들에 기반한다.

**기술적 완화책**(법적 판단과 무관하게 노출 최소화, §3.2와 정합): 짧은 발췌
(판정요지 수백 자)만 LLM 컨텍스트에 주입, 장기 보관 없이 24h TTL 캐시만, 출처
(담당부서·자료구분·등록일)를 항상 명시.
