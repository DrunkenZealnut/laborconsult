|------|------|
| Feature | 법제처 조문 조회가 **구버전 판본**을 반환하는 문제 해소 — MST 사전매핑을 법령명(`LM`) 조회로 전환 |
| 시작일 | 2026-08-20 |

### Value Delivered

| 관점 | 내용 |
|------|------|
| **Problem** | `legal_api.py:91-108`의 MST(법령일련번호) 사전매핑 **17개 중 11개가 낡았다**(65%). 법제처 API는 MST를 명시하면 **그 판본의** 조문을 반환하므로, 사전매핑이 히트하는 법령일수록 옛 조문을 답한다 — 근로기준법은 최대 10개월 지난 판본이다. 원인은 코드 주석의 전제 오류다: *"법 전부개정 시에만 변경"*이라 적혀 있으나 실제로는 **일부개정마다 일련번호가 바뀐다.** 그 결과 사전매핑이 없는 법령은 매번 현행을 조회해 정확한데, **매핑해 둔 주요 법령일수록 틀리는 역설**이 생겼다. 실질 변경 사례가 확인됐다 — 고용보험법 제70조 육아휴직 급여 요건이 "30일 이상"에서 **"30일 또는 7일 이상"**으로 확대됐는데, 옛 판본은 7일 경로를 모른다(받을 수 있는 사람에게 못 받는다고 답할 수 있다). |
| **Solution** | MST를 쓰지 않고 **법령명(`LM`) 파라미터로 조회**한다. 법제처가 자동으로 현행판을 반환하므로 드리프트가 **원리적으로 불가능**해진다. 17개 법령 전부에서 검증했고(17/17 성공, 평균 0.26초, 전부 현행 시행일), 오히려 API 호출이 줄어든다 — 현재는 검색(MST 획득) + 조회 2회인데 `LM`은 조회 1회다. |
| **Function UX Effect** | 사용자가 받는 법조문이 항상 현행이 된다. 개정이 잦은 고용보험법·산재보험법·근로기준법에서 특히 크다. 답변 지연은 오히려 감소한다(검색 1회 제거). |
| **Core Value** | "갱신을 잊지 않으면 정확한 구조"에서 **"잊을 것이 없는 구조"**로 바꾼다 — 사전매핑을 지우면 재발 경로 자체가 사라진다. |

### 1.2 실질 영향 — 조문에 따라 다르고, 어느 것인지 사전에 알 수 없다

과장하지 않기 위해 변경 조문의 전문을 대조했다. **전부 심각한 것도, 전부 무해한 것도 아니다.**

| 사례 | 성격 | 판정 |
|------|------|------|
| **고용보험법 제70조**(육아휴직 급여) — "제19조에 따른 육아휴직을 **30일**" → "제19조**제1항**에 따른 육아휴직을 30일 **또는 같은 법 제19조제6항에 따른 육아휴직을 7일**" | **실질 변경 — 수급 요건 확대** | 🔴 옛 판본은 7일 경로를 모른다 |
| 근로기준법 제59조 — "통계청장" → "국가데이터처장" | 기관명 정정 | 🟡 오답은 아니나 낡은 표기 |

### 1.3 처방 검증 — `LM`(법령명) 조회

MST 없이 법령명으로 조회하면 법제처가 현행판을 반환한다. **사전매핑 17개 전부에서 검증**:

- **17/17 성공**, 평균 지연 **0.26초**, 반환 판본이 전부 현행 — 단 대조 기준은 **공포일자+공포번호**여야 한다. Do 단계에서 시행일자로 대조하다 세법 2종이 오탐됐는데(부칙 단계시행 법령은 같은 공포본을 목록·본문이 다른 시행일로 표기), 공포일-호 기준으로 17/17 동일 판본이 확인됐다
- `JO` 파라미터로 특정 조문만 받는 것도 확인(`LM=고용보험법&JO=007000` → 0.22초)
- API 호출은 **줄어든다** — 현행 경로는 `lawSearch`(MST 획득) + `lawService`(조문) 2회인데, `LM`은 `lawService` 1회다. 동적 MST 조회 자체도 0.07초로 저렴하지만, 그마저 불필요해진다.

### 1.4 왜 지금까지 안 드러났는가 (재발 방지의 근거)

- `_MST_CACHE = dict(_PRELOADED_MST)`(`legal_api.py:113`)로 시작하므로 **사전매핑된 법령은 API를 아예 호출하지 않는다** — 실패 로그도, 지연도, 어떤 신호도 남지 않는다.
- 조문 텍스트는 정상적으로 반환된다. **틀린 내용이 아니라 옛 내용**이라 육안으로도 구별되지 않는다.
- 주석이 *"법 전부개정 시에만 변경"* 이라고 단언해 재확인 동기를 없앴다.

## 3. 처방 방향

1. **`fetch_article`의 조회 파라미터를 `MST` → `LM`으로 전환**. `_lookup_mst` 호출 제거.
2. **`_resolve_law_name`은 유지**한다 — `LM`은 정식 법령명을 요구하므로 약칭·표기 정규화가 오히려 더 중요해진다(예: "근퇴법" → "근로자퇴직급여 보장법").
3. **`_PRELOADED_MST`·`_MST_CACHE` 제거**. 남겨두면 "언젠가 다시 쓰겠지"로 부활해 같은 문제가 재발한다.
4. **캐시 무효화** — L1은 프로세스 재시작으로 해소되지만 **L2(Supabase, TTL 24시간)에 낡은 조문 텍스트가 남는다.** 배포 시 해당 캐시 행을 지우거나 키에 버전 접두사를 넣는다.
5. **회귀 고정** — 반환 시행일이 현행인지 확인하는 검사는 네트워크가 필요해 CI에서 못 돈다. `check_schema.py`처럼 **수동 실행 항목**으로 두고, 오프라인 회귀는 "`MST` 파라미터를 쓰지 않는다"는 구조 검사로 고정한다(사전매핑 부활 방지).

### 3.1 대안 비교 (왜 `LM`인가)

| 안 | 정확성 | 호출량 | 재발 위험 | 판정 |
|----|:---:|:---:|:---:|------|
| **LM 조회** | 항상 현행 | **2회 → 1회** | **원리적으로 없음** | **채택** |
| 사전매핑 갱신 스크립트 + 주기 실행 | 갱신 시점까지 정확 | 불변 | **높음** — 지금이 그 실패 상태이고, 갱신을 강제할 장치가 없다 | 기각 |
| 사전매핑 폐기 + 항상 동적 `_lookup_mst` | 항상 현행 | 불변(2회) | 없음 | 차선 — LM보다 호출 1회 많음 |
