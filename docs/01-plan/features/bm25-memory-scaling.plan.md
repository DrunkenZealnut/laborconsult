# bm25-memory-scaling Plan

## Executive Summary

| 항목 | 내용 |
|------|------|
| Feature | BM25 코퍼스 로드의 **메모리 상한 구조를 바꿔** 코퍼스 증가가 OOM으로 이어지지 않게 한다 |
| 시작일 | 2026-08-26 |
| 예상 기간 | 1~2일 |
| 선행 | legal-corpus-coverage(2026-08-26 머지, PR #58) — 인터닝으로 119%→67% 응급 처치 |
| 발단 | 그 사이클 Check에서 **RSS가 Vercel 한도의 119%**로 실측됨. 인터닝으로 급한 불은 껐으나 증가율은 그대로다 |

### Value Delivered

| 관점 | 내용 |
|------|------|
| **Problem** | BM25 로드 피크가 **692MB**이고 Vercel 기본 한도는 **1024MB**다. 직전 사이클 전에는 **1,218MB(119%)**로 이미 넘어 있었고, 문자열 인터닝으로 겨우 67%까지 내렸다. 그런데 **인터닝은 상수 배수를 줄일 뿐 증가율을 바꾸지 않는다** — 실측 기울기가 **문서 1만 건당 약 +90MB**라 3~4만 건만 더 늘면 다시 한도를 넘는다. 이 프로젝트는 판례·해설서 적재가 진행형이라 그 시점이 멀지 않다. 넘으면 소프트 `MemoryError`는 `search_hybrid`의 broad except가 Dense-only로 **조용히 흡수**해 하이브리드 검색이 반쪽이 되고(품질 저하가 로그에도 안 남는다), 하드 OOM-kill은 코드로 막을 수 없다. |
| **Solution** | 세 축을 분리해 각각 다른 처방을 쓴다. ① **피크**(692MB) — 코퍼스 전체를 메모리에 올린 뒤 토큰화하는 현재 구조가 원인이므로 **스트리밍 로드**로 바꾼다. ② **상주** — 검색 결과 반환용으로 `text` 29.6M자를 들고 있는데(코퍼스 438MB의 대부분), 메타만 남기면 **5MB**다. ③ **한도** — `vercel.json`을 legacy `builds`에서 `functions`로 옮기면 메모리를 최대 3,009MB까지 지정할 수 있다(과금은 메모리 비례). ①②는 코드, ③은 인프라라 서로 독립적이고, ①②만으로 충분하면 ③은 쓰지 않는다. |
| **Function UX Effect** | 사용자에게 보이는 변화는 없다 — 검색 결과·응답 품질은 동일하다. 바뀌는 것은 **코퍼스를 늘려도 하이브리드 검색이 조용히 죽지 않는다**는 것이고, 이는 앞으로의 코퍼스 확장(판례 보강·해설서 추가)이 검색 품질을 해치지 않는다는 뜻이다. |
| **Core Value** | 지금은 "코퍼스를 늘리면 검색이 조용히 반쪽이 될 수 있다"는 제약이 확장 계획에 숨어 있다. 그 제약을 없애 **코퍼스 증가와 검색 품질이 같은 방향으로 가게** 한다. |

## 1. 실측 (2026-08-26)

### 1.1 메모리 분해 — 인덱스가 아니라 **코퍼스**가 크다

76,983문서 기준, 인터닝 적용 상태:

| 단계 | RSS | 증가 |
|---|---:|---:|
| 인터프리터 + 모듈 | 16MB | — |
| **코퍼스 로드(dict + text)** | **437MB** | **+421MB** |
| 토큰화(인터닝) | 532MB | +95MB |
| BM25Okapi 인덱스 구축 | **692MB** | +160MB |

- **가장 큰 항목은 원본 코퍼스(437MB, 63%)**이고 인덱스는 160MB에 불과하다. 최적화 대상은 인덱스 압축이 아니다.
- 인터닝 전에는 토큰화 피크 934MB → 인덱스 1,218MB였다(같은 코퍼스). 인터닝이 토큰 중복 94.1%(549만 → 고유 32.6만)를 흡수해 526MB를 줄였다.

### 1.2 코퍼스 구성

| source_type | 문서 수 | 비중 |
|---|---:|---:|
| qa | 49,842 | 64.7% |
| textbook | 10,103 | 13.1% |
| precedent | 7,203 | 9.4% |
| interpretation | 6,828 | 8.9% |
| regulation | 1,763 | 2.3% |
| counsel | 1,244 | 1.6% |

`text` 총 **29.6M자**(문서당 평균 384자). 필드 비중은 text 77.8% · title 9.0% · id 7.1% · source_type 3.4% · section 2.7%.

**메타(text 제외)만 직렬화하면 5MB**다 — 상주 메모리에서 text가 압도적이라는 뜻이다.

### 1.3 증가율

문서 1만 건당 약 **+90MB**(66,307건 → 76,983건 구간의 실측 기울기 기준). 현재 692MB이므로 **약 3.7만 건**을 더 넣으면 1024MB에 닿는다. 진행 중인 코퍼스 확장(판례 보강 잔여, 해설서 추가 서적)을 감안하면 여유가 크지 않다.

### 1.4 `text` 폐기만으로는 피크가 안 줄어든다 (반증)

"인덱스 구축 후 text를 버리면 되지 않나"를 실측했다 — **피크는 692MB 그대로**다. 토큰화 시점에 text가 필요하므로 폐기는 피크 **이후**에만 가능하다. OOM은 피크에서 나므로 이 접근만으로는 해결되지 않는다.

→ **피크를 줄이려면 코퍼스를 통째로 올리지 않는 구조**가 필요하다(스트리밍).

## 2. 목표 / 비목표

### 목표

| ID | 트랙 | 내용 | 지표 |
|----|------|------|------|
| **M1** | 피크 축소 (P0) | 스트리밍 로드 — 코퍼스 전체를 메모리에 올리지 않고 토큰화 | 피크 692MB → **≤ 400MB** |
| **M2** | 상주 축소 (P0) | 검색 결과용 메타만 유지, `text`는 보관하지 않음 | 상주에서 text 437MB분 제거 |
| **M3** | 회귀 방지 (P0) | 메모리 상한을 **테스트로 고정** — 넘으면 CI가 실패 | 상한 초과 시 실패하는 회귀 |
| **M4** | 여유 확보 (P1) | 위 둘로 부족하면 Vercel 메모리 상향 | 한도 대비 사용률 ≤ 50% |

### 비목표

- **검색 품질 변경** — BM25 점수·순위·반환 필드는 **불변**이어야 한다. 이 사이클은 순수 메모리 작업이다.
- **코퍼스 축소** — 문서를 줄이면 검색 recall이 떨어진다. 직전 사이클이 공공저작물 도달을 2→21건으로 올린 것과 정면으로 충돌한다.
- **BM25 알고리즘 교체**(예: 디스크 기반 FTS·Elasticsearch) — 운영 구성요소가 하나 늘고, 이 규모에서는 과하다. M1·M2로 부족할 때 재검토.
- **`rank_bm25` 대체 구현** — 자체 BM25는 점수 동일성 검증 비용이 크다.

## 3. 처방 방향

### 3.1 M1 — 스트리밍 로드

현재 `load_bm25_corpus()`는 `json.load(f)`로 배열 전체를 파싱한 뒤 리스트 컴프리헨션으로 토큰화한다. 두 큰 객체(코퍼스 dict 437MB + 토큰 리스트 95MB)가 **동시에** 살아 있는 것이 피크의 원인이다.

- 코퍼스 포맷을 **JSONL**(줄 단위 JSON)로 바꾸면 한 문서씩 읽어 토큰화하고 즉시 `text`를 버릴 수 있다.
- `build_bm25_corpus.py`가 gz를 쓰므로 `.jsonl.gz`로 바꾸고, 로더는 구 포맷(`.json.gz`)도 읽을 수 있게 **양쪽 지원**한다 — 배포 순서 때문이다(코드가 먼저 나가고 데이터가 나중일 수 있다).
- 예상 피크: 토큰 리스트(~95MB) + 메타(~5MB) + 인덱스(~160MB) ≈ **260MB**.

### 3.2 M2 — 메타만 상주

`search_bm25`가 반환하는 `content`(= `text`)를 어떻게 채울지가 관건이다.

- **후보 (a)**: BM25 hit에 `content`를 비워 보내고, RRF 병합 후 **Pinecone `fetch(ids=...)`로 일괄 보충**. BM25 전용 hit이 있을 때만 왕복 1회 추가.
- **후보 (b)**: `text`를 짧게 잘라 보관(예: 앞 200자). 메모리는 줄지만 LLM 컨텍스트에 들어가는 본문이 잘려 **인용 무결성**을 해친다 — 직전 사이클 A-9와 같은 실패 모드라 기각 가능성이 높다.
- **(a) 우선 검토**. 단 `format_pinecone_hits`가 `content` 없는 hit을 버리므로 **보충 실패 시 BM25 전용 hit이 조용히 사라진다** — 폴백 경로를 반드시 설계한다.

### 3.3 M3 — 회귀 방지

지금까지 메모리는 **사람이 기억해서 재는 값**이었고, 그래서 119%가 될 때까지 아무도 몰랐다. 테스트로 고정한다.

- 실제 코퍼스를 로드해 RSS를 재고 상한과 비교하는 테스트. 로드가 2~3초라 CI에서 감당 가능하다.
- ⚠️ **`ru_maxrss`는 프로세스 최대치**라 다른 테스트가 먼저 메모리를 쓰면 오염된다 — 별도 프로세스에서 재야 한다.
- 상한은 실측값에 여유를 둔 값으로 정하고, **넘으면 실패**한다. "경고만" 두면 지금과 같아진다.

### 3.4 M4 — Vercel 메모리 상향 (조건부)

`functions` 속성으로 `memory`를 최대 **3,009MB**까지 지정할 수 있다(문서 확인). 그러나:

- 현재 `vercel.json`은 legacy **`builds`** 블록이고, `builds`와 `functions`는 **병용할 수 없다**. `api/index.py` + `public/**` 정적 서빙 + `routes` 전체를 `functions`/`rewrites` 체계로 옮겨야 한다 — 배포 구조 변경이라 실패 시 사이트 전체에 영향이 간다.
- 메모리는 **과금 대상**이다(Active CPU 가격 모델에서 provisioned memory가 요금에 들어간다).
- 따라서 **M1·M2를 먼저 하고, 그것으로 목표에 도달하면 M4는 하지 않는다.** 필요해지면 별도 사이클로 분리해 마이그레이션 위험을 단독으로 다룬다.

## 4. 함정 (실측·이력 기반)

| # | 함정 | 근거 |
|---|------|------|
| a | **`text` 폐기는 피크를 줄이지 못한다** | 토큰화 시점에 필요하므로 폐기는 피크 이후다(§1.4 실측). 피크가 OOM 지점이다 |
| b | **`BM25_MAX_DOCS`는 메모리 상한이 아니다** | 절단이 `json.load` 이후라 가장 큰 할당이 이미 끝난 뒤다(기존 주석에 기록됨) |
| c | **소프트 실패가 조용하다** | `search_hybrid`의 broad except가 `MemoryError`를 Dense-only로 흡수한다 — 품질이 반쪽이 되는데 로그에 "BM25 unavailable"만 남는다 |
| d | **`ru_maxrss`는 감소하지 않는다** | 최대치라 해제 효과가 안 보인다. 상주를 재려면 별도 프로세스나 다른 지표가 필요하다 |
| e | **인터닝을 되돌리면 즉시 한도 초과** | 회귀 `test_bm25_interning`이 고정 중. 이 사이클에서 로더를 재작성할 때 **인터닝을 유지**해야 한다 |
| f | **BM25 전용 hit의 content 보충 실패** | `format_pinecone_hits`가 content 없는 hit을 버리므로, 보충이 실패하면 BM25 결과가 통째로 사라진다(§3.2) |
| g | **코퍼스 포맷 변경은 배포 순서를 탄다** | 코드가 먼저 배포되고 gz가 나중이면(또는 반대) 로더가 못 읽는다 — 구·신 포맷 양쪽 지원이 필수 |

| 메모리 회귀 테스트 | 없음 | **CI에서 상한 초과 시 실패** |

## 7. 산출물 (예정)
