## 1. 착수 조사 결과 (실측 완료)

### 1.1 겹침 266건의 실제 저장 상태 — 문제 재정의

BM25 사본(`data/bm25_corpus.json.gz` = laborlaw-v2 전체 복제)으로 전수 확인:

| 상태 | 건수 | 세부 |
|------|---:|------|
| `ctx_precedent_{게시글ID}_c{n}` 벡터로 검색 가능 | 127 | nodong.kr 크롤 출신, 구버전 contextual 업로드 |
| **laborlaw-v2에 벡터 없음 = 프로덕션 검색 불가** | **139** | `upload_new_precedents.py`가 `precedent` NS(프로덕션 미조회)에 업로드. 파일명이 사건번호 선두인 B포맷 — `2023다300559`, `2019두59349` 등 최신 대법원 판례 다수 |

139건은 선행 사이클에서 "이미 코퍼스에 있음"으로 정당히 스킵됐으나, 실은
**처음부터 검색 불가능했던 판례들**이다. 파일 존재 ≠ 검색 가능 — 이 구분이
선행 사이클 중복 판정의 맹점이었다.

### 1.2 기존 laborlaw-v2 벡터의 정체 (재임베딩 방식 결정 근거)

- 생성 스크립트는 **리포 밖에서 실행된 구버전** `pinecone_upload_contextual.py`
  (진행 파일 경로가 삭제된 외부 디렉토리, git history에 업로드 커밋 없음).
  ctx_precedent 2,260 + ctx_interpretation 6,828 = 9,088 정확 일치.
- ID는 결정적(`ctx_{type}_{파일명 선두숫자}_c{전역 청크 인덱스}`)이나, 같은 ID로
  덮어쓰려면 **구버전과 동일한 청크 경계 재현**이 필요하고, 기존 벡터는 청크당
  Haiku 문맥 생성이 개입돼 있어(재처리 시 ~$1.1 + 15~25분) 재현 리스크가 있다.
- 현행 `pinecone_upload_contextual.py`는 판례를 `precedent` NS로 보내도록
  바뀌어 있어 그대로 돌리면 죽은 NS에 중복만 생긴다. `--reset`은 `delete_all`
  이라 **laborlaw-v2에 절대 사용 금지**.

### 1.3 쟁점 태그 커버리지·삭제 가능성

- 겹침 266건 중 **264건(99%)** 교재 쟁점 태그 추출 가능(`build_case_topic_index` 재사용 실측)
- ctx 구벡터 127건의 **전체 벡터 ID가 BM25 사본에 있음** → Pinecone Serverless가
  지원하는 **ID 지정 삭제**로 정리 가능(메타데이터 필터 삭제는 미지원이지만 불필요)

### 1.4 F3 대체 경로 탐침

- 대법원 종합법률정보(glaw.scourt.go.kr): **도메인 소멸** (DNS 미해석) —
  통합 포털 portal.scourt.go.kr로 이관됐고 SPA 구조라 즉시 프로그램 접근 불가
- 법제처 재조회는 이미 소진(표본 진단: DB 미수록 68% / 미색인 32% / 복구 0)

## 2. 구현 계획 — 3트랙

### Track A — F1·F2: NFD 버그 봉인 (코드 수정만, NS 복구는 안 함)

| 대상 | 수정 |
|------|------|
| `pinecone_upload_legal.py::extract_post_id()` | `unicodedata.normalize("NFC", ...)` 선행 + 정규식 `\d{2,4}[가-힣]{1,4}` 확장 + `_KR_TO_ASCII`를 court_precedents의 `_CASE_CODE_MAP`(45종) 방식으로 교체 |
| `upload_new_precedents.py::collect_existing_case_numbers()` | 정규식 `[다두도가누]` → `[가-힣]{1,4}` + NFC 선행 (F2) |
| `test_precedent_ingest.py` | 두 함수를 import해 NFD 파일명·복합 부호 회귀 고정 (T14) |

`precedent` NS 자체의 474건 손상 **복구는 하지 않는다** — 프로덕션 미조회 NS이고,
실질 가치(139건)는 Track B가 laborlaw-v2 쪽에서 회수한다. NS 정리는 별도 판단.

### Track B — 유실 139건 복구 + 겹침 266건 쟁점 태깅 통일 (핵심)

**방식: ctx 재임베딩이 아니라 법제처 재수집으로 통일.** 근거(§1.2): 구버전 청크
경계 재현 리스크·LLM 비용 없이, 검증된 기존 파이프라인을 그대로 재사용한다.

1. `fetch_court_precedents.py`에 **명시 대상 모드** 추가: `--cases <csv>` —
   대상 목록이 명시 입력일 때는 L2 파일 중복검사를 건너뜀(있는 걸 알고 재수집).
   겹침 266건 목록 CSV 생성 후 수집 → `output_판례_보강/`에 합류
2. `enrich_court_precedents.py` 재실행 → 신규 수집분 자동 태깅 (수정 불필요 —
   대상 디렉토리가 이미 `output_판례_보강/`)
3. `pinecone_upload_court_precedents.py` 재실행 → `precedent_{사건번호}` ID로
   laborlaw-v2 업로드 (기존 500건은 동일 ID 덮어쓰기라 무해)
4. **ctx 구벡터 삭제** (신규 소형 스크립트 `cleanup_ctx_precedents.py`):
   법제처 수집에 **성공한 사건만** 대응 `ctx_precedent_{게시글ID}_c*` ID를
   BM25 사본에서 뽑아 `index.delete(ids=...)`. 수집 실패분은 ctx 유지(폴백).
   실행 전 대상 ID 목록을 파일로 출력하고 `--dry-run` 제공
5. `build_bm25_corpus.py` 재빌드 → gz 커밋

예상: 수집 ~5분(266×2요청), 임베딩 ~720청크 ≈ $0.01, LLM 0회.

### Track C — F3 스파이크 (타임박스, 구현 아님)

미발견 98건의 대체 수집 경로 실행 가능성 판정만:

| 후보 | 검증 방법 | 예상 |
|------|-----------|------|
| ① 대법원 통합 포털 검색 XHR | 브라우저 자동화로 판례검색 네트워크 관찰 → 엔드포인트 재현 가능성 | 불확실 (SPA·세션) |
| ② AI Hub 법률 데이터셋 | 데이터셋 구성 확인(수동 다운로드 필요 여부) | 수동 절차 |
| ③ 판결서 인터넷열람 | 유료(건당 수수료), 비신원처리 판결문 | 비용 ~10만원, 수동 |
| ④ 영구 미수록 수용 | — | 기본값 |

산출물: 판정 결과 + 권고 1건. **이번 사이클에서 수집 구현은 하지 않는다.**
