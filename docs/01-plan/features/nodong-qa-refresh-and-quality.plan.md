# 노동OK Q&A 갱신 및 답변 품질 검증 계획

> 작성·조사 기준일: **2026-10-23** · 상태: **Plan — 구현·재수집 전**
> 입력: 로컬 원문·분석 파일, Pinecone 메타데이터, 검색·답변 코드, Supabase 읽기 전용 조회, 기존 평가 결과.
> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. 체크박스는 실제 작업 완료 후 갱신한다.

**Goal:** 2026년 3월 이후 노동OK Q&A의 수집 공백을 보완하고, 게시글·답변 변경을 지속적으로 반영하면서 정확도와 만족도에 대한 기여를 측정한다.

**Architecture:** 원문 manifest → 변경분 수집 → 문서별 청킹·임베딩·벡터 장부 → BM25 재생성 → 날짜·출처를 보존하는 검색 → 통제된 답변 평가 → 사용자 피드백 순서로 연결한다.

**Tech Stack:** 기존 Python 수집기·업로더, Pinecone `laborconsult`, BM25, 상담 파이프라인, Supabase `laborconsult` 스키마, 웹 상담·관리자 화면.

**Spec:** 이 문서의 범위·완료 조건. 계산식 수정은 [계산기 업데이트 계획](wage-calculator-update-2026-10.plan.md)에서 관리한다.

## 1. 핵심 판단

노동OK Q&A는 답변 생성에 **실제로 검색·공급되고 있다.** 다만 저장된 최신 질문은 2026-03-04이고, Q&A가 없는 경우와 비교한 정확도 실험 및 사용자 만족도 측정이 없다. 따라서 현재 자료만으로 “정확도와 만족도를 얼마나 높였다”고 판단할 수는 없다.

| 순서 | 작업 | 결과물 |
|---|---|---|
| Q0 | 원문·벡터·평가 기준선 고정 | 문서별 목록, 버전, 비교용 질문·정답 기준 |
| Q1 | 증분 수집과 기존 답변 변경 감지 | 신규·변경·실패 목록 및 수집 범위 보고 |
| Q2 | 변경분 임베딩, 오래된 청크 정리, BM25 동기화 | 대조 가능한 검색 코퍼스 버전 |
| Q3 | 날짜·출처 전달과 과거 규칙 오용 방지 | 시점에 맞는 검색·답변 및 회귀 검증 |
| Q4 | 검색 기여의 내부 추적 | 노동OK Q&A를 다른 상담 자료와 구분한 운영 지표 |
| Q5 | Q&A 사용·미사용 및 갱신 전후 비교 | 법률·계산 정확도와 답변 유용성 비교 보고 |
| Q6 | 사용자 피드백 수집 | 실제 응답자의 만족도·불만 사유 지표 |
| Q7 | 정기 갱신 운영 | 주기·실패 알림·재실행·복구 절차 |

### 2.2 답변에 사용되는 정도

**운영 조회:** 2026-09-23~10-23 KST 범위의 대화 300개 중 기존 모니터 기준으로 합성 130개를 제외한 170개·165개 세션. 해당 범위의 최신 저장일은 10-11이므로 10-23까지 매일 사용량이 관측됐다는 뜻은 아니다.

| 관측값 | 수치 | 판단 한계 |
|---|---:|---|
| 상담 사례 비교 수행 | 151/170, 88.8% | Q&A와 다른 상담 코퍼스가 합쳐진 지표 |
| 사례 표시 | 148개 답변, 사례 총 275개 | 표시가 실제 법률 정확성·사용자 만족을 의미하지 않음 |
| 낮은 유사도 표시 | 3개 | `case_match`의 임베딩 유사도 기준이며 법률적 모순 판정이 아님 |
| 상담 자료 우세 표시 | 61개 | 검색 출처 구성이 상담 자료에 치우쳤다는 내부 표시 |
| 교재 사용 표시 | 79개 | 사례 자료 외 다른 근거도 사용됨 |
| 오래된 규칙 필터 표시 | 4개 | 필터가 잡은 사례 수이며 전체 오래된 규칙의 수가 아님 |

현재 운영 메타데이터만으로는 노동OK Q&A의 개별 게시글·청크가 얼마만큼 사용됐는지 분리하기 어렵다.

**자동평가:** 2026-10-03 평가 60문항의 자동 통과율은 **90%, 54/60**이었다. 53개 답변에 Q&A 출처가 포함됐고, Q&A 출처 항목 134개의 제목은 정규화·비식별 처리를 거쳐 로컬 노동OK 원문 제목과 매칭됐다. 이는 Q&A가 컨텍스트에 공급되는 증거다.

[평가 코드](../../../eval_consultation.py)는 법률·주의 문구·의도·주제·계산 호출 등 형식적 조건을 확인하며, `expected_values`의 수치 의미를 정답과 대조하지 않는다. **90%는 법률 정확도나 사용자 만족도가 아니다.** Q&A 사용·미사용 비교도 없다. 이전 지식iN 사람 평가와 후속 자동평가도 별도 표본·지표이므로 이 수치와 합산하지 않는다.

## 3. Global Constraints — 공통 원칙

1. **범위를 식별한 뒤 갱신한다.** `qa` namespace나 `source_type=qa`만으로 노동OK Q&A 전체를 정확히 식별할 수 있다고 가정하지 않는다. 원문 목록·URL·게시글 ID·출처를 대조한다.
2. **기존 청크를 먼저 지우지 않는다.** 문서의 새 청크 업로드·확인 후 그 문서에 속한 잔여 청크만 정리한다. 현재 업로더의 `--reset`은 이 작업에 사용하지 않는다.
3. **검색 두 경로를 함께 맞춘다.** Pinecone만 최신으로 만들고 배포 BM25를 과거 버전으로 남기지 않는다. 두 저장소가 원자적으로 동시에 바뀐다고 가정하지 않고 갱신 중 상태와 복구 절차를 둔다.
4. **시점을 보존한다.** 게시글 작성일만으로 법률의 적용일을 결정하지 않는다. 질문 속 사건일과 규칙 시행일을 대조한다. 과거 사건에 유효한 과거 답변은 보존한다.
5. **사례와 공식 근거를 구분한다.** 기존 `COUNSEL_CITATION_RULES`의 사례 참고·재서술 원칙을 유지한다. 법적 결론은 공식 근거와 계산 결과로 검증한다.
6. **평가는 운영 기록과 분리한다.** 비교 평가의 대화·법령 캐시·관리자 결과 게시가 운영 데이터를 변경하지 않도록 저장을 분리하거나 비활성화한다. 평가 버전·설정은 기록한다.
7. **원문 개인정보를 늘리지 않는다.** 기존 비식별 처리를 유지하고, 내부 추적용 ID를 공개 답변에 새로 노출하지 않는다. 피드백에 자유서술을 필수로 요구하지 않는다.
8. **기존 변경 파일을 보존한다.** 조사 시점 `data/bm25_corpus.jsonl.gz`에 이미 변경이 있었다. 실행 전에 작업 상태와 배포 기준본을 확인하고 새 산출물은 임시 경로에서 검증한다.

## 4. 단계별 작업

### Q0. 목록과 평가 기준선 고정

**파일:** 기존 원문 폴더, `pinecone_upload_contextual.py`, `vector_ledger.py`, `eval_consultation.py`, `data/eval_consultation_queries.json`, `data/eval_kin_queries.json`.

- [ ] 두 Q&A 폴더를 게시글 ID 기준으로 통합 집계한다. 같은 ID의 본문·답변이 다르면 최신성 근거로 대표본을 선택하고 원본은 보존한다.
- [ ] Pinecone의 해당 문서 ID·청크·메타데이터와 원문을 대조한다. 날짜가 없거나 파싱되지 않는 글은 별도 목록으로 분리한다.
- [ ] 변경 전 manifest, 영향을 받을 벡터의 값·메타데이터, 현재 BM25, 청킹·임베딩·맥락 생성 설정을 보관한다. ID 목록만으로 덮어쓴 벡터를 복구할 수 있다고 가정하지 않는다.
- [ ] 기존 자동평가 결과와 질문 집합을 보존한다. P0 계산기 수정 후의 코드를 Q5 실험의 공통 기준선으로 고정한다.

**완료 기준:** 파일·고유 문서·청크의 차이를 설명할 수 있고, 변경 대상과 복원 대상이 정해져 있다.

### Q1. 신규 글·기존 답변을 함께 갱신하는 수집

**파일:** `crawl_qna.py`; manifest 관리 모듈과 `test_qna_ingestion.py`는 신규 제안.

**manifest 제안 필드:** `corpus_origin`, `post_id`, `canonical_url`, `local_paths`, `posted_at`, `answer_updated_at`, `fetched_at`, `question_hash`, `answer_hash`, `content_hash`, `parse_version`, `status`, `run_id`. 원문에 없는 답변 수정 시각은 추정하지 않고 null로 둔다.

- [ ] 2026-03-05부터 **실제 실행 시 정한 KST 종료 시각**까지 신규 글을 수집한다. 3월 초 기존 자료와 일정 범위가 겹치도록 조회해 경계 누락을 확인한다.
- [ ] 페이지 순회·게시글 ID 목록을 기록한다. 공지·정렬 변화가 있으므로 날짜 하나만 보고 순회를 중단하지 않는다. 끝나지 않은 페이지 구간은 미수집으로 보고한다.
- [ ] 질문·답변별 해시를 비교해 이미 존재하는 글의 추가 답변과 수정을 감지한다. 신규 글만 검사하는 중복 건너뛰기 방식은 바꾼다.
- [ ] 제목·작성일·질문·답변을 분리해 추출한다. 본문에 언급된 사건 날짜가 게시글 작성일로 들어가는 사례를 막는다.
- [ ] 실패·차단·일시적 접근 불가를 삭제로 해석하지 않는다. 재시도와 재개 위치를 기록하고 사이트의 접근 정책·응답 속도에 맞춘다.
- [ ] 답변 없음, 뒤늦은 답변, 글 수정, 중복 ID, 한글 파일명 정규화, 날짜 누락, 페이지 순서 변경을 fixture로 검증한다.

**완료 기준:** 신규·변경·동일·실패·미수집 수가 보고되고, 같은 원문으로 재실행했을 때 불필요한 신규 문서가 생기지 않는다.

### Q2. 변경분 임베딩과 검색 동기화

**파일:** `pinecone_upload_contextual.py`, `vector_ledger.py`, `build_bm25_corpus.py`, `app/config.py`; 문서 장부·테스트는 기존 구조를 재사용하거나 확장한다.

- [ ] 첫 갱신 후보는 운영 검색과 분리한 평가 namespace에 만든다. 평가 전용 namespace 매핑과 BM25 경로 선택을 추가해 갱신 전·후 스냅샷을 재현한다. 같은 namespace에 섞여 있던 다른 상담 자료는 모든 비교 조건에서 같은 버전으로 유지한다. 운영 `qa` 반영은 Q5 관문 통과 후 검증된 manifest로 수행한다.
- [ ] 원문 manifest에서 신규·변경 문서만 선택한다. 기존 `ctx_qa_{post_id}_c{index}` ID와의 호환 관계를 명시한다.
- [ ] 문서별 청크 ID, 내용 해시, 청킹 버전, 임베딩 모델·차원, 맥락 생성 설정, 업로드 성공 상태를 장부에 기록한다. 현재 `text-embedding-3-small`·1,536차원과 검색 질의 임베딩의 호환성을 유지한다. 모델 변경은 이 갱신과 별도 실험으로 다룬다. 파일명만으로 완료를 판단하지 않는다.

- 검색 유사도·출처 표시·자동 통과율을 법률 정확도나 만족도로 발표하는가?
