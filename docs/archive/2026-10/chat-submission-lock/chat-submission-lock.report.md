### 1.3 Value Delivered

| 관점 | 내용 |
|---|---|
| **Problem** | 답변 중 FAQ, 오류 뒤 다시 시도, 첨부 인코딩 중 연타 세 경로에서 main은 요청을 2~3건 보냈다. 첨부를 읽는 동안 쓴 다음 질문은 지워졌고, 파일 읽기가 실패하면 안내 없이 질문 말풍선만 남았다. |
| **Solution** | 관문 한 쌍(`beginSubmission` / `endSubmission`)을 전송 진입점 여섯 곳에 두었다. 판정은 이용 제한 잠금과 `applyChatLock()` 하나로 합쳤다. 입력은 전송 시작 때 스냅숏해 비우고, 인코딩이 실패하면 입력창이 비어 있을 때만 되돌린다. |
| **Function UX Effect** | 연타·Enter·FAQ·다시 시도로 서버가 받는 요청이 1건이 되었다(main 2~3건). 답변을 기다리는 동안 다음 질문을 입력창에 써 둘 수 있고 지워지지 않는다. 전송 직후 상태 말풍선이 바로 보인다. |
| **Core Value** | 화면이 허용하는 동작과 서버 요청이 1:1이 되었다. 일일 쿼터(IP당 50회)와 LLM 비용, 세션 기록이 사용자가 보낸 질문 수만큼만 쓰인다. PR #103의 '정상처럼 보이는 실패' 차단을 같은 버튼·finally 위에서 이어 갔다. 회귀는 행동 테스트 16개와 변이 22개로 고정했다. |

## 3. 구현 내용

### 3.1 설계 결정 요약 (D1~D11)

| # | 결정 | 구현 결과 |
|---|---|---|
| D1 | 관문은 `beginSubmission()` / `endSubmission()` 한 쌍. '진행 중 OR 잠금'이면 거절하고, 아니면 점유한다 | 진입점은 `send()`와 다시 시도 두 곳이 같은 쌍을 부른다 |
| D2 | 버튼 상태는 `applyChatLock()`이 계산한다: `btn.disabled = locked \|\| submitting` | 진행 중에는 전송 버튼만 잠근다. 입력창과 첨부는 열어 둔다 |
| D3 | `let submitting`을 `restoreChatLock` IIFE보다 앞에 선언한다 | 로드 시점 TDZ 오류를 막는다. L16이 순서를 고정한다 |
| D4 | 관문 직후 질문·첨부를 스냅숏하고 비운다. 인코딩이 실패하면 입력창이 비어 있을 때만 되돌리고 `invalid` 안내를 띄운다 | 재현 D(입력 유실)와 E(무안내)를 해결했다 |
| D5 | 진행 중 FAQ는 입력창만 채운다 | 예약 전송 300ms 뒤에도, 누른 순간 진행 중이었으면 보내지 않는다(§6.2) |
| D6 | '대화 초기화'는 진행 중 요청을 끊는다 (`chatEpoch`, `activeSend.abort()`) | 끊긴 요청은 안내 없이 끝난다. 인코딩 중이면 뒤의 epoch를 보고 보내지 않는다 |
| D7 | 상태 말풍선은 `ensureStatus()` 하나로 띄운다. `readSSE`는 새로 만들지 않고 이어 쓴다 | 전송 직후 '질문 보내는 중...'이 보이고, 말풍선은 둘로 늘지 않는다 |
| D8 | `doSend()`는 버튼을 직접 만지지 않는다 | 버튼 대입은 `applyChatLock()`에만 남는다. finally에서 버튼을 무조건 열지 않는다 |
| D9 | Enter 처리기(`keydown`)는 바꾸지 않는다 | 버튼이 점유 시점부터 잠기므로 인코딩 중 Enter도 막힌다 |
| D10 | `sw.js` VERSION을 올린다 | `v10-2026-10-06` → `v11-2026-10-22` |
| D11 | PR 1개, 커밋 1개 | 본 변경은 커밋 1개(`f884a51`)다. 리뷰 반영 커밋 2개가 같은 PR에 더해졌다 |

### 3.2 전송 진입점 6곳

| 진입점 | 관문 위치 |
|---|---|
| 전송 버튼, Enter | `send()`의 첫 문장 |
| FAQ, 게시판 '질문하기', `?q=` 링크 | `askQuestion` → `send()` (관문은 `send()`에 있다) |
| 다시 시도 | 클릭 처리기의 첫 문장(try 밖) |

### 3.3 바뀌지 않은 것

- 이용 제한 잠금의 판정·저장·해제(`guardLockFromEvent`, `setChatLock`, localStorage)
- `keydown`, 첨부 선택·미리보기, 답변 렌더링

### 6.3 리뷰 미반영 (Design §12.4)

- **막힌 Enter도 `preventDefault`한다.** 한글 IME 조합 중 Enter 영향을 확인하지 못해 그대로 두었다. 그 결과로 생기던 줄바꿈 문제는 C2가 막았다.
- **`done` 뒤 `reader.cancel()` 대기 중의 1ms 미만 창.** 이론상 창이라 수용했다.
- **진행 중 다시 시도 버튼의 시각적 비활성.** 범위 밖이다. 버튼은 남아 있어 나중에 누를 수 있다.
- **L14의 '상태 0' 단언은 약하다.** 대화를 비우기만 해도 참이 된다. 의미 있는 단언은 버튼 잠김 해제와 안내 0건이다.

### 6.4 Check 조치 (Analysis §7)

- 문서 갭 GAP-1~4를 Design v0.3으로 정정했다.
- L14에 헤더 전 abort 사례를 더했다. 콜드 스타트 중 fetch가 응답 헤더 전에 AbortError로 끝나는 경로다.
- DG-1은 범위 밖 후속으로 기록했다. DG-2는 Design §5에, DG-3은 §11에 적었다.

## 8. 교훈

### 8.1 확인된 것

1. **설계 단계의 시제품과 실제 함수 행동 테스트가 '대화 초기화' 문제(D6)를 구현 전에 잡았다.** 관문을 넣기 전까지는 보이지 않던 문제였다.
2. **변이 검사의 '검출'이 실제로는 테스트 취소였다.** 실패 원인을 확인하지 않으면 검출률 숫자는 믿을 수 없다. 대기를 `settle()`로 바꿔 멈춤이 단언 실패로 드러나게 했다.
3. **vm 테스트가 놓친 타이밍 경합은 리뷰가 찾았다.** 300ms 예약 전송은 한 실행 순서로만 시험되었다. 비동기 예약이 있으면 실행 순서의 조합까지 테스트한다.
4. **문서의 사소한 불일치가 결함을 되살릴 수 있다.** 본문 코드가 `!value`로 남아 있으면 C2 결함이 다음 구현에서 돌아온다. 설계 문서의 코드는 최종 코드와 맞춘다.
5. **상태 파일을 문자열 치환으로 갱신하면 조용히 빠질 수 있다.** 설명 줄 하나가 빠졌는데 아무도 몰랐다. 치환 뒤에는 일치 여부를 단언한다.

### 8.2 다음에 적용

- 진입점이 여럿인 기능은 진입점마다 검사를 두지 말고, 관문 한 쌍으로 묶은 뒤 구조 검사(첫 문장, finally)로 고정한다.
- 예약 실행(`setTimeout`)이 있는 진입점은 누른 순간의 상태를 기록하고, 실행 시점에 다시 판정한다.
- 브라우저 확인 기록에는 어느 코드 버전 기준인지 적는다. 이번 기록은 C2 이전 기준이다.
