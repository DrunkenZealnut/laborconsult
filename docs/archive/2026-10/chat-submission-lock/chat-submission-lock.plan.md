# chat-submission-lock — 모든 전송 진입점을 묶는 진행 중 잠금 Plan

> 입력: 외부 노동상담 서비스의 프런트엔드 패턴 검토(2026-10-21, 저장소 밖 자료) 중 P0 '전송 상태 제어'다. 검토 판정은 "채택하되, 같은 버튼·finally를 건드리는 PR #103을 먼저 정리한 뒤 '진행 중 OR 이용 제한 잠금'을 한 판정으로 합친다"였다. PR #103은 2026-10-21 머지됐다(`758f694`).
> 작성: 2026-10-22 · 단계: Plan · 기준: main `758f694`(PR #103 머지)
> 재현 방법: main `public/index.html`의 실제 `send`·`doSend`·`attachRetry`·`askQuestion`을 Node vm에서 실행했다. fetch·FileReader·DOM은 모의이고, 네트워크·브라우저는 쓰지 않았다. 재현 스크립트는 저장소 밖에 둔다.

## Executive Summary

| 관점 | 내용 |
|---|---|
| **Problem** | 같은 화면에서 요청이 두 번 나가는 경로가 셋 있다. 답변을 기다리는 동안 FAQ를 누를 때, 이전 오류의 '다시 시도'를 누를 때, 첨부를 읽는 사이 전송 버튼이나 Enter를 한 번 더 누를 때다. main 재현에서 세 경로 모두 요청이 2건 나갔다. 일일 쿼터(IP당 50회)와 LLM 비용을 두 번 쓰고, 두 답변이 한 화면에 섞여 그려진다. 또 첨부를 읽는 동안 입력한 다음 질문은 지워지고, 파일 읽기에 실패하면 질문 말풍선만 남고 아무 안내도 없다. |
| **Solution** | 전송을 시작하는 모든 경로(버튼·Enter·FAQ·게시판 '질문하기'·`?q=` 링크·다시 시도)가 하나의 관문을 지나게 한다. 관문은 첨부 인코딩부터 스트림 종료까지 '진행 중'을 유지하고, 판정은 PR #103의 이용 제한 잠금과 한 함수로 합친다. 입력은 전송을 시작할 때 스냅숏해 바로 비우고, 실패하면 되돌린다. |
| **Function UX Effect** | 답변이 끝날 때까지 두 번째 요청이 나가지 않는다. 진행 중에 FAQ를 누르면 질문이 입력창에 채워지기만 한다. 다음 질문은 답변을 읽으며 미리 써 둘 수 있고 지워지지 않는다. 전송 직후 상태가 바로 보여, 콜드 스타트 동안 무반응으로 보이지 않는다. |
| **Core Value** | PR #103의 '정상처럼 보이는 실패' 차단을 이어 간다. 화면이 허용하는 동작과 서버가 처리하는 요청이 1:1이 되어, 쿼터·비용·세션 기록이 사용자가 보낸 질문 수만큼만 쓰인다. |

**목표 지표**
- 재현 A~C(§2)의 요청이 2건에서 1건이 된다. 오프라인 vm 행동 테스트로 고정하고, 수정 전 코드에서 실패하는 것을 확인한다.
- D(인코딩 중 입력 유실)와 E(읽기 실패 무안내)가 사라진다. 입력이 보존되고, 실패하면 복원과 안내가 나온다.
- 이용 제한 잠금 계약(`test_chat_lock.js` L1~L6)은 바뀌지 않는다.
- 로컬 모의 서버와 브라우저로 연타·Enter·FAQ·다시 시도·첨부를 시험했을 때 서버가 받는 요청은 1건이다.

## 1. 출처와 범위 판단

- **출처.** 검토 문서는 외부 앱이 요청을 보내기 전에 진행 중 여부부터 검사하는 패턴을 근거로 들었다. 우리 코드에서 적용할 지점(`send`·인코딩 루프·`doSend`·다시 시도·`askQuestion`)을 짚었고, 함수 수준 재현 2건(첨부 이중 전송, 진행 중 FAQ)을 붙였다. 이번 Plan은 PR #103 머지 뒤의 main에서 재현을 다시 했고, 경로 셋(다시 시도·입력 유실·읽기 실패)을 더 찾았다(§2).
- **가져오지 않는 것.** 외부 앱의 5초 재전송 대기는 쓰지 않는다. 서버 남용 방어가 아니고(그 역할은 분당 한도와 일일 쿼터가 맡는다), 정상적인 빠른 후속 질문까지 막는다.
- **범위.** `public/index.html`의 상담 전송 경로가 대상이다.
  - 전송 버튼, Enter
  - `askQuestion`을 부르는 FAQ, 게시판 '질문하기', `?q=` 링크(계산기 흐름도에서 진입)
  - 오류 안내의 '다시 시도'
- 게시판 글쓰기와 이메일 모달은 따로 게이팅(CAPTCHA)하므로 범위 밖이다. 서버는 바꾸지 않는다.

## 2. 현재 동작 (재현 2026-10-22, main `758f694`)

| # | 경로 | 결과 |
|---|---|---|
| A | 첨부가 있을 때, 인코딩 중에 전송 버튼이나 Enter를 한 번 더 누름 | 인코딩 중에는 버튼이 열려 있다(`btn.disabled=false`). 사용자 말풍선 2개, 요청 **2건** |
| B | 답변 수신 중 FAQ 선택 | 300ms 뒤 `send()`가 진행 중 여부를 보지 않는다. 요청 **2건** |
| C | 답변 수신 중 이전 오류의 '다시 시도' | `doSend`를 직접 부른다. 요청 **2건** |
| D | 첨부 인코딩 중 다음 질문 입력 | 인코딩이 끝나면 `send()`가 입력창을 비워 **입력이 사라진다** |
| E | 파일 읽기 실패 | `send()`가 예외로 끝난다. 질문 말풍선만 남고 안내 요소는 0개다(요청 0). 입력과 첨부는 남는다 |

- 첨부가 없으면 버튼 연타는 막힌다. `doSend`가 같은 틱에 버튼을 잠그기 때문이다. 그래서 A는 첨부가 있을 때만 생긴다.
- 상태 말풍선('질문 분석 중...')은 `readSSE`가 응답 헤더를 받은 뒤에야 만든다. 그 전에는 사용자 말풍선만 보인다. 이 구간에는 첨부 인코딩, 네트워크, 콜드 스타트가 들어간다(콜드 스타트는 BM25 로드만 Linux에서 약 7초).
- 요청 두 건이 함께 나가면 생기는 일:
  - 일일 쿼터와 LLM 비용을 두 번 쓴다.
  - 두 답변이 한 화면에 동시에 그려진다. `removeStatus()`가 모든 상태 말풍선을 지우므로, 한쪽 상태 표시를 다른 쪽이 지운다.
  - 같은 세션의 동시 요청이라 세션 기록 저장이 겹칠 수 있다(추정, 검증하지 않음).

## 3. 원인

- **'진행 중' 상태의 표현이 전송 버튼의 `disabled` 하나뿐이다.** 게다가 그것을 `doSend` 첫 줄에서야 켠다. 첨부 인코딩(`send()`의 await 루프)이 그보다 먼저 돈다.
- **진입점마다 검사가 다르다.**
  - Enter는 `btn.disabled`를 본다.
  - 전송 버튼은 disabled 속성에 기댄다.
  - FAQ·게시판·`?q=`는 `send()` 첫 줄의 이용 제한 검사만 거친다.
  - '다시 시도'는 `doSend`를 직접 부르고 이용 제한만 확인한다.
  - 진행 중 여부를 보는 공통 지점이 없다.
- **`send()`는 입력창과 첨부를 인코딩이 끝난 뒤에 비우고, 인코딩 예외는 잡지 않는다.**

## 4. 해결 방향

### 4.1 P0 — 하나의 전송 관문

- 전송을 시작하는 모든 경로가 한 관문 함수를 지난다. 관문은 '진행 중 OR 이용 제한 잠금'이면 거절하고, 통과하면 그 자리에서 진행 중을 점유한다. 첨부 인코딩부터 스트림 종료까지를 한 try/finally로 감싸 해제 지점을 하나로 둔다.
- 버튼·첨부·입력창의 상태는 지금처럼 `applyChatLock()` 한 곳에서 계산하되, 진행 중 여부도 함께 본다.
  - 진행 중에는 전송 버튼만 잠근다.
  - 입력창과 첨부는 열어 둔다. 답변을 읽으며 다음 질문을 써 둘 수 있게 하기 위해서다.
  - 이용 제한 안내 문구(placeholder)는 그대로 둔다.
- 진행 중에 FAQ를 누르면 질문을 입력창에 채워 두기만 하고 보내지 않는다. `askQuestion`이 입력창을 먼저 채우고 `send()`를 부르므로, 관문이 막으면 자연히 그렇게 된다.
- '다시 시도'도 관문을 지난다. 진행 중에 누르면 아무 일도 일어나지 않고, 버튼은 나중에 다시 누를 수 있게 남긴다. 지금은 누르는 즉시 비활성이 된다.

### 4.2 P0 — 입력 스냅숏과 실패 복원

- `send()`는 관문을 통과하자마자 질문과 첨부를 스냅숏하고, 입력창과 미리보기를 비운다. 인코딩 중에 쓴 다음 질문이 지워지지 않는다(D).
- 인코딩이 실패하면 다음을 한다(E). 서버 요청은 보내지 않는다.
  - 관문을 푼다.
  - 입력창이 비어 있을 때만 질문과 첨부를 되돌린다. 그사이 사용자가 쓴 글을 덮지 않기 위해서다.
  - 안내 요소를 띄운다.

### 4.3 P1 — 전송 직후 상태 표시

- 관문을 통과하면 상태 말풍선을 먼저 띄우고, `readSSE`는 그것을 이어 쓴다(새로 만들지 않는다). 상태 말풍선이 둘로 늘지 않게 한다.

### 4.4 P1 — 테스트·문서·배포

- `test_chat_lock.js`에 vm 행동 테스트를 더한다. §2의 재현 A~E를 옮겨, 수정 전 코드에서 실패하고 수정 후 통과하는지 확인한다. 모든 진입점이 관문을 지나는지는 구조 검사로 고정한다.
- CLAUDE.md Abuse Guard 절의 프런트 계약에 '진행 중 잠금' 규칙을 더한다.
- `public/sw.js`의 `VERSION`을 올린다(현재 `v10-2026-10-06`).

## 5. 범위 밖

- **서버 측 중복 방지(요청 ID, 멱등 키).** 정상 화면 경로의 중복은 관문이 없애고, 의도적인 반복은 분당 한도와 일일 쿼터가 막는다.
- **5초 재전송 대기.** §1 참조.
- **답변 중지 버튼.** 진행 중 잠금이 생기면 새 질문은 답변이 끝나거나, 60초 무활동으로 중단된 뒤(`SEND_TIMEOUT_MS`)에 보낼 수 있다. 중지 기능은 별도 과제다.
- **`?q=` 외부 링크 자동 전송.** 외부 페이지가 방문자의 브라우저로 질문을 보내게 할 수 있다(그 방문자의 쿼터를 쓴다). 같은 출처 확인이나 확인 단계 도입은 따로 판단한다(도입 검토 #5).
- **도입 검토의 나머지.** 선택형 상황 확인, 답변별 피드백, 후속 질문.

## 7. 완료 조건

1. 재현 A~C에서 요청이 1건만 나간다. vm 행동 테스트로 고정하고, 수정 전 코드에서 실패하는 것을 확인한다.
2. D: 인코딩 중에 쓴 글이 남는다. E: 읽기에 실패하면 관문이 풀리고, 질문과 첨부가 돌아오며, 안내 요소가 뜬다(요청 0).
3. 이용 제한 계약(L1~L6)은 그대로다. 진행 중에 이용 제한 거절이 오면 전송이 끝난 뒤에도 잠금이 유지된다.
4. 전송 직후 상태 말풍선이 보이고, 응답이 오면 같은 말풍선을 이어 쓴다(둘로 늘지 않는다).
5. CI 오프라인 스위트와 노드 테스트가 통과한다. 로컬 모의 서버의 브라우저 확인에서 연타·Enter·FAQ·다시 시도·첨부 모두 서버가 받은 요청이 1건이다.
6. `sw.js` `VERSION`을 올리고 CLAUDE.md에 반영한다.
