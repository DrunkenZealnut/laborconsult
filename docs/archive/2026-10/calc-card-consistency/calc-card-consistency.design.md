# calc-card-consistency — Design

> Plan: `calc-card-consistency.plan.md`(같은 폴더, v0.1) · 작성 2026-10-18 · 기준 코드 main `56c621b`
> 범위: Plan P0(G2·kin-01)·P1(문서·fixture). Design 중 고정수당 축에서도 금액이 갈리는 것을 찾았다(f1·f2). 원인이 G2와 달라 범위 밖으로 두고 후속을 권한다(§0 D8·§11).
> 검증 방법: `_run_calculator(params, query)`에 의도분석 결과 형태의 params를 넣었다(LLM 호출 없음). 방법 A(§3)와 D1(§4)은 **런타임에 끼운 시뮬레이션**으로 확인했다. 대상은 격자 2,160카드와 기존 오프라인 스위트 4종이다. 저장소 코드는 바꾸지 않았고 스크립트는 저장소 밖에 둔다.
> 새 법률 사실은 쓰지 않는다. 카드 문구의 근거(제18조 제3항·제50조·2022다291153)는 기존 원문 앵커 그대로다(§1).

## 3. G2 — 연장분을 더하는 곳과 월 총액을 같은 판정으로

### 3.1 규칙과 위치

`_run_calculator`에서 구성 판정이 모두 끝난 뒤, 계산기 호출 직전(`composition_unknown` 다음, `calc = WageCalculator()` 앞 — 현재 2569~2575행)에 둔다.

```python
    # 질문에 적힌 연장·야간·휴일 근로시간을 평균임금·보수 추정(F6)이 더하는 입력이면 연장수당도 계산한다(calc-card-consistency G2).
    # 빠지면 '월 총 예상 수령액'에 그 몫이 없어 같은 카드의 세전 월 급여·평균임금과 갈렸다(4대보험만: 월 총 2,502,857원 vs 세전
    # 3,285,000원, 세후 2,885,875원). 위의 파생 연장 규칙·facade 자동 대상과 같은 뜻이다. 구성 판정 뒤라야 한다 — 그 임금이 이미 든
    # 금액(포괄·구성 진술)은 F6가 더하지 않아 대상이 아니고, 보류 경로의 amount_hold는 이 규칙보다 먼저 정해진다
    premium_added = has_wage and not unknown_mode and "overtime" not in targets and adds_premium_pay(inp)
    if premium_added:
        targets.append("overtime")
```

계산 뒤(`result` 후처리 블록 안):

```python
        if premium_added:
            result.warnings.append(_PREMIUM_ADDED_NOTE)
```

**위치가 구성 판정 뒤여야 하는 이유.** `_adds_premium`은 `wage_composition_known`을 읽는다. 이 값은 구성 판정 블록이 정한다. 또 보류 경로의 `amount_hold`는 그 블록 안에서 그때의 targets로 만든다. 규칙을 파생 연장 규칙(2412행) 옆, 즉 구성 판정 앞에 두면 둘 다 어긋난다. 보류 경로라면 연장수당이 amount_hold에 함께 들어가 문제가 없다. 하지만 정확 경로(기본급 + 총액 진술)에는 사용자가 묻지 않은 연장수당이 생긴다.

### 3.2 판정 함수 (`wage_calculator/calculators/shared.py`)

```python
def has_premium_hours(inp: WageInput) -> bool:
    """연장·야간·휴일 근로시간이 하나라도 입력됐는가 — 포괄임금 역산의 근거이자 F6가 더할 시간이 있는지의 판정."""
    s = inp.schedule
    return any((getattr(s, f, 0) or 0) > 0 for f in (
        "weekly_overtime_hours", "weekly_night_hours", "weekly_holiday_hours", "weekly_holiday_overtime_hours"))


def adds_premium_pay(inp: WageInput) -> bool:
    """월 임금총액 추정(monthly_pay_estimate)이 연장·야간·휴일 근로 임금을 더하는 입력인가 — 더하면 카드의 연장수당 섹션도
    계산해야 '월 총 예상 수령액'이 같은 금액을 쓴다(calc-card-consistency G2)."""
    return _adds_premium(inp) and has_premium_hours(inp)
```

> → §13 C15: 구현은 `_adds_premium(inp) and premium_weekly(inp, 1.0).total > 0`(더할 금액)이다. `has_premium_hours`는 구성 판정(포괄임금 역산 등)이 그대로 쓴다.

- `pipeline._has_premium_hours`(1300행)는 지우고 `from wage_calculator.calculators.shared import has_premium_hours as _has_premium_hours`로 바꾼다. 호출부 10여 곳은 그대로 둔다.
- facade `_auto_detect_targets`는 바꾸지 않는다(CLI 전용, §11-6).

### 4.2 시간 추출 — `_hours_mentions` 확장

질문의 'N시간' 해석은 한 곳에서 한다. `_hours_mentions`(1776행)가 돌려주는 3-튜플을 이름 있는 튜플로 바꾸고 필드 둘을 더한다.

```python
class _HourMention(NamedTuple):
    value: float
    span: bool            # 기간 합계(실근로)인가 — 출처 대조(_ground_schedule_hours)가 쓴다
    days: tuple           # 그 절의 기간 일수들
    daily: bool = False   # '하루 N시간'·'N시간씩' — 1일 시간(조건부 예시만 쓴다)
    aside: str = ""       # 근무시간이 아닌 표현: "threshold"(15시간 이상)·"break"(휴게 1시간)·"range"(6~7시간)
```

> → §13 C10: `total`(표지 있는 합계) 필드와 `aside`의 `premium`·`period` 값을 더했다. `daily`는 출처 대조의 `daily_rate`와 달리 날짜의 '1일'을 빼고 '일 N시간'을 더하며 1주 단위가 앞선다 — 출처 대조가 읽는 값은 그대로다.

- `daily`의 판정은 기존 `daily_rate`와 같다(`_DAILY_UNIT_RE` 또는 뒤에 '씩').
- `aside`는 새 정규식 셋으로 판정한다.
  - 기준선: 시간 바로 뒤의 '이상·미만·이하·초과·넘·안 되·못 미치'
  - 휴게: 시간 바로 앞의 '휴게·휴식·점심·식사·쉬는 (시간)'
  - 범위: 시간 바로 앞의 '숫자 ~·-'
- 호출부 둘은 필드 이름으로 읽게 고친다(`_ground_schedule_hours`·`_rejected_span_hours`). **새 필드는 출처 대조가 읽지 않는다.** 그래서 버리는 값·안내는 지금과 같다(R7, 회귀는 `test_audit50` T10 반례 전부).

### 4.3 예시를 만드는 조건 (모두 참일 때만)

| # | 조건 | 어긋나면 | 근거·실례 |
|---|---|---|---|
| 1 | 미확인 모드 주휴 블록이 붙는 경로이고(임금 없음 경로·미확인 모드), 주휴가 대상이며, 근로시간 제도 신호(`regime`)가 없다 | 예시 없음 | 제도 신호 카드는 제도 확인이 먼저다 |
| 2 | 1주 근무일수가 있다(`params["weekly_work_days"]`, 0 < d ≤ 7) | 예시 없음 | 일수를 가정하지 않는다 |
| 3 | 범위 표현이 없고, 기준선·휴게 표현을 뺀 시간 값이 하나로 정해진다. 1일 값이 하나 이하, 합계 값이 하나 이하여야 하고, 둘 다 있으면 1일 × 근무일수 = 합계(±0.05)다 | 예시 없음 | kin-01: 6시간씩 + 총 18시간 → 6 × 3 = 18. '하루 6시간, 총 20시간'은 어긋난다. '6~7시간'은 값이 하나가 아니다. '주 15시간 이상이어야'는 기준선이라 뺀다 |
| 4 | 기간 합계에 붙은 일수('3일 동안'·'28일~30일')가 있으면 그 일수가 1주 근무일수와 같다 | 예시 없음 | a50-40: '3일 동안 25시간' + 주 6일 → 3 ≠ 6. 이 조건이 없으면 '주 6일 × 4.1667시간 = 25시간' 예시가 나온다(시제품 실측) |
| 5 | 1일 시간 ≤ 8, 1주 합계 ≤ 40 | 예시 없음 | 넘는 시간은 소정근로일 수 없다(제50조). '하루 10시간씩 이틀'·'주 6일 × 7시간(42시간)' |
| 6 | 1주 합계가 15시간 미만이면 산식 대신 '미발생' 줄 | — | 제18조 제3항 |

> → §13 C10·C11: 조건 1은 계산한 `regime`이 아니라 질문의 제도 신호로 본다(미확인 모드에서는 `regime`이 늘 비어 있다). 조건 3의 합계는 표지 있는 값('총'·'주 N시간'·'N일 동안 N시간')만이고 표지 없는 값은 1일 시간·합계와 같을 때만 둔다. 조건 4는 질문 전체의 기간 일수를 본다. 연장·야간·휴일 근로나 1주가 아닌 기간의 합계가 있으면 예시를 만들지 않는다.
>
> → §13.6 C21·C22(Check): '총 N시간'은 1주 단서(같은 문장의 주 3일·이번 주 등, 또는 그 절의 기간 일수)가 있고 그 절에 하루 단서(시각 범위·어제·익일 등)가 없을 때만 합계다. 한 자리 날짜의 '1일'('10월 1일'·'지난 1일')은 1일 단위가 아니다.

함수 경계는 다음 둘로 나눈다. 블록 함수는 질문을 모른다(순수 함수 유지).
- `_question_work_hours(query, weekly_days) -> float | None`: 조건 2~5를 보고 1일 시간을 돌려준다.
- `_conditional_holiday_example(query, weekly_days, hourly) -> str | None`: 조건 6과 문구를 맡는다.

`_unknown_schedule_block`은 `example: str | None = None` 인자를 받는다. 두 호출부(2357·2393행)가 `holiday and regime is None`일 때만 예시를 계산해 넘긴다.

## 11. 범위 밖·후속

1. **기준 월액 단일화(f1·f2, 권장 후속 사이클).** facade 월 총액과 F6 소비처 8곳의 기준 월액을 한 함수로 모은다. 그 함수는 통상임금 월액 + 비통상 고정수당 + max(계산한 연장 등, 고정연장수당)이다. §3.7 대안 B를 기준 월액까지 넓힌 형태다. 고칠 대상은 다음 둘이다.
   - f1: 시급 12,000원 + 고정연장수당 20만 원 → 월 총 2,702,857원 vs 세전 2,502,857원
   - f2: 월급 + 직책수당에서 평균임금 계열이 수당을 빠뜨린다. 연장이 있으면 퇴직금이 그만큼 적다(§2.2).

   이 사이클의 불변식 격자에 고정수당 축을 더하는 것이 그 사이클의 완료 조건이다. 법적 쟁점(보수월액의 비과세 식대, 평균임금의 상여 3/12 등)도 함께 다룬다.

12. **표지 없는 값의 예시 회복.** '주5일 40시간'처럼 표지 없는 합계는 이제 예시가 없다(리뷰어 코퍼스 대조: 예시 158 → 73건). '주 N일 V시간'(15 ≤ V ≤ 40)을 합계로 보는 보강을 검토할 수 있다(리뷰 제안). 그 질문들은 대개 의도분석이 시간을 뽑아 미확인 모드가 아니므로 급하지 않다.
