- 설계 대조 갭 G-1~G-5(Low 4·Info 1)는 모두 조치했다. G-1·G-2는 핫픽스, G-3·G-4는 Design §14 문서 보강, G-5는 측정 지문 기록이다.
- 설계 범위 밖 결함 S1(Medium)·S2~S6(Low 5)은 Match Rate에 넣지 않는다. CLAUDE.md의 원칙대로, Match Rate는 설계대로 만들었는지만 답하기 때문이다. S1·S3·S6은 핫픽스로 고쳤고, S2·S4·S5는 §7 후속이다.

## 8. 교훈

### 8.1 확인된 것

1. **시제품을 Design 단계에서 실제 코드에 적용하고 CLI 116사례를 사례별로 diff해 '의도된 변경'을 미리 목록화했다.** 그 덕에 Do의 CLI diff가 설계 목록(14건)과 정확히 같았다. 설계 문서가 숫자 근거를 갖는 값이었다.
2. **독립 리뷰와 갭 분석이 모두 파이프라인 경로에서 결함을 찾았다.** S1과 M4가 그렇다. 계산기를 직접 부르는 테스트로는 보이지 않는 결함이었다. 계산기 단일화도 파이프라인 카드로 검증해야 한다.
3. **리뷰 반영 코드(M4)가 새 회귀(S1)를 만들었다.** '포함' 같은 자연어 규칙은 흔한 다른 용법(세금 포함)을 반례로 먼저 넣고 짜야 한다.
4. **좁은 기준이 추출 오류를 가리고 있었다(calc-18).** 단일화는 상위 단계의 오류를 드러낸다. 연 상여를 월 수당으로 뽑는 오류는 예전에도 있었지만 휴업수당이 고정수당을 보지 않아 가려졌다.
5. **반올림된 월액 × 12(연봉)는 경계에서 틀린다.** 연 단위 값은 월액을 거치지 말고 연봉 원값에서 받아야 한다(S3).

### 8.2 다음에 적용

- 공통 값을 단일 함수로 옮길 때는 시제품과 CLI diff 목록을 먼저 만든다. 목록에 없는 변화는 회귀로 본다.
- 자연어 판정(포함·전·후 같은 표지)은 반례 목록(흔한 다른 용법)을 테스트 첫 항목에 둔다.
- 공통 값을 바꾸면 Live를 같은 fixture로 기준선과 함께 찍는다. 추출 단계의 회귀는 최종 답변에서만 보인다.
- 완료 조건을 바꾸면 그때 Plan 본문에도 적는다. 이번에는 Design과 Analysis에만 남았다가 Report 단계에서야 Plan v0.2에 반영했다.
