### 2.1 오프라인 Pinecone 타임아웃 격리

**프로덕션 핸들과 합치지 않은 것이 설계 결정이다.** 180초는 프론트 idle(60초)의 **3배**라 브라우저가 이미 abort한 뒤에도 호출이 이어지고, 동시에 Vercel `maxDuration`(300초) **안**이라 플랫폼이 끊어 주지도 않는다 — 아무도 듣지 않는 채로 최대 180초를 태우고 그만큼 과금된다. 공용 팩토리로 합치면 그 값이 언젠가 `rag.py`로 샌다.

회귀(`test_offline_units.py`)는 **양방향**이다:
- 요청 경로 5개 모듈(`api/index.py`·`rag.py`·`pipeline.py`·`graph.py`·`self_rag.py`)이 이 함수를 import하지 않을 것

### 2.2 BM25 색인 생존 검증 복구

`_PROBE`는 계속 8쿼리를 `search_bm25`로 검색해 결과를 실어 보내는데 `main()`이 `probe["results"]`를 읽지 않았다. 변이 검사로 실패 모드를 실증했다:

```
색인 소실 시:  ok=True, docs=79,763   ← 기존 단언 전부 통과
               hits=0                 ← 새 단언이 잡는다
```

단언은 둘 — ① 8쿼리 전부 1건 이상(색인 생존) ② 최대 점수 > 0(가중치 생존). **순위는 얼리지 않는다** — `search_bm25`는 안정 정렬이라 동점 순서가 코퍼스 인덱스 순서에 의존하고, 그 순서는 Pinecone 페이지네이션 때문에 재빌드마다 달라진다. 순위를 얼리면 내용이 같아도 재빌드만으로 깨지고, 실무 대응이 "기준값 삭제"가 되어 가드가 소멸한다(이 파일의 프로즌 기준값 주석이 기록한 이력).

부수 정리: 죽은 `only` 파라미터와 `_PROBE`의 해당 분기 제거, stale 주석 3곳, CI 스텝 이름(`검색 동일성` → `색인 생존`).

**콜아웃 처리가 이 변경의 핵심이다.** h4를 그냥 열면 섹션 라벨의 16.4%(110개)가 `관련법령`류가 되고 73개 섹션이 같은 이름을 갖는다 — 출처 카드로 무의미하다. `NON_BOUNDARY_RE`가 그것을 경계에서 빼되 **폐기로 세지 않는다**: 구분 없이 세면 폐기율이 2.5% → **15.2%** 로 상한(10%)을 넘겨, 위생 규칙 오작동 감지기가 의도된 동작에 상시 발동한다. 게이트의 목적은 "규칙이 오작동해 섹션이 조용히 뭉개진다"를 잡는 것이지 의도된 비경계를 세는 것이 아니다.

콜아웃 규칙을 전역으로 둔 것은 실측 근거가 있다 — 기존 4권 h1~h3에 **0건 매치**라 `section_idx`가 밀리지 않는다. T29-h가 그 0건을 계속 확인한다.

`load_body_normalized`는 일부러 h1~h3 고정으로 남겼다. 소비자가 enrich이고, 범위를 넓히면 enrich가 보는 표제 집합이 바뀌어 판례 쟁점 태그가 달라지고 **판례 코퍼스 전체가 재업로드 대상**이 된다(태그는 청크 텍스트의 접두사다). 청킹 경계와 위생 처리 범위는 목적이 달라 분리했다.

### 2.4 측정 — 도달률은 개선되지 않았다

`eval_retrieval.py`(고정 fixture, `--freeze` 미실행):

```
변경 전:  기준선 13/19 = 68.4%  →  승격 17/19 = 89.5%   승격 발동 4건
변경 후:  기준선 13/19 = 68.4%  →  승격 17/19 = 89.5%   승격 발동 4건
```

**완전히 동일하다.** 이 변경이 개선한 것은 *도달*이 아니라 *귀속*이고, 그 이상을 주장할 근거는 측정에 없다.

한 가지 관찰 — 최종 컨텍스트의 해설서 건수가 기준선 28 → 23으로 줄었다. 도달률·발동률이 동일하므로 설계의 판정 기준(집계 지표)으로는 회귀가 아니지만, 설계 문서가 적은 `±1건 흔들림`보다는 크다. 청크 세분화의 영향으로 보이나 단정할 근거는 없다.

### 3.1 CodeRabbit 지적 1건 — 반영

`heading_max_level` 범위 검사만으로는 `3.5`·`True`가 통과한다. `#{1,3.5}`는 정규식 **수량자가 아니라 리터럴**로 해석돼 예외 없이 어떤 헤딩에도 매치되지 않는다:

```
re.compile(r"^(#{1,3.5})\s+(.+)$").search("## 제1장 총칙")  → None
```

결과는 조용한 실패다 — `parse_sections`가 본문 전체를 `"본문"` 한 섹션으로 만들고, 헤딩이 0개라 폐기율이 0/0이 되어 게이트도 통과한다. 생성 시점에 막았고(`bool`은 `int` 서브클래스라 별도 배제), T29-i를 7종(`7`·`0`·`-1`·`3.5`·`True`·`'3'`·`None`)으로 넓히고 T29-j로 그 리터럴 패턴이 헤딩에 매치되지 않는다는 근거 자체를 고정했다.

## 4. Lessons Learned

### 4.1 "검증을 지울 때 무엇이 함께 지워지는가"

PR #62의 등가성 대조 종결은 그 자체로는 타당했다(구 포맷 파일이 삭제돼 대조 대상이 사라졌다). 문제는 그 블록이 **검색 출력을 보는 유일한 지점**이기도 했다는 것이고, 종결 판단에서 그 겸직이 보이지 않았다. 검증을 제거할 때는 "이 검증이 죽으면 무엇이 무방비가 되는가"를 따로 물어야 한다.

### 4.2 게이트가 세는 것과 세지 않는 것을 구분해야 한다

콜아웃을 폐기로 세면 폐기율이 15.2%로 뛰어 게이트가 발동한다. 그때의 자연스러운 대응은 **상한을 올리는 것**이고, 그러면 감지기가 꺼진다. 옳은 처리는 분류를 나누는 것이었다 — "손상 폐기"와 "의도된 비경계"는 게이트가 답하려는 질문이 서로 다르다.

### 4.3 개선폭을 측정하면 개선이 없을 수도 있다

`heading_max_level`은 착수 시점에 "검색 품질 개선"으로 분류돼 있었으나, 측정 결과 도달률은 **완전히 동일**했다. 실제 개선은 출처 귀속이었다. 측정하지 않았다면 보고서에 "검색 개선"으로 적혔을 것이고, 그 오기록이 다음 사이클의 판단 근거가 됐을 것이다.

### 4.4 잘못된 설정값이 예외 대신 리터럴로 흡수되는 경로

`#{1,3.5}`가 `re.error`를 내지 않고 리터럴로 해석되는 것은 Python 정규식의 정상 동작이다. 값 검증을 범위로만 두면 이런 경로가 남는다 — 이 저장소의 `body_start=""`(`str.find("")`가 `0`을 반환) 함정과 같은 클래스다. **문자열로 조립되는 설정값은 타입까지 생성 시점에 막는다.**
