> **Note**: `supabase-schema-migration`은 위 발견에 대응해 laborconsult를 다른 앱과 공유하던 Supabase `public` 스키마에서 **전용 `laborconsult` 스키마**로 전면 이전한 사이클 — 테이블 9종·RPC 8종·Storage 버킷 1. 사고의 실제 메커니즘은 `SECURITY DEFINER` 함수의 `SET search_path = public, pg_temp`였다: 정의자 권한으로 돌면서 미지정 참조가 `search_path`로 해석되므로 `purge_expired_data()`의 `DELETE FROM board_posts`가 **다른 앱의 게시글을 지우도록** 작성돼 있었다(pg_cron 미활성이라 실행된 적은 없음을 확인). `search_path`에서 `public`을 제거하고 전 객체를 스키마 한정했으며, DB 실측(`pg_proc.proconfig`)과 CI 회귀(D7) 이중으로 고정했다. DDL은 패치 재생이 아니라 **최종 상태 4파일로 통합** — 이전 프로젝트 전환에서 base만 적용하고 패치를 놓쳐 `session_data`·`law_article_cache`가 빠진 채 프로덕션이 돌았던 전례 때문이다. 접속 생성부 5곳(`legal_api.py`의 별도 클라이언트 포함)을 `make_supabase_client()` 하나로 모으고 기본 스키마를 `laborconsult`로 뒀다(fail-closed). **검증 과정에서 두 가지를 추가로 잡았다**: ① 커스텀 스키마엔 Supabase 기본 권한이 자동 부여되지 않아 테이블 GRANT·함수 EXECUTE가 각각 빠졌다(같은 클래스로 두 번 걸린 뒤 원리로 규약화) ② `postgrest-py`의 `.maybe_single().execute()`가 0행일 때 `None`을 반환해 404가 500이 되던 결함 5곳 — `board_detail`이 `qa_conversations`를 먼저 조회하는 구조라 **사용자 글 상세는 한 번도 열린 적이 없었다.** 정적 분석·스키마 대조·단위 테스트 어느 것도 못 잡는 유형이고, Gap 분석에서 미검증으로 남겼던 종단 검증(G-1)을 실제로 실행해서야 드러났다. 프리뷰·프로덕션 양쪽에서 게시판 글쓰기~삭제 전 구간 통과. **게시판 글쓰기는 배포된 채 100% HTTP 500이었고 이 사이클에서 처음 작동한다.** 잔여: pg_cron 미등록, 옛 프로젝트 상담 원문 248건 방침.
