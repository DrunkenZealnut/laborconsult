# bm25-memory-scaling Design

> Plan: `docs/01-plan/features/bm25-memory-scaling.plan.md`
> 상태: Design 완료 / Do 대기
> **Plan 대비 축소** — 실측이 M2(메타만 상주)를 불필요하게 만들었다(§2).

## 1. 실측이 설계를 단순화했다

Plan은 세 축(M1 스트리밍 · M2 메타만 상주 · M4 Vercel 상향)을 두고 조합을 예상했다. 프로토타입으로 세 조합을 **별도 프로세스**에서 재보니 결론이 달라졌다:

| 방식 | 피크 RSS | 한도(1024MB) 대비 | 로드 시간 |
|---|---:|---:|---:|
| 현행 (배열 일괄 로드) | 692MB | 68% | 2.7초 |
| A: 스트리밍 + `text` 미보관 | 330MB | 32% | 2.8초 |
| **B: 스트리밍 + `text` 전문 보관** | **415MB** | **41%** | **2.8초** |
| C: 스트리밍 + `text` 300자 | 372MB | 36% | 2.9초 |

**B를 채택한다.** A가 85MB 더 낮지만, 그 대가로 얻는 복잡도가 이득에 비해 크다:

- BM25 결과의 **98%가 dense에 없는 전용 hit**이다(실측 12주제, 124건 중 121건 · 질의당 평균 10.1건). `text`를 버리면 **거의 모든 BM25 hit**에 대해 Pinecone `fetch`로 본문을 되채워야 한다.
- `format_pinecone_hits`는 `content`가 빈 hit을 버린다 — 보충이 실패하면 **BM25 결과가 통째로 사라진다**. 검색이 조용히 Dense-only가 되는 것을 막으려는 사이클에서 새로운 조용한 실패 경로를 만드는 셈이다.
- 매 검색 왕복이 1회 늘고, 그만큼 지연·장애 표면이 커진다.

**즉 이 사이클의 실질 변경은 M1(스트리밍) 하나다.** M2는 기각하고, M4(Vercel 메모리 상향)는 41%로 충분하므로 착수하지 않는다 — `builds`→`functions` 마이그레이션 위험을 지지 않아도 된다.

### 1.1 목표치 조정

Plan §5의 "피크 ≤ 400MB"는 실측 전 임의값이었다. 실질 기준은 **한도 대비 여유**이고 41%면 목표(≤40%)와 사실상 같다. 여유 문서 수가 더 의미 있는 지표다.

| 지표 | 현재 | Plan 목표 | **Design 목표** |
|---|---:|---:|---:|
| 로드 피크 | 692MB | ≤ 400MB | **≤ 450MB** |
| 한도 대비 | 68% | ≤ 40% | **≤ 45%** |
| 여유 문서 수 | 약 3.7만 | ≥ 15만 | **≥ 6만** |
| 검색 결과 | — | 불변 | **불변**(필드·점수·순위) |

여유 문서 수 6만은 현재 76,983건의 **78% 추가 여유**다. Plan의 15만은 A안(330MB) 전제였고, B안에서는 (1024−415)/90×1만 ≈ 6.8만이다.

## 2. 변경 설계

### 2.1 코퍼스 포맷 — JSONL

현재 `data/bm25_corpus.json.gz`는 **JSON 배열**이라 `json.load()`가 전체를 파싱해야 한다. 배열 파싱 중에는 코퍼스 dict 전체(437MB)와 이후 토큰 리스트가 **동시에** 살아 있고, 그것이 피크의 원인이다.

**JSONL**(줄 단위 JSON)로 바꾸면 한 문서씩 읽어 토큰화하고 그 줄의 dict를 즉시 놓아줄 수 있다.

```text
data/bm25_corpus.jsonl.gz   ← 신규 (한 줄 = 문서 1건)
data/bm25_corpus.json.gz    ← 구 포맷, 당분간 폴백으로 계속 읽는다
```

- 파일 크기는 동일하다(19.8MB gz). gzip은 줄 단위여도 압축률이 같다.
- **구·신 포맷을 모두 읽는다.** 배포 순서 때문이다 — 코드가 먼저 나가고 gz가 나중일 수 있고 그 반대도 가능하다. 구 포맷 지원 제거는 전환이 끝난 뒤 별도 커밋으로 한다.

### 2.2 로더

```python
def load_bm25_corpus() -> bool:
    # 1) .jsonl.gz 있으면 스트리밍, 없으면 .json.gz 일괄(구 경로)
    # 2) 한 줄 읽기 → 토큰화(인터닝) → 필요한 필드만 담은 dict를 corpus에 append
    # 3) 원본 줄 dict는 루프를 벗어나며 해제된다
    # 4) BM25Okapi 구축 후 토큰 리스트 명시 해제
```

지켜야 할 것:

- **인터닝을 유지한다.** 토큰 94.1%가 중복이라(549만 → 고유 32.6만) 이것 없이는 스트리밍을 해도 한도를 넘는다. 회귀 `test_bm25_interning`이 이미 고정 중이며, 로더를 재작성하면서 빠뜨리기 쉬운 지점이다.
- **보관 필드를 명시한다.** 원본 줄 dict를 그대로 `append`하면 스트리밍의 의미가 없다(같은 객체를 계속 들고 있게 된다). `id·title·section·source_type·book_id·text`만 새 dict로 옮긴다.
- **`BM25_MAX_DOCS` 절단이 파싱 이후가 아니라 루프 안에서 일어난다** — 스트리밍이라 이제 이 상수가 실제로 메모리를 제한한다(기존 주석의 "메모리 상한이 아니다"가 무효가 되므로 함께 고친다).

### 2.3 빌더

`build_bm25_corpus.py`가 `.jsonl.gz`를 쓰도록 바꾼다. 기존 가드(NS별 0건·직전 대비 20% 초과 감소·원자적 교체)는 그대로 유지한다.

- 산출 파일명이 바뀌므로 **`.gitignore`·CLAUDE.md의 "gz 커밋 필수" 문구도 함께 갱신**한다. 커밋을 빠뜨리면 프로덕션이 Dense-only로 조용히 폴백한다(기존 규약).
- 전환 시점에 구 `.json.gz`를 저장소에서 바로 지우지 않는다 — 롤백 여지를 남긴다.

## 3. 회귀 — 메모리를 테스트로 고정

지금까지 메모리는 **사람이 기억해서 재는 값**이었고, 그래서 119%가 될 때까지 아무도 몰랐다. 이번 사이클의 가장 오래 남는 산출물은 이 테스트다.

```text
test_bm25_memory.py (신규, CI 편입)
  1) 별도 프로세스에서 load_bm25_corpus() 실행
  2) ru_maxrss를 상한과 비교, 초과 시 실패
  3) 검색 결과 동일성: 고정 쿼리 N건의 상위 id·score가 기준값과 일치
```

설계상 주의:

- **반드시 별도 프로세스**에서 잰다. `ru_maxrss`는 프로세스 최대치라 같은 프로세스에서 다른 테스트가 먼저 메모리를 쓰면 오염된다(Plan §4-d).
- **경고가 아니라 실패**로 둔다. 경고는 읽히지 않는다 — 그것이 지금 상태를 만든 원인이다.
- 상한은 실측(415MB)에 여유를 둔 **550MB**. 너무 빡빡하면 CI 환경 차이로 흔들리고, 너무 느슨하면 회귀를 못 잡는다. 한도의 54%라 초과해도 즉시 위험하지는 않은 지점이다.
- ⚠️ **실패했을 때 상한을 올리는 것이 기본 대응이 아니다.** 코퍼스가 늘어 넘었다면 그때가 다음 구조 개선(A안·샤딩·Vercel 상향)을 검토할 시점이다. 상한 상향은 그 판단을 한 뒤에만 한다.
- 로컬 macOS와 CI(Linux)의 절대값이 다를 수 있다 — Do 단계에서 CI 실측 후 상한을 확정한다.

### 3.1 검색 결과 불변 검증

메모리 최적화가 검색을 바꾸면 안 된다(Plan 비목표). 전환 전후로 같은 쿼리의 상위 결과를 대조한다.

- 고정 쿼리 5~10건의 `(id, score)` 상위 5개를 기준값으로 저장.
- 인터닝·스트리밍은 **같은 문자열을 공유할 뿐 값을 바꾸지 않으므로** 점수가 완전히 일치해야 한다. 불일치는 곧 결함이다.

## 4. 함정 (Plan §4 + Design 단계 추가)

| # | 함정 | 대응 |
|---|------|------|
| a | 원본 줄 dict를 그대로 보관하면 스트리밍 이득이 사라진다 | 필요한 필드만 새 dict로 복사(§2.2) |
| b | 로더 재작성 중 **인터닝 누락** | 회귀 `test_bm25_interning` 유지 + 메모리 테스트가 이중으로 잡는다 |
| c | 배포 순서 불일치(코드↔데이터) | 구·신 포맷 양쪽 지원(§2.1) |
| d | `ru_maxrss` 오염 | 별도 프로세스 측정(§3) |
| e | 소프트 `MemoryError`가 Dense-only로 조용히 흡수 | 이번 사이클이 줄이려는 대상. 로더 실패 시 로그 레벨을 warning 이상으로 유지 |
| f | **CI 시간 증가** | 코퍼스 로드가 2.8초 + gz 읽기. 기존 오프라인 스위트(수 초)에 얹히므로 허용 범위이나 Do에서 실측 확인 |
| g | **`.jsonl.gz` 미커밋** | 기존 `.json.gz`와 같은 규약 — 빠뜨리면 프로덕션이 Dense-only. CLAUDE.md 문구를 파일명과 함께 갱신 |
