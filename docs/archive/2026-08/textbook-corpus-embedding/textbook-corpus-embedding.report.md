## 3. 배운 것

### 3.1 두 방어가 서로를 무력화할 수 있다

`OCR_FIXES`(오인식 사건번호 정정 사전)를 **추출 이후** 적용했는데, 부호 화이트리스트가
오인식 부호(`대`·`도다`)를 걸러내므로 그 사전은 **어떤 입력에도 발동할 수 없는 사문 코드**였다.
화이트리스트가 오염을 막는 바로 그 성질이 정정 경로를 차단한 것이다. Win 본문에 오인식 표기가
실제 6회 있었다.

각각은 옳은 방어인데 순서 때문에 하나가 죽었다. 주석은 "fetch와 동일 사전 재사용"이라고
적혀 있어 **작동한다는 잘못된 신호**까지 줬다. 회귀는 T20-j/k로 고정.

### 3.2 설계 대비 검증은 설계의 공백을 못 잡는다

gap-detector가 120항목을 설계와 대조해 Match Rate 100%를 냈지만, 이후 `/simplify`와
`code-analyzer`가 **High 2건**을 더 찾았다. 둘 다 설계 자체의 공백이라 대조로는 잡히지 않았다.

- **P-1 가드 누수** — G1~G3을 `CONSULTATION_SYSTEM_PROMPT`에만 넣었는데 답변 경로가 두 갈래다.
  해설서 청크는 분기와 무관하게 컨텍스트에 실리므로 임금계산·괴롭힘 판정·법제처 실패 경로에서
  **저작물이 무가드로 LLM에 들어갔다.** 설계 §4.3은 `COMPOSER_SYSTEM`(사용처 0)만 확인했고,
  `pipeline.py`에 인라인으로 있는 `SYSTEM_PROMPT_TEMPLATE`은 `prompts.py` grep에 걸리지 않았다.
- **P-2 공개 재게시** — Plan §3.2는 "코퍼스는 비공개 검색 백엔드다"를 저작권 결정의 근거로
  삼았는데, `chunk_text` 미노출만 따졌고 **답변이 공개 게시판에 전문 게시된다는 사실**을
  다루지 않았다. G1이 실패하면 저작물 문장이 크롤 가능한 페이지가 된다.

교훈 — "설계대로 만들었는가"와 "이 변경이 닿는 경로를 다 봤는가"는 다른 질문이다. 후자는
설계를 기준으로는 물을 수 없다.

### 3.3 조용한 실패를 코드로 봉인해야 한다

이 사이클에서 잡은 결함은 **전부 예외도 로그도 남기지 않는** 유형이었다.

| 결함 | 증상 |
|------|------|
| chunk_id 충돌 | Pinecone upsert가 조용히 덮어씀 (177건) |
| 가드 부착 조건 끊김 | 로그도 예외도 없이 무가드 |
| BM25의 `book_id` 부재 | G4가 그대로 우회 |
| 폐기율 분모 오류 | 정상 서적이 게이트에 걸릴 수 있음 |
| 헤딩 0개 | 게이트를 통과해 책 전체가 단일 섹션 |
| `sync_overlap` ImportError | 함수 안 import라 **실행 시점에야** 죽음 |
| SW 캐시 | 수정이 반영 안 됐는데 화면은 정상 (실제로 검증 중 겪음) |

신규 assertion 67건은 대부분 이것들을 고정하는 데 쓰였다.

### 3.4 규모를 재기 전에 규격을 의심할 것

주해 Ⅲ에서 사건번호를 뽑을 때 기존 정규식을 그대로 썼다면 308건 중 **113건이 조문 표기
노이즈**였다(`43조의2` 31회 등). 조문 해설서는 판례 수험서보다 조문 표기 밀도가 훨씬 높아,
Win 노동법에서는 드러나지 않던 오염이었다. 같은 도구도 데이터 성격이 바뀌면 규격을 다시 봐야 한다.
