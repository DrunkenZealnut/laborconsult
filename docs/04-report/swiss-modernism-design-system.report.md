### 5.3 자체 재점검에서 발견한 결함 (보고서 작성 직전)

Check·Act·CodeRabbit 세 단계를 모두 통과한 뒤에도 4건이 남아 있었다 — 전부 **원본부터 어느 diff에도 걸리지 않은 잔재**였다.

| 결함 | 원인 | 발견 방법 |
|------|------|-----------|
| `board.html`이 여전히 Google Fonts `Noto Serif KR` 로드 | Do 단계에서 CSS 변수만 지우고 `<link>` 태그를 안 지움. 검증 grep이 `'Noto Serif KR'`(공백)로 찾았는데 실제 URL은 `Noto+Serif+KR`(URL 인코딩)이라 거짓 음성 | `getComputedStyle`로 실제 렌더 폰트 확인 |
| `board.html` "질문" 배지가 파랑(`#2980b9`)으로 잔존 | 토큰 치환 스크립트가 건드리지 않은 원본 그대로의 규칙 | 하드코딩 hex 전수 재검색 |
| 질문하기·삭제 버튼이 HTML 숫자 엔티티(`&#9998;` `&#128465;`)로 이모지 표시 | Do 단계 이모지 스캔이 리터럴 유니코드 문자만 봐서 엔티티 인코딩을 놓침 | 엔티티 패턴 전수 재검색 |
| `index.html` 이메일 모달 오버레이가 삭제 대상이던 `--navy-deep`(`#0F1B30`) 그대로 | rgba 하드코딩이라 토큰 제거 대상 목록(hex 문자열 매칭)에 안 걸림 | rgba 3자리 십진수를 hex로 역산해 대조 |

**시사점**: 정적 검증(grep)은 공백·인코딩 차이로 거짓 음성을 낸다. 문자 이모지 스캔은 HTML 엔티티를 못 잡는다. hex 매칭은 rgba 십진수로 우회된 색을 못 잡는다. 각 검증 방법에는 사각지대가 있고, 사각지대는 방법을 바꿔야 보인다.

## 6. 회고

### 6.1 잘한 것 (Keep)

- **대비를 계산으로 검증한 것.** 액센트 hover 방향("8% 어둡게" vs "밝게"), 버튼 글자색(흰색 vs 오프블랙) 두 가지가 암산과 반대로 나왔다. 계산 없이 규격 문구만 따랐다면 AA 미달 상태로 병합됐을 것이다.
- **설계서를 예외의 단일 기록처로 쓴 것.** 흐름도 색 정책, 스페이싱 이연, 컨테이너 범위 축소— 전부 §8에 근거와 함께 남겨서 다음 사이클이 설계 없이 바로 착수할 수 있다.
- **각 단계가 서로 다른 결함을 잡은 것.** 정적 분석(Check) → 브라우저 실측(Act-1) → 외부 리뷰(CodeRabbit) → 자체 재점검. 넷 다 필요했다 — 하나를 생략했다면 그 단계가 잡은 결함만큼 남았을 것이다.

### 6.2 개선이 필요한 것 (Problem)

- **Do 단계의 기계 치환이 대형 페이지에서 절반의 성공이었다.** 색·서체처럼 이름이 있는 값은 1:1 치환이 통했지만, 타이포·스페이싱처럼 문맥 판단이 필요한 값은 치환 스크립트가 건드리지 못하고 지나쳤다. Check 71%가 이걸 드러냈다.
- **검증 grep 자체에 거짓 음성이 있었다.** `Noto Serif KR` 검색이 URL 인코딩(`+`)을 못 잡았다. "grep으로 0건 확인"이 "실제로 0건"을 보장하지 않는다는 걸 이번에 체감했다.
- **이모지 스캔이 인코딩 하나(리터럴 유니코드)만 봤다.** HTML 숫자 엔티티라는 두 번째 인코딩 경로를 놓쳤다.

### 6.3 다음에 시도할 것 (Try)

- **하드코딩 색 검색에 rgba 십진수 역산을 기본으로 포함한다.** 이번엔 우연히 알아챘지만, hex 문자열 매칭만으로는 구조적으로 놓칠 수밖에 없는 사각지대다.
- **"완료" 선언 전에 검증 방법을 최소 2가지로 다양화한다.** grep(패턴) + 실제 렌더(`getComputedStyle`) + 브라우저 실측(대비) 세 가지가 서로 다른 결함을 잡았다. 하나만 썼다면 이번 보고서도 틀린 채로 나갔을 것이다.
- **다음 사이클(흐름도 25종)은 착수 전 매핑표부터 고정한다.** 하드코딩 hex 2,888회는 이름이 아예 없어 기계 치환이 원천 불가능하다. 색당 매핑을 먼저 정하지 않으면 이번과 같은 절반의 성공이 반복된다.

## 7. 프로세스 개선 제안

### 7.1 PDCA 프로세스

| 단계 | 현재 | 개선 제안 |
|------|------|-----------|
| Do | 대형 파일에 기계 치환만 적용 | 색처럼 이름 있는 축과 스페이싱처럼 문맥 판단이 필요한 축을 애초에 분리해 각기 다른 방법을 쓴다 |
| Check | grep 기반 정적 집계 | 브라우저 실측(대비·렌더 확인)을 Check 단계 자체에 포함시켜 Act로 미루지 않는다 |
| Act | 완료 보고서 직전 재점검이 별도 절차였음 | "보고서 작성 = 최종 재점검"을 PDCA report 단계의 명시적 체크리스트 항목으로 둔다 |

### 7.2 도구/환경

| 영역 | 개선 제안 | 기대 효과 |
|------|-----------|-----------|
| 검증 스크립트 | 하드코딩 색 검색에 hex + rgba 십진수 역산을 함께 돌리는 헬퍼 고정 | 이번 발견한 사각지대 재발 방지 |
| 이모지 스캔 | 유니코드 리터럴 + HTML 숫자 엔티티(`&#...;`) 동시 검사 | 표시용 이모지 누락 방지 |
| CI | Playwright 대비 감사를 오프라인 스위트에 추가하는 것 검토 | 매 사이클 수동 검증 불필요 |
