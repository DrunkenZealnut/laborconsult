# 상담 답변 PDCA 품질 구축 설계

## 1. 목적

노동상담 답변 파이프라인을 다음 다섯 단계의 반복 가능한 PDCA 체계로 구축한다.

1. 고정 상담 평가셋과 평가 하네스
2. 법조문 인용 검증
3. 정보 부족 질문의 위험도 라우팅
4. 사용자·전문가 피드백 저장
5. 정기 평가와 개선 루프

목표는 단순히 코드 경로가 존재하는 상태가 아니라, 답변의 정확성·근거성·안전성·계산 결과를 측정하고 다음 개선 작업으로 연결할 수 있는 상태다.

## 2. 현재 기준선

현재 답변 파이프라인은 `app/core/pipeline.py`에서 의도분석, 계산기·괴롭힘 판정, 법령·판례·RAG 조회, 컨텍스트 조립, 다중 LLM 폴백, 면책·절단 고지, 판례·행정해석 인용 검증, 상담사례 대조, 저장을 순서대로 수행한다.

현재 이미 보호되는 계약은 다음과 같다.

- 계산 결과는 계산기의 결과를 우선 사용한다.
- Claude → OpenAI → Gemini 순서의 답변 폴백이 있다.
- 빈 답변과 스트림 절단을 실패 또는 절단으로 구분한다.
- 판례번호·행정해석 문서번호는 검색 결과 화이트리스트로 검증한다.
- 면책 고지는 코드에서 보장한다.
- 절단·가드 의심·저작권 관련 답변은 공개 게시판에서 제외한다.

현재 확인된 품질 공백은 다음과 같다.

- 최종 답변의 법조문 번호·내용은 판례·행정해석과 같은 사후 검증을 받지 않는다.
- 상담 평가셋과 운영 답변 품질 지표가 하나의 실행 경로로 묶여 있지 않다.
- 정보 부족 질문의 모든 유형이 가능한 범위에서 답변되는 구조라, 고위험 사실관계 누락을 별도 차단하지 않는다.
- 사용자 평가와 전문가 교정 결과를 저장하는 표준 피드백 계약이 없다.
- 설계 문서상 `legal_consultation.py`의 책임과 현재 구현상 실제 멀티소스 RAG 책임이 분리되어 있다.

## 3. 범위와 비범위

### 포함

- 상담용 고정 평가 fixture와 실행기
- 답변·근거 품질 지표 및 실패 분류
- 법조문 인용 검증 및 안전한 교정
- 정보 부족 필드의 위험도 분류와 답변 정책
- 피드백 메타데이터 저장과 운영 검토용 조회 기반
- 정기 실행 가능한 PDCA 명령과 배포 게이트

### 제외

- 새로운 법률 데이터 크롤링
- LLM 제공자 교체
- 계산기 산식 자체의 재설계
- 기존 공개 게시판의 사용자 경험 전면 개편
- 사용자 개인별 법률자문 또는 자동 사건 수임

## 4. 대안 검토

### 대안 A — 일괄 리팩터링

평가·검증·라우팅·피드백을 한 번에 수정한다. 구현 속도는 빠르지만 답변 품질 변화의 원인을 분리할 수 없고, 법률상담 경로의 회귀 위험이 크다.

### 대안 B — 단계별 PDCA 구축 (권장)

평가셋을 먼저 고정하고, 기준선을 측정한 뒤 검증기·라우팅·피드백을 순서대로 추가한다. 각 단계가 이전 단계의 측정 결과를 입력으로 사용하므로 실패 원인을 분리할 수 있고, 운영 동작 변경을 단계별로 제한할 수 있다.

### 대안 C — 운영 대시보드 우선

먼저 로그와 통계 화면을 만들고 답변 품질 문제를 수집한다. 운영 가시성은 빨리 얻지만, 법조문 오류나 고위험 정보 누락을 즉시 막지 못한다.

대안 B를 선택한다. 상담 답변은 잘못된 법률 정보의 비용이 높으므로 측정 기준을 먼저 고정하고, 이후 동작을 바꾸는 순서가 가장 안전하다.

## 5. 목표 아키텍처

```text
사용자 질문
    │
    ├─ 기존 상담 파이프라인
    │   ├─ 의도·주제 분석
    │   ├─ 계산/판정 도구
    │   ├─ 법령·판례·RAG 검색
    │   ├─ 답변 생성
    │   └─ 사후 검증·저장
    │
    ├─ Answer Evidence Contract
    │   ├─ 사용한 소스 목록
    │   ├─ 법령·판례·행정해석 허용 인용
    │   ├─ 가정·누락 정보
    │   └─ 위험도·검증 결과
    │
    └─ PDCA 평가 계층
        ├─ 고정 평가셋 실행기
        ├─ 자동 품질 지표
        ├─ 전문가 검토 표본
        └─ 다음 개선 사이클 입력
```

핵심 원칙은 답변 생성과 품질 평가를 분리하는 것이다. 평가 하네스는 동일한 파이프라인과 동일한 소스 계약을 사용하지만, 평가 결과가 사용자 답변을 직접 오염시키지 않도록 별도의 실행 경로로 둔다.

## 6. 단계별 설계

### 6.1 1단계 — 고정 상담 평가셋·평가 하네스

#### 산출물

- `data/eval_consultation_queries.json`
- `eval_consultation.py`
- 평가 결과 JSON 스키마와 요약 출력
- fixture 구조·정답 라벨을 검증하는 오프라인 테스트

#### 평가셋 구성

초기 60건으로 시작하고, 다음 분포를 고정한다.

| 영역 | 건수 |
|---|---:|
| 임금·계산 | 10 |
| 해고·징계·구제절차 | 10 |
| 근로시간·휴일·연차 | 10 |
| 퇴직금·퇴직·고용보험 | 8 |
| 산재·괴롭힘·차별 | 8 |
| 판례·행정해석·법령 조회 | 8 |
| 정보 부족·복합·구어체 질문 | 6 |
| **합계** | **60** |

각 항목은 다음 필드를 갖는다.

- `id`, `category`, `question`
- `expected_intent`, `expected_topic`
- `required_laws`, `allowed_sources`
- `expected_calculation`, `expected_values`
- `required_notices`, `forbidden_claims`
- `risk_level`

개인정보가 포함된 실제 상담 원문은 fixture에 직접 넣지 않고, 비식별화된 합성 질문을 사용한다.

#### 지표

- 의도·주제 라우팅 정확도: 목표 95% 이상
- 계산 결과 정확도: 목표 100%
- 필수 법적 근거 포함률: 목표 90% 이상
- 판례·행정해석 환각: 0건
- 면책 고지 포함률: 100%
- 절단·가드 제외 답변의 공개 노출: 0건
- 답변 생성 P95 시간: 기준선 측정 후 회귀 한계 설정

자동 평가로 판정할 수 없는 법적 적절성은 전체의 10% 이상을 전문가 블라인드 검토 대상으로 둔다.

### 6.2 2단계 — 법조문 인용 검증

#### 책임 분리

`app/core/citation_validator.py`에 법조문 전용 검증을 추가하되, 기존 판례·행정해석 검증 API를 변경하지 않는다.

검증기는 다음 입력을 받는다.

- 답변 전문
- API가 실제 반환한 법률명·조문번호·조문 텍스트
- 허용된 법령 출처 목록

검증 결과는 다음 형태로 통일한다.

```json
{
  "total_laws_cited": 0,
  "valid": [],
  "hallucinated": [],
  "mismatched": [],
  "warnings": []
}
```

#### 실패 처리

- 법률명·조문번호가 확인되지 않으면 해당 번호만 제거한다.
- 내용까지 대조할 수 없으면 내용을 임의로 재생성하지 않고 확인 필요 경고를 붙인다.
- 교정 실패 시 원답변을 성공 답변으로 가장하지 않고 `metadata.llm.law_citation_fixed=false`를 저장한다.
- 기존 판례·행정해석 교정과 동일한 단계 예산·하트비트 계약을 사용한다.

### 6.3 3단계 — 정보 부족 질문 위험도 라우팅

기존의 “가능한 범위에서 답변” 정책을 유지하되, 누락 필드의 위험도에 따라 정책을 나눈다.

| 위험도 | 예시 | 정책 |
|---|---|---|
| 낮음 | 단순 개념 설명, 선택적 계산 정보 | 가정 후 답변하고 가정 명시 |
| 중간 | 임금액·근무시간 일부 누락 | 범위 답변 또는 조건부 계산 |
| 높음 | 해고일, 사업장 규모, 근로자성, 신청기한 | 결론 제한·핵심 정보 요청 |

위험도는 계산 유형과 `AnalysisResult`의 `missing_info`를 조합해 코드로 결정한다. LLM이 자유형으로 위험도를 결정하지 않도록 필드별 정책 레지스트리를 둔다.

고위험 누락 시에도 사용자를 빈 답변으로 돌려보내지 않고 다음 세 가지를 제공한다.

1. 현재 확인 가능한 일반 원칙
2. 결론을 바꾸는 누락 사실
3. 다음 답변에 필요한 최소 정보

### 6.4 4단계 — 사용자·전문가 피드백 저장

기존 `qa_conversations.metadata`에 호환 가능한 중첩 객체를 추가한다.

```json
{
  "quality": {
    "risk_level": "medium",
    "assumption_used": true,
    "retrieved_source_mix": {"law": 2, "precedent": 1, "counsel": 2},
    "law_citation_checked": true,
    "required_evidence_coverage": 0.9,
    "expert_review_required": false
  },
  "feedback": {
    "user_rating": null,
    "user_reported_issue": null,
    "expert_status": "unreviewed",
    "expert_correction": null
  }
}
```

사용자 피드백은 별도 공개 게시판 데이터로 취급하지 않는다. 개인정보와 원문 답변을 불필요하게 복제하지 않으며, 전문가 교정은 관리자 전용 조회 경로에서만 사용한다.

### 6.5 5단계 — 정기 PDCA 실행 체계

다음 명령으로 동일 평가를 반복 실행할 수 있도록 한다.

```text
python3 eval_consultation.py --offline
python3 eval_consultation.py --live --limit 60
```

- `--offline`: 스키마·라우팅·검증기·지표 계산만 검증
- `--live`: 외부 API와 LLM을 사용해 실제 답변 품질 측정
- 결과에는 코드 버전, 평가셋 버전, 모델, 인덱스, 실행 시각을 기록

배포 게이트는 다음과 같이 둔다.

- P0: 계산값 오류, 확인되지 않은 법조문·판례의 단정, 절단 답변 공개 노출 → 배포 차단
- P1: 라우팅 정확도 95% 미만, 필수 근거 포함률 90% 미만 → 수정 후 재평가
- P2: 표현·렌더링·지연 회귀 → 다음 사이클 이월 가능

정기 실행 결과는 이전 기준선과 비교하고, 실패 질문을 다음 평가셋 보강 후보로 만든다.

## 7. 데이터 흐름과 오류 처리

```text
질문
  → 분석 결과 + missing_info
  → 위험도 판정
  → 검색·도구 실행
  → evidence contract 생성
  → LLM 답변
  → 법령/판례/행정해석 사후 검증
  → 고지·교정
  → 답변·품질 메타데이터 저장
```

외부 API 실패는 기존 graceful degradation을 유지한다. 단, 고위험 질문에서 필수 법령 조회가 실패한 경우에는 일반 지식을 현행 법령처럼 단정하지 않고 확인 필요 안내를 남긴다.

## 8. 테스트 전략

각 단계에 다음 테스트를 추가한다.

- 평가셋 스키마와 중복 ID 검증
- 지표 계산 단위 테스트
- 법조문 번호·법률명·내용 불일치 테스트
- 법조문 검증 실패 시 원답변 보호 테스트
- 위험도별 missing-info 라우팅 테스트
- 품질 메타데이터 저장·공개 게시판 제외 회귀 테스트
- 기존 계산기 골든·LLM 폴백·인용 검증 테스트 회귀
- 라이브 실행은 별도 수동 게이트로 수행하고, 키 없는 CI에서는 오프라인 계약만 검증

## 9. 롤아웃 순서

1. 평가셋과 오프라인 하네스만 추가하고 기준선 기록
2. 법조문 검증기를 비차단 관측 모드로 배포
3. 법조문 오류·교정 성공률 확인 후 차단 정책 활성화
4. 저위험 missing-info 라우팅부터 활성화
5. 고위험 라우팅을 제한된 질문군에 적용
6. 피드백 저장과 관리자 검토 연결
7. 정기 평가와 배포 게이트 활성화

각 단계는 이전 단계의 회귀 테스트와 고정 평가셋 기준선을 통과해야 다음 단계로 이동한다.

## 10. 완료 기준

전체 구축 완료는 다음 조건을 모두 만족하는 경우다.

- 고정 평가셋 60건과 재현 가능한 실행기가 저장소에 있다.
- 계산 결과 정확도 100%, 판례·행정해석·법조문 환각 0건을 평가할 수 있다.
- 고위험 정보 누락 질문에 대한 명시적 정책과 회귀 테스트가 있다.
- 사용자·전문가 피드백이 기존 저장 구조와 호환되게 기록된다.
- 배포 전 평가 명령과 P0/P1 게이트가 문서화되고 실행 가능하다.
- 기존 계산기·폴백·보안·공개 게시판 회귀 테스트가 통과한다.
